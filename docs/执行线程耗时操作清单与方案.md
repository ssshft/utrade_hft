# 算法执行线程：耗时操作清单与修改方案

> 范围：`utrade_hft` 里**跑算法单的那一条线程**（`BaseStrategy::heavy_work()`）。
> 目标：把这条线程上所有"可能耗时"的操作找全，逐项判定，给出改法。
> 状态：**A1 / A2 均已实施**（A2 = `SaveSpreadStats` 搬进 `T_signal`；A1 = `SaveSnapshot` 搬进 `T_signal`，见 §4.1）；
> 其余仍只出方案。新增 `tests/thread_cost/` 基准。
> 生成时间：2026-10-22（A2 实施 2026-10-21；A1 实施 2026-10-23；B6 全局持仓闸门 2026-10-26）

## 0. 结论

**这条线程上值得点名的操作一共 15 处：2 处真 IO（必须搬）、5 处每 tick 白做一遍的构造（顺手削）、1 处每秒一次的全局求和（B6，2.75 µs @500，可忽略）、4 处已经在别的线程上（不用动）、3 处不是"耗时"但同位置的真缺陷（一起改）。**

先把量级说清楚，免得改错优先级：

| | 实测（500 个对子） | 折算成每分钟 |
|---|---|---|
| `SaveSnapshot` | **1.53 ms/次** | 6 次 = **9.2 ms** |
| `SaveSpreadStats` | **1.62 ms/次** | 1 次 = **1.6 ms** |
| 合计 | | **10.8 ms / 60000 ms = 0.018%** |

**所以：按当前 500 个对子，它不是盈利问题，是尾延迟问题。** 0.018% 的占空比意味着大约 5700 个信号里才有 1 个正好落在这段停顿里。真正的理由是另外两条：

1. **尾延迟**。上面是 macOS/APFS 的中位数。部署机是 ext4，`rename()` 要过 journal；盘上有日志轮转、快照、别的进程写盘时，单次 `flush()` 可以是**几十到几百毫秒**。这不是"慢了 1.5 ms"，是"这一秒的行情全错过了"。中位数看不出来，p99.9 才看得出来。
2. **线性放大**。实测 1000 个对子是 2.9 ms/次（线性），2000 个就是 5.8 ms。对子数是这个系统唯一确定会涨的量（多找所、多找对子），所以在 500 的时候改，成本最低。

第三条理由是你自己提的那条，也是对的：**规则要跟规模无关**。"这条线程上不做 IO"在 500 个对子时省不下钱，在 3000 个对子时救命；而一条"只在量大的时候才要遵守"的规则，实际上没人会遵守。

**另外，扫这条线程时撞到一个比上面所有项都严重的东西：`m_statsQ` 只有 32 个槽，而它每轮要推"每个对子一条"。超过 32 个对子，第 33 个之后的统计永远推不出去 ⇒ 那些对子永远不开仓，且不报错。** 详见 §5。生产配置现在只有 1 个对子（`etc/config.json` 的 `pairKeys`），所以它是潜伏的；但"对子数会涨"正是这个系统的方向。

## 1. 先画清线程边界

`include/base/base_strategy.h:91-155`，一条 `while(1)` 忙等线程，串行做三件事：

```cpp
while (1) {
    if (tb2TradeRcmd->tryPop(rcmd)) { ... on_ordertrade / on_balance / on_position ... }   // ① 回报
    if (dbpreader) { if (dbpreader->FetchLast()) { idle = false; } }                        // ② 价差
    if (now - utcTime >= timerInterval * 1000) { on_timer(now); utcTime = now; }            // ③ 定时器
}
```

三点必须记住：

- **① 和 ② 是"事件"，③ 是"每秒一次的整表扫描"。** 三者共用一条线程 ⇒ ③ 里任何一次阻塞，都直接顶住 ① 和 ②。
- `on_timer` 的频率是 **1 Hz**，不是 1 ms：`etc/config.json:17` 是 `"timerInterval": 1000`，而 `base_strategy.h:139` 用微秒时间戳比 `timerInterval * 1000`。`base_strategy.h:212` 那句 `int timerInterval{1}; //ms` 的注释是错的，别看它。
- 所以"这条线程每秒被占住多久"= `OnTimer` 一轮的总耗时。下面所有东西都往这个账上记。

`on_timer` 展开后是：`AlgoContext::OnTimer`（执行侧，`AlgoContext.cpp:1231-1628`，约 400 行）+ `PairTradingContext::OnTimer`（策略侧，`PairTradingContext.cpp:1112-1193`，6 个步骤）+ 每 200ms 一次的 `ScanFinishedAlgoOrders`。

B5 是同一个毛病的另一种形态：`PairOrder::pairInstrumentKey`、`BaseAlgoOrder::pairInstrumentKey` 都是 `char[INST_KEY_LEN]`，而 `SpreadManager::GetSpread()` 和 `mSpreadReportCount` 都吃 `std::string`。pair 键是 `"BINANCE_SWAP_BTC-USDT|OKX_SWAP_BTC-USDT"` 这种 33 字符的串，**超过 SSO 的 15 字符 ⇒ 每次隐式转换都是一次 malloc + memcpy**。改法：`GetSpread` 加一个吃 `const char*` 的重载（内部 `mSpread.find(std::string)` 免不了，但至少可以把"每 tick 两次"降到"每 tick 零次"——把算好的键缓存在算法单上），`mSpreadReportCount` 见 B3。

B6 是 2026-10-26 加全局持仓闸门（祖先 `just_close_flag`）时新增的，两点值得记下来，免得以后被"优化"回去：

- **不能改用缓存的 `pi.positionValue`**。它只在 `UpdateOnAlgoOrder` 里刷，两次成交之间的价格变动不会更新 —— 拿它当风控输入，涨了 10% 也看不出来。现算的代价只是一次乘法。
- **也不需要走 `GetAllPairInfos()`**。这里只要一个和、不要指针列表；直接在类内遍历 `m_pairInfoMap`（2.6 µs @500）就够了，不必为了它对外暴露容器。（2026-10-28 之前这里写的是"`GetAllPairInfos()` 要拷一份 vector，5.38 µs，贵一倍"——那个理由已随 B4 的修复失效。）

### D 类 —— 不是"耗时"，但同一条线程上的真问题

这三条顺手记下来，因为它们和你这次问的是同一个位置，改的时候一起改最省事：

**D1 `SpreadManager::GetSpread()` 返回值没判空就解引用 —— 崩在这条线程上。**

`AlgoContext.cpp:1301-1302`：

```cpp
dbp::DbpData* pdata = SpreadManager::Instance().GetSpread(it->second->pairInstrumentKey);
if (eventTime - pdata->generateTs > 30 * second1 && ...)   // ← pdata 可能是 nullptr
```

`GetSpread` 的实现是 `unordered_map<string, unique_ptr<DbpData>>` 查找（`SpreadManager.h:45`），**key 不存在就返回 nullptr**（`SpreadManager.cpp:102-109`）。而这张算法单的价差条目在不在表里，取决于注册时 `AddSpreadPara` / `QuantDbp::Subscribe` 有没有成功 —— **代码里没有任何一处保证它一定成功**。订阅失败一次、或者 key 与 topic 名不一致，这里就是空指针解引用，而它旁边就是报单逻辑。

这条已经在 `docs/writefilecontent_refactor.md` 的 **R4** 里记过，但记的是 `WritePairOrder` 那条路径（`BaseAlgoOrder.cpp:770`）；**`AlgoContext.cpp:1301` 这一处同样的解引用没有被记进去，而它每 tick 都跑**，比 R4 记的那条频率高得多。

**D2 出向队列 `push()` 的返回值被丢掉 —— 队列满时静默丢单。**

`include/command_helper.h` 的 `add_new_order` / `cancel_order` / `query_order` / `query_account` 四个函数，结尾都是：

```cpp
iter->second->push(tcmd);        // 返回值是 QueueStatus::Ok / Full / Invalid，没人看
```

`ShmSpscQueue::push`（`include/ShmSpscQueue.h:353-367`）**永不阻塞，满时返回 `Full` 并丢弃**。于是队列满 ⇒ 这张单没发出去 ⇒ 但 `QuantTrade::CreateOrder` 返回 `true`（`QuantTrade.h:22-29` 无条件 `return true`）⇒ `UpdateAlgoPairOrderByInsertQuantOrder` 照样把它登记成在途 ⇒ 策略等一个永远不来的回报。4096 槽不容易满，但"不容易"和"不可能"是两件事，而且失败方式是静默的。

**D3 `LOG_DEBUG("{}", tcmd.getString())` —— 每张单无条件做两次 `fmt::format`。**

同样是 `command_helper.h`，四个出向函数里各有一处（`:95`、`:118`、`:141`、`:159`）。`getString()`（`pubsub_protocol.h:324-348`）先 `fmt::format("[{}]")`，再 `append` 一个 `fmt::format` 出来的 15 字段串 —— **2 次堆分配 + 一次完整格式化**，而且因为它是宏参数，**无论日志级别是什么都会被求值**。

这条**账本里没有**：`docs/全系统字符串格式化与延迟项清单.md` 的 P1 段列了 `tb` 侧的 `getString()`（P1-3/P1-4），但 `command_helper.h` 这四处是 `utrade_hft` 的出向边界，漏掉了。按账本自己的分级标准，它是 **P1（每单路径）**。

## 3. 为什么 A 类不能只换格式化函数

`tests/thread_cost/` 把 500 行的 `SaveSnapshot` 拆成三段量了一遍：

```
snprintf 格式化到内存      :   484 µs
ofstream<< 格式化到内存    :   828 µs   (1.7x snprintf)
ofstream<< + flush + rename:  1534 µs
```

- **格式化占 54%，IO 占 46%。** 两个都不是可以忽略的量级。
- 所以"把 `ofstream <<` 换成 `snprintf`"只能省 1/3，剩下的 700 µs 还是 `open/write/flush/rename` 四个系统调用。
- 反过来"只把写盘挪走、格式化留在主线程"也省不干净 —— 825 µs 的格式化还在。
- **正确做法是整段搬走：格式化和落盘都在后台线程。** 主线程只负责"把当前状态拷成一段 POD"。

## 4. 方案

### 4.1 A 类：快照与统计落盘搬到后台线程

#### 数据流（已实施，2026-10-23）

```
交易线程（heavy_work -> OnTimer 第 6 步）        T_signal（已有线程，1s 一轮，睡等不占核）
────────────────────────────────────           ──────────────────────────────────
CollectSnapshotRows()
  PairInfo -> PairInfoRecord × N（字段搬运，16.3 µs @500）
        │
        └─ push N 行 + 1 个空 pairKey 的哨兵 ──►  RunSignalOnce 第 3 步：pop 到队列空
                                                 - 遇到哨兵：整份重写一次 + clear
                                                 - 没遇到：留在 m_snapWrite 跨轮攒
                                                 WritePairInfoRecordFile：整份重写
                                                 ofstream<<setprecision(17) -> .tmp -> rename
```

**为什么没单开一条写盘线程**：10s 一版、1.5 ms 的写，占空比 0.015%，挂在本来就是 1s 一轮的
`T_signal` 上可以忽略。独立线程唯一的好处是"磁盘卡住不拖累分位数"，代价却是多一条线程、
多一次 join、以及 ⑥ 那条 `pre_stop` 顺序约束。挂上去之后，那条约束**结构上不存在**了：
`StopSignalThread()` 一返回就不可能还有 `rename` 在飞。

#### 关键设计决策

**① 为什么是"行的队列"，而不是"整份快照的队列"，也不是单槽邮箱。**

| 方案 | 主线程每次 | 内存 | 问题 |
|---|---|---|---|
| 整份快照入队（172 KB/元素） | 拷 172 KB | 定长槽 × 容量 = 数 MB 常驻 | 172 KB 的 `vector` 不是平凡可拷贝，`boost::lockfree` 的 static_assert 直接不过；只能退化成定长槽数组 |
| 单槽邮箱（mutex + swap） | 拷 172 KB + 30 ns 锁 | 2 × vector（按实际对子数） | 能用，但多一把锁 + 一个 condvar；且和本文件已有的 SPSC 队列风格不一致 |
| **PairInfoRecord 行队列（采用）** | 拷 172 KB + N 次 push | 1024 × 304 B ≈ 304 KB（内联成员） | 需要"批次边界"和"整批放得下"两个协议 |

关于"用队列会不会积压"：**不会**，而且就算积压也不致命 —— 10s 发布一次、写一次 1.5ms，
磁盘卡 30s 也只是卡完补写 3 批，最后落地的仍是最新那份。我早前写过"队列会落后几十秒、比不落盘更危险"，
那句话只在"每次写都比 10s 更慢"（磁盘永久性故障）时成立，已收回。

**② 主线程只拷 POD，不拷 `PairInfo`。**
`PairInfo` 归交易线程独占（`OnPosition` / `OnSpread` / `ProcessRisk` / 算法单回调都在改它），
别的线程读它会读到撕裂的 `double`，脏账直接进重启恢复。所以只能由交易线程自己拷成
`pt::PairInfoRecord`（`PairInfo.h`，33 个具名字段，`sizeof = 304 B`，无 NSDMI）交出去。

**实测（`tests/thread_cost`，500 行，调的是生产函数本体）：取数 16.3 µs = 整段 1493 µs 的 1.1%。**
（第一版是 23.3 µs —— 多了 `memset` 清零 + "临时对象 + push_back"两次整行搬运；
去掉 NSDMI、改成直接写进 `out[k]` 之后降到 16.3。剩下的大头是 500 次 `map.find` 的字符串哈希。）

**③ 批次边界用哨兵行（空 `pairKey`）。**
队列本身不知道"一批在哪结束"。推完 N 行再推一个 `PairInfoRecord{}`（聚合值初始化 ⇒ 全零
⇒ `pairKey[0] == 0`），写线程 pop 到哨兵才落盘。真实行的 `pairKey` 一定非空（来自配置），不会歧义。

**④ 批次边界用哨兵行（空 `pairKey`）。**
队列本身不知道"一批在哪结束"。推完 N 行再推一个 `PairInfoRecord{}`（聚合值初始化 ⇒ 全零
⇒ `pairKey[0] == 0`），T_signal pop 到哨兵才落盘。真实行的 `pairKey` 一定非空（来自配置），不会歧义。
🔴 **哨兵必须 `continue` 掉，不能跟着 `push_back` 进 `m_snapWrite`**：它 pairKey 全零，混进去
就是下一批开头多一行空 key 的垃圾。本批是"先写后 clear"，所以本批永远是对的 —— 错的是**下一批**，
症状延迟一轮才出现（D11 因此特意连推两批，见 ⑧）。

**⑤ 容量一开始就设够，不做降级路径。**
`capacity<1024>` ⇒ **1023 个对子**，500 对子时相当于 2 轮缓冲，304 KB 内联在 `PairTradingContext` 里。
所以 `Init` 里没有"容量不够就退回同步落盘"的分支（`m_snapAsyncOk` 已删除）。
⚠️ 代价是**超出容量时 `push` 静默失败**（返回值没人接）：行丢了、哨兵也可能丢，那一批就会
跨轮攒着等下一个哨兵。1023 个对子是硬边界，真到了就是配置错了。

**⑥ `pre_stop`：停掉唯一的后台线程，再同步写。**
```cpp
ptContext.StopSignalThread();     // T_signal 里也包含落盘 ⇒ join 完不可能还有 rename 在飞
... SaveSnapshot(csvStatePath);   // 权威版本（退出前最后一笔成交）
```
早期版本单开写盘线程时，这里必须"先 `StopStateWriter()` 再写"，否则写线程手里那份最多 10s 前的
快照可能在权威版本之后 `rename` 落地 —— `rename` 是原子的，事后完全分不出来，等于把新账盖成旧账。
**现在只有一条后台线程，这个顺序坑不存在了**，这也是合并线程最实在的收益。

**⑦ 原子替换语义必须保留。**
`写 .tmp → rename` 是"崩在写一半时旧文件完好"的唯一保证。搬到后台线程后照抄，不要图省事直接 `trunc`。

**⑧ 测试怎么验（不能轮询）。**
`OnTimer` 只"发布"，所以 D11 的 `stat()` 断言会变成竞态。先停掉 `T_signal`，再手工推一轮：
```cpp
fx.ctx.StopSignalThread();          // join，之后每一步都确定
fx.ctx.OnTimer(t0);                 // 发布：断言 m_snapQ.read_available() == N+1
int64_t lastStats = t0;             // = nowUs ⇒ 这一轮不触发"到点重算分位数"
fx.ctx.RunSignalOnce(t0, lastStats);// 第 3 步把队列排空并落盘
```
`RunSignalOnce` 就是生产 `SignalWork()` 循环调的那一轮，生产与测试同一段代码。D11 断言四件事：
`read_available()` 的发布行数、文件真的写出来了、**异步落盘与 `SaveSnapshot` 逐字节相同**
（两条路径共用 `WritePairInfoRecordFile`，列序/精度一漂就红）、**连推两批内容不变**（专抓 ④ 的哨兵污染）。

#### 实施时踩到的两个坑（都值得记）

1. **内联队列会把测试套件撑爆栈**（这条折腾了两轮，最终方案不是改队列）。
   1024 × 304 B ≈ 304 KB 内联在 `PairTradingContext` 里 —— 生产一个进程一个实例，无所谓；
   但测试里它是**栈对象**（`Fx fx;`），而 **clang 不做栈槽复用**：同一个函数里每个 `Fx` 各占一份
   独立栈槽。`TestG_Restart` 有 27 个 ⇒ 27 × ~320 KB ≈ 8.6 MB > 主线程 8 MB 栈 ⇒
   **函数序言里一碰栈就 SIGSEGV**。
   症状极具误导性：上一节（F14）最后一条 `PASS` 打完就崩，连下一节的 `=== G. 重启 ===` 都打不出来，
   看着像那条断言挂的；而且 stdout 重定向到文件时是块缓冲，日志会**截在半个行**上。
   定位办法：`script -q /dev/null ./suite`（伪终端 ⇒ 行缓冲）看最后一行到底停在哪。
   最终改的是**测试**：`Fx` 里改成 `unique_ptr<PairTradingContext> ctxStore` + `PairTradingContext& ctx`，
   `sizeof(Fx)` 从 320 KB 降到几十字节，105 处 `fx.ctx.xxx` 调用点一行没动。
   （先试过把队列本身换成 `unique_ptr`，那是把"测试的栈"问题变成"生产的堆"问题，不划算。）
2. **`ofs << int8_t` 打的是字符不是数字**：布尔列一度用 `int8_t` 存，直接流输出把 0/1 写成
   `\0`/`\x01`，`LoadSnapshot` 把 `"\x01"` 当"非 0"⇒ **布尔全变 true**（G2/G6 立刻红）。
   现在结构体里用 `bool`、写文件时统一 `static_cast<int>`。

### 4.2 B 类：五个每 tick 的重复构造

**B1 播报串（`AlgoContext.cpp:1288-1290`）**

```cpp
char algoOrderMsg[stra::MSG_LEN];
sprintf(algoOrderMsg, "algoOrder --- strategyName:%s ...", ...);
algoOrderStr += string(algoOrderMsg) + "\n";
```

这段每个算法单每 tick 都跑，而 `algoOrderStr` 只有 `algoOrderReportCount >= 60`（即 60s 一次）时才被用（`:1534-1540`）。改法：把拼接挪进 `if (algoOrderReportCount >= 60)` 里。**这是本节里性价比最高的一处**——一行缩进，省掉每个算法单每秒一次的 `sprintf` + 2 次 malloc。

**B2 `PairOrder` 整表拷贝（`AlgoContext.cpp:1295`）**

改成先取 id、再按 id 取引用：

```cpp
// 不能直接遍历 mPairOrder：PairOrderTrade 内部会 DeletePairOrderByPairOrder(自己)，
// 边遍历边删原表会让迭代器失效。原来是整表拷贝绕开的，代价是每 tick 深拷一遍。
std::vector<int64_t> ids;
ids.reserve(pairOrderMgr.GetAllPairOrders().size());
for (const auto& kv : pairOrderMgr.GetAllPairOrders()) ids.push_back(kv.first);

for (int64_t id : ids) {
    PairOrder* po = pairOrderMgr.SelectPairOrderByPairIdPtr(id);  // 需新增：找不到返回 nullptr
    if (!po) continue;                                            // 上一轮已经删掉了
    it->second->PairOrderTrade(*po);

```

注意 `SelectPairOrderByPairId`（`PairManager.h:116`）现在返回引用、找不到会怎样需要确认；要么加一个返回指针的版本，要么先查 size。**这一步改完要重跑 `tests/algo_exec`**，因为"边遍历边删"正是这个套件覆盖的路径。

**B3 `mSpreadReportCount` 两次全表扫（`AlgoContext.cpp:1250-1252`、`1589-1593`）**

这是个 `unordered_map<string,int>`，每 tick 加一、满了归零。它唯一的作用是"价差断流告警的节流"（`:1302` 的 `mSpreadReportCount[key] > 60`）。改法二选一：

- 换成 `unordered_map<const void*, int>` 或直接用 `pairInstrumentKey` 的 `uint64_t` 哈希当 key —— 省掉字符串哈希，但仍有两次全表扫；
- 更好：不存计数，存"上次告警时间"（`unordered_map<string,int64_t>`），判断改成 `eventTime - lastAlertTs > 60s`。**一次查找代替两次全表扫**，而且语义更准（原来的计数器是"tick 数"，tick 间隔一变节流窗口就变）。

**B4 `GetAllPairInfos()` 按值返回（实测 5.4 µs × 5 次/秒）—— ✅ 2026-10-28 已修，见本节末"实测"**

27 µs/秒，不值得单独改。

~~但如果 §4.1 改完顺手把 `OnTimer` 里那 4 个 `for (PairInfo* pi : pim.GetAllPairInfos())` 循环合并成一个，这 27 µs 就变 5.4 µs，而且**顺便修掉一个语义问题**：现在 `ProcessRisk` 和 `CheckAlgoOrderTimeout` 分别在两个循环里跑，中间没有一致性保证。~~

**上面这段"顺便修掉语义问题"是错的，2026-10-27 更正**：`OnTimer` 步骤 3/4/5 那三个循环
**没有**跨对子状态可"不一致" —— `ProcessRisk` 只读 `PairInfo` + 只读的 `RiskManager::m_cfg`，
`CheckAlgoOrderTimeout` / `CheckExposureAbnormal` / `ProcessModify` 也都是纯 `PairInfo` 局部读写
（见 `RiskManager.h:107-119` 只有一个 `m_cfg` 成员）。所以**合并是纯粹的性能等价变换，不修任何 bug**；
省下的是 3 次 `GetAllPairInfos()`（实测 0.42/2.04/5.50/11.04 µs @50/200/500/1000 对子）
⇒ 500 对子每 tick 从 16.5 µs 降到 5.5 µs，**占 1 Hz 的 OnTimer 的 0.0016%**。

结论：**保持三个独立循环**。理由不是性能，而是：① 三个循环各自对应祖先 `on_timer` 的一个阶段
（本工程所有注释都按"祖先 :行号"对齐，合并会打断这个映射）；② 万一将来真的引入跨对子状态
（例如在 `ProcessRisk` 里算一个全局敞口/撤单预算），**分开遍历才是安全的**——"所有对子先过完
阶段 3，再统一进阶段 4"能保证阶段 4 看到的是完整的全局结果，合并之后变成"谁排在前面谁先看到
半成品"。要降这 16.5 µs 的话，正确做法是给 `PairInfoManager` 加一个直接遍历 `m_pairInfoMap`
的 `ForEachPair(f)`（2.75 µs @500，比拷 vector 便宜一半，见 §"TotalPositionValue" 那段），
而不是合并循环。

#### 2026-10-28 实测：真正的开销不是 malloc，是 500 次 `find()`

`GetAllPairInfos()` 每次做的是"遍历 `m_pairKeys` → 每个 key 去 `m_pairInfoMap.find()`"，
那 500 次**字符串哈希 + 桶查找**才是钱；vector 那一次 malloc 只占 ~0.1 µs。所以"把 map 引用
暴露出去直接遍历"确实能省，但省的不是分配。五种写法实测（本机 macOS，中位数，同一条
`pairTotalVolume` 累加做防优化）：

| 对子数 | A 3×`GetAllPairInfos` | B 1×遍历 map | C 3×遍历 map | D 1×缓存指针表 | E 3×缓存指针表 |
|---|---|---|---|---|---|
| 50 | 1.17 | 0.04 | 0.08 | 0.04 | 0.08 |
| 200 | 6.38 | 1.00 | 2.96 | 0.12 | 0.38 |
| **500** | **17.17** | **2.58** | **7.75** | **0.29** | **0.88** |
| 1000 | 34.79 | 4.96 | 14.92 | 0.58 | 1.75 |

（µs，A 是现状）

D/E 快得离谱的原因：`unordered_map` 遍历是**链式指针追逐**，500 个节点散在 832 KB 里，
CPU 预取器完全使不上劲；而 `vector<PairInfo*>` 是 4 KB 连续数组，预取器能提前拉，
真正要碰的 `PairInfo` 也只有每个对象一两个 cache line（500×64 B = 32 KB，常驻 L1/L2）。

**推荐 D：在 `Init()` 末尾缓存一份 `std::vector<PairInfo*> m_pairPtrs`，`GetAllPairInfos()`
改成返回它的 `const&`。** 理由：`m_pairInfoMap` 全仓库只有 `Init():63` 一个插入点、从不 erase，
而 `unordered_map` 的**元素地址跨 rehash 是稳定的** ⇒ 这张表建一次就永久有效。
它同时拿下三个好处：17.17 → 0.29 µs、零分配、顺序仍是配置顺序（`m_pairKeys` 序，日志可对）。

**不要**为此把 `unordered_map&` 暴露出去（`GetPairInfoMap()`）：
① 非 const 引用 = 任何调用方都能 `clear()`/`insert` 别人的对子，而且**遍历期间插入会让迭代器失效**
（`GetAllPairInfos()` 返回拷贝，天然免疫）；② 遍历顺序变成桶序 —— 实测 10 个对子插入 000~009，
map 遍历出来是 `009 007 005 003 006 002 008 001 004 000`。它是确定的（同一份 libstdc++ + 同一插入序
就稳定），但**不是配置序**，和快照的文件行序（`m_pairKeys` 序）对不上；换 libstdc++ 版本或增删对子就会变，
排查时对日志不友好。
③ 顺带说明：`GetPairInfoMap()` 这种非静态成员函数必须用对象调（`pim.GetPairInfoMap()`），
写 `PairInfoManager::GetPairInfoMap()` 编不过（`call to non-static member function without an object argument`）。

#### `PairInfoManager` 里所有遍历对子的地方（2026-10-28 清点）

**走 `m_pairKeys` + `find`（配置序，每次 N 次哈希查找，~5.7 µs @500）**

| 行 | 函数 | 为什么要配置序 |
|---|---|---|
| `:256` | `CollectSnapshotRows` | **必须**：顺序 = 快照文件行序（`.h:45`） |
| `:405` | `LoadSnapshot` | 按行序回读 |
| `:554` | `LoadSpreadStats` | 同上 |
| `:626` | `GetAllPairInfos` | 调用方都在 OnTimer/信号路径上，其实不关心顺序 |
| `:853` | `RecalcVolumeParams` | 不关心顺序 |

**直接遍历 `m_pairInfoMap`（桶序，~2.6 µs @500，零分配）**

| 行 | 函数 | 备注 |
|---|---|---|
| `:643` | `TotalPositionValue` | 全局持仓闸门，1 次/秒，只读 |
| `:786` | `UpdateOnBalance` | ⚠️ 每次余额推送 × 500 次 `strstr` —— 这是**真正贵**的那处，但已知 key 匹配不上（死代码），按约定**要删不要修**，别顺手优化 |

#### 最终建议：**继续用 vector，但返回缓存表的 `const&`；不要改成返回 map**

决定因素不是 OnTimer 那 17 µs/秒（那是噪声），而是 **`GetAllPairInfos()` 有 10 个调用点**：

| 位置 | 函数 | 频率 |
|---|---|---|
| `PairTradingContext.cpp:114` | `Init`（恢复统计后重算 orderParams） | 启动 1 次 |
| `:272` | `HandleOrphanAlgoOrders` | 启动 1 次 |
| `:1240` | `OnTimer` 0.6 配置落地 | 仅配置变更 |
| `:1261` | `OnTimer` 0.7 `stopAllAlgo` 撤单 | 该开关打开时 1 Hz |
| `:1278` | `OnTimer` 1 每分钟重算量 | 每 `volumeRecalcIntervalSec` |
| `:1308 / :1318 / :1327` | `OnTimer` 3 / 4 / 5 | 1 Hz |
| `:1399 / :1425` | `TryReconcile` | 启动期间 1 Hz |
| `PairTradingStrategy.cpp:642` | `ScanFinishedAlgoOrders`（`SCAN_INTERVAL_US=200ms` 被 1 Hz tick 节流） | 1 Hz |

**10 处全是 `for (PairInfo* pi : pim.GetAllPairInfos())`。** 返回 `const std::vector<PairInfo*>&`
⇒ 10 处**一行都不用改**；改成返回 map ⇒ 10 处全要重写成 `for (auto& kv : ...) { auto& pi = kv.second; ... }`，
`pi->x` 全变 `pi.x`。其中 6 处是启动/一次性路径，改它们零收益 —— 纯 churn。

所以：

| 方案 | 500 对子/次 | 调用点改动 | 顺序 | 结论 |
|---|---|---|---|---|
| 现状（返回拷贝） | 5.75 µs | 0 | 配置序 | 能跑，浪费 |
| **返回缓存 `vector<PairInfo*>` 的 `const&`** | **0.29 µs** | **0** | **配置序** | ✅ 选这个 |
| 返回 `const unordered_map&` | 2.58 µs | 10 处重写 | 桶序 | ❌ 更慢且要改 10 处 |

具体改动（三处，**2026-10-28 已实施**）：

1. `PairInfoManager.h`：加私有成员 `std::vector<PairInfo*> m_pairPtrs;`，
   `GetAllPairInfos()` 签名改成 `const std::vector<PairInfo*>& GetAllPairInfos();`
   （**不是** const 方法 —— 缓存失配时它要重建，见第 2 条；这样也不用 `const_cast` 或 `mutable`）。
2. `PairInfoManager.cpp`：`Init()` 末尾（`:69` 那条 LOG 之前）调 `RebuildPairPtrs()` 按 `m_pairKeys`
   序建表；`GetAllPairInfos()` 返回 `m_pairPtrs`，并在 `size()` 与 `m_pairInfoMap.size()` 不等时重建。
   `unordered_map` 的**元素地址跨 rehash 稳定**，所以这张表建一次就永久有效。
3. 把 `GetPairInfoMap()` 删掉（没人用，而且正是这次的诱因），`OnTimer` 里那段合并循环也一并删掉，
   恢复步骤 3/4/5 三个循环。

**实测（改完）**：`3 × GetAllPairInfos()` @500 对子 = **0.88 µs**（改前 17.17 µs，19.5×），
单次 0.29 µs；缓存表 size 与 map size 一致。

**"两份缓存"的顾虑**：`vector<PairInfo*>` 只存指针，500 对子 = **4 KB**，map 本体
500 × 1664 B ≈ 850 KB，指针表占 0.5%，`PairInfo` 仍然只有一份，不是拷贝。
唯一的真风险是**成员集合多一个真源**（`Init` 之外加对子 ⇒ 新对子静默漏掉全部处理）。
用一行消掉：`GetAllPairInfos()` 里 `if (m_pairPtrs.size() != m_pairInfoMap.size()) RebuildPairPtrs();`
—— 一次 `size()` 比较（~0 成本），失配就自愈，不会静默漏。

如果连这 4 KB 和那个 `size()` 都不想加，那正确答案是**什么都不做**：23 µs/秒是 OnTimer 的
0.0023%，不值得为它动 10 个调用点。

### 4.3 `commands.json`（承接上一轮的结论）

**不进 `OnTimer`，进 `signal_work()`。** `PairTradingContext.cpp` 的 `SignalWork()` 已经有现成的循环（`std::this_thread::sleep_for(std::chrono::seconds(1))`，每轮调一次 `RunSignalOnce`），把 `stat` + 按 `mtime/size` 变化才解析的逻辑放那儿，解析结果推进 SPSC 队列；`OnTimer` 只做有上界的排空：

```cpp
CommandMsg cm;
int n = 0;
while (n++ < 8 && m_cmdQ.pop(cm)) { pim.ApplyCommand(cm.pairKey, cm.cmd, cm.params); }
```

`n++ < 8` 是必须的：没有上界，一条坏命令（比如把所有对子都 STOP）就会让这个 `while` 在这一轮里跑满 N 次 `ApplyCommand`，把"耗时的操作不该在这条线程"这个前提自己破坏掉。

### 4.4 D 类：跟着一起改

| # | 改法 | 为什么现在改 |
|---|---|---|
| D1 | `if (!pdata) continue;`（或在 `GetSpread` 里返回一个静态空对象） | 一个空指针就能让整条执行线程挂掉，而它旁边就是报单逻辑 |
| D2 | 检查 `push()` 返回值；`Full` 时 `LOG_ERROR` + 让 `CreateOrder` 返回 `false` | 现在队列满 = 静默丢单 + 策略以为单已发出 + 等一个永不来的回报。`CreateOrder` 返回 `false` 的路径已经存在（`BaseAlgoOrder.cpp:887-890`），接上就行 |
| D3 | 四处 `LOG_DEBUG("{}", tcmd.getString())` 改成 `LOG_DEBUG("{}", int(tcmd.cmdTypeEnum))` 之类的定长输出，或者直接删 | 每张单 2 次 `fmt::format` + 2 次 malloc，在**报单路径**上。这是账本漏掉的 P1 |

## 5. 顺带发现：两个 SPSC 队列的容量是硬上限，超了静默失效

这条不在"耗时"的范围内，但它是扫这条线程时撞出来的，而且比上面所有项都严重，所以单独列。

`PairTradingContext.h:38-41`：

```cpp
// 容量：样本队列按"每 5s 每对子一条"算，256 槽 ≈ 20 对子时 64s 的积压余量；
// 统计队列每 60s 才一条，32 槽足够。满了丢**最新**那条（boost 语义），
// 正常永远触发不到 —— 两者都只用于观测。
using SpreadSampleQueue = ... capacity<256>;
using SpreadStatsQueue  = ... capacity<32>;
```

**注释里"统计队列每 60s 才一条"是错的。** `signal_work()` 的实现是：

```cpp
for (auto& kv : m_spreadWindows) {          // 遍历**所有**对子
    ...
    m_statsQ.push(out);                     // 每个对子推一条，返回值没人看
}
```

也就是**每 60s 一轮，推 N 条**，不是一条。

### 后果

| 队列 | 容量 | 每轮实际推送量 | 硬上限 | 超了会怎样 |
|---|---|---|---|---|
| `m_statsQ` | **32** | N（每个对子 1 条） | **32 个对子** | 第 33 个之后的统计**永远**推不出去 |
| `m_sampleQ` | 256 | N × (2s + 本轮 Build 耗时) / `spreadSampleIntervalMs`(5s) ≈ 0.4N | **约 500–640 个对子**（`Build` 一轮 885 µs/对子，N 大时把窗口进一步压缩） | 超出部分样本被丢，24h 窗口变稀，分位数失真 |

`m_statsQ` 那条是**确定性**的：`signal_work` 在几微秒内把 N 条全部 push 完，而 `OnTimer` 1 秒才排空一次，所以每轮都只有前 32 个（哈希序，不是配置序）能进去。

而统计推不出去的后果，顺着代码走一遍是：

1. `PairInfo::largeStats` 永远是默认值（`valid=false`，分位数 NaN）；
2. `SignalGenerator::RecalcOrderParams` 在 `if (!ls.IsValid()) return;`（`SignalGenerator.cpp:69`）早退 —— **四个开仓开关 `ttOLSwitch/ttOSSwitch/mtOLSwitch/mtOSSwitch` 停在默认的 `false`**（`PairInfo.h:98`）；
3. `CheckSignalForSatisfy` 于是永远不产生开仓信号。

**净效果：超过 32 个对子时，多出来的对子静默地永不开仓。** 没有报错、没有告警，日志里一个字都不留，看起来一切正常。而且**哪 32 个能活下来取决于 `unordered_map` 的哈希序**，不是你在配置里写的前 32 个。

### 改法

1. **`m_statsQ` 改成按"对子"下发，不按"轮"下发**：`signal_work` 里每轮只推 `spreadStatsPerRound`（比如 8）条，用一个游标轮转，`OnTimer` 排空后再回推。这样队列容量与对子数解耦，`OnTimer` 每轮的排空量也有上界。
2. **或者**：把统计直接写进 `PairInfo`（`largeStats` 是普通字段），用 `std::atomic<uint64_t> seq` 做"发布-读"配对，根本不走队列。代价是要处理"读到一半被改"的撕裂 —— 但 `SpreadStats` 只有 11 个 double，用双缓冲 + 序号即可。
3. **不管选哪个，`push()` 的返回值必须检查**。现在两处 push 都丢返回值，而"满了丢最新那条"这句注释本身就承认了会丢 —— 丢的是**统计**，不是观测数据。这一条和 §4.4 的 D2 是同一个毛病。
4. `PairTradingContext.h:38-41` 那段注释必须改。它现在描述的是"设计意图"，与实现相反，下一个读代码的人会信它。

**这一项的优先级高于 §7 表里的所有项**——因为它是"改完 IO 也照样只有 32 个对子在跑"。

|---|---|---|---|
| 0 | §5 `m_statsQ` 容量 32 + `push()` 返回值 | 决定"能不能跑超过 32 个对子"；不做这个，下面都只是给 32 个对子优化 | 中（改的是 T_signal ↔ T_market 的协议） |
