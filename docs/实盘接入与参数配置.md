# 实盘接入与参数配置（DOGE-USDT 配对）

> 目标：把 `BINANCE.USDT_SWAP.DOGE-USDT|GATEIO.USDT_SWAP.DOGE-USDT` 接到真实行情 + 真实交易上跑通
> **开仓 → 超时撤单 → 风控平仓 → 正常平仓** 整条链。
>
> 配套工具：`tests/param_calc/`（链接**真实的** `SignalGenerator.cpp` 算阈值，不要靠手推）。

---

## 0. 结论速览（先看这段）

**「价差 0.0002」这个数必须先确认口径，两种理解的结论完全相反：**

| 你看的是 | 换算成策略用的相对价差 | 能不能开仓（当前配置） |
|---|---|---|
| dbp 里的 `spreadAskAsk` 字段本身 = 0.0002 | **2.0 bp** | **❌ 开不了**。需要 ±19.05 bp |
| 两腿价格之差 = 0.0002 USDT（DOGE≈0.0937） | **21.3 bp** | **⚠️ 勉强够（1.12×）**，只在 MT、且价差真走到才行 |

原因是**执行成本比价差还大**（值取自 `etc/config.json` 的 `op.feeSlippage` 段，2026-10-26）：

```
F_mt（主动腿挂单 + 被动腿吃单 + 滑点）= 0.0002 + 0.0005 + 0.0000 = 0.0007 = 7.0 bp
F_tt（两腿都吃单 + 滑点）              = 0.0005 + 0.0005 + 0.0000 = 0.0010 = 10.0 bp
```

（`SignalGenerator.h` 里 `FeeSlippageConfig` 的费率默认值是 **0**，只是兜底；拿默认构造去算会把
"净利不够"算成"够"，结论直接反掉 —— 见 `tests/param_calc` 里的 `ProductionConfig()`。）

判据分两层，**别混**：开关看 `StartSpread` 是否穿过 0；**成交**看实时价差能不能走到那个价位。
叠上地板 `minSpreadTarget = 0.0012` 之后，真正的约束是"裸价差要走到多深"：

```
开多(MT) 需 裸价差 < −19.05 bp = −(地板 12.05 + F_mt 7)              开空(MT) 对称
开多(TT) 需 裸价差 < −25.05 bp = −(地板 12.05 + ttAdd 3 + F_tt 10)   开空(TT) 对称
```

即 8% 分位至少要 −19.05 bp（MT）/ −25.05 bp（TT），开仓才**有机会**成交。

DOGE ≈ 0.0937 时，**19.05 bp ≈ 0.000178 USDT**。所以：
- 绝对价差 0.0002 USDT → 21.3 bp → **只有门槛的 1.12 倍**，勉强够，且要价差真的冲到这里；
- 相对价差 0.0002（= 2 bp）→ **只有门槛的 10%，开不了**。

**怎么确认**：`PairTradingStrategy::on_dbpdata`（`PairTradingStrategy.cpp:126`）会把
**四条价格**打到 stdout（`activeAsk activeBid passiveAsk passiveBid`），不是价差。
如果你是从这行输出里自己减出来的，那就是绝对价差 → **21.3 bp，能开**。
如果你是从 `dbp` 共享内存 / 别处的 `spreadAskAsk` 字段读的，那就是相对价差 → 2 bp。

用计算器立刻验证：

```bash
cd utrade_hft/tests/param_calc
./run.sh band 0 0.00213     # 相对 ±21.3bp -> 4 个开关全开（第 4 节"可达性"看能不能真成交）
./run.sh band 0.0002 0.0002 # 相对 0.0002 上下 -> 开关被地板打开，但门槛在 -19.05bp，碰不到
```

## 1. 价差口径（一切数字的前提）

### 1.1 四个轴的定义

价差**不是本工程算的**，是 `dbp` 进程算好写进共享内存的。公式在
`dbp/dbprocess/dbsnap.h:303-306`：

```cpp
spreadBidAsk = calcspread(activeBidPrice[0], passiveAskPrice[0]);
spreadBidBid = calcspread(activeBidPrice[0], passiveBidPrice[0]);
spreadAskBid = calcspread(activeAskPrice[0], passiveBidPrice[0]);
spreadAskAsk = calcspread(activeAskPrice[0], passiveAskPrice[0]);
```

而 `calcspread`（`dbsnap.h:230-238`）按 `spreadCalcType` 分支：

```cpp
SPCT_PRICEDIV1 = 0  ->  (d1 - d2) / d1
SPCT_PRICEDIV2 = 1  ->  (d2 - d1) / d1
SPCT_PRICESUB1 = 2  ->  d1 - d2
SPCT_PRICESUB2 = 3  ->  d2 - d1
```

**`dbp/etc/dbprocess.xml` 里 `spreadcalctype = 1`** → `SPCT_PRICEDIV2` → `(d2 − d1)/d1`。
（注意 `dbp/etc/dbprocess.json` 写的是 0，但**代码读的是 `dbprocess.xml`** ——
`dbpinitialer.cpp:28` 硬编码 `auto filename = "dbprocess.xml"`。两份配置不一致，以 xml 为准。）

`active` / `passive` 来自 `pairlist.xml` 里 `<name>` 按 `|` 切分的左右两半
（`dbpserver.cpp:306-307`：`result[0]` → active，`result[1]` → passive）。
`utrade_hft/etc/config.json` 的 `pairKeys` 是 `BINANCE...|GATEIO...`，所以：

```
active  = BINANCE.USDT_SWAP.DOGE-USDT
passive = GATEIO.USDT_SWAP.DOGE-USDT

spreadBidAsk = (GATEIO_ask − BINANCE_bid) / BINANCE_bid
spreadBidBid = (GATEIO_bid − BINANCE_bid) / BINANCE_bid
spreadAskBid = (GATEIO_bid − BINANCE_ask) / BINANCE_ask
spreadAskAsk = (GATEIO_ask − BINANCE_ask) / BINANCE_ask
```

**四个都是无量纲的相对价差，正 = GATEIO 比 BINANCE 贵。**

### 1.2 方向怎么读

`OPEN_LONG` 的腿约定是**主动腿卖、被动腿买**（`AlgoPairOrder.cpp:408-430`：
`tradingTypeOffset == OPEN_LONG` 分支里 `activeDirection = DT_SHORT; passiveDirection = DT_LONG;`），
也就是"卖 BINANCE + 买 GATEIO"。
要赚钱就得 **GATEIO 便宜**，即 `spread` 为**负**。

这和开关判据一致：`canOpenLong = mtOLStartSpread < 0`，而
`mtOLStartSpread = askAskDQ × 0.8 + F_mt`，只有 `askAskDQ` 足够负才成立。

所以：
- `spread` 很负 → 开多（卖 BINANCE / 买 GATEIO）
- `spread` 很正 → 开空（买 BINANCE / 卖 GATEIO）

## 2. 参数是怎么算出来的

`SignalGenerator::RecalcOrderParams`（`SignalGenerator.cpp:24-146`）在每个统计刷新周期
（默认 60s）跑一次，从**分位数**推导全部阈值：

```
CalcExpectSpread(qb, isTT, direction):
    execCost = CalcExecCost(isTT)
    buffer   = isTT ? ttAddPercent : 0
    startSpread = qb × spreadAdjPct − direction × (execCost − buffer)
    endSpread   = startSpread + direction × 5e-6
```

代入四个开仓方向（`direction`：开多 = −1，开空 = +1）：

| 方向 | 分位数来源 | StartSpread | 开关判据 |
|---|---|---|---|
| `ttOL` 开多 | `bidAskDQ` | `bidAskDQ × 0.8 + 0.0007` | `< −minSpreadTarget` |
| `mtOL` 开多 | `askAskDQ` | `askAskDQ × 0.8 + 0.0007` | `< −minSpreadTarget` |
| `ttOS` 开空 | `askBidUQ` | `askBidUQ × 0.8 − 0.0007` | `> +minSpreadTarget` |
| `mtOS` 开空 | `bidBidUQ` | `bidBidUQ × 0.8 − 0.0007` | `> +minSpreadTarget` |

（TT 的 0.0007 = `F_tt − ttAddPercent` = 0.0010 − 0.0003；MT 的 0.0007 = `F_mt`。
两者数值相同纯属巧合：`activeTakerFeeRate − activeMakerFeeRate = ttAddPercent = 3bp`。）

另外两个前置门槛：

- **`minSpreadSpan = 0`（当前是关的）**：`spreadSpan = bidBidUQ − askAskDQ` 低于它，
  `RecalcOrderParams` **直接关掉全部四个开仓开关并 return**（`SignalGenerator.cpp:64-69`）。
  祖先线上用的是 `0.0002`。**设成正数要小心**：CEX-CEX 的 8/92 分位带宽只有 1~11bp 时，
  2bp 的门槛会让这个对子**永久不开仓，日志里只有一句 `swch is false!`**，看不出是这条挡的。
  它和地板**不是一回事，别指望地板把它盖住**：`minSpreadSpan` 是"整对子不参与"的开关
  （带宽不够就四个开仓开关全关，地板再深也没用），地板只是把阈值钉住。两者独立。
- **`openMaxFundingRate = 0.002`**：任一腿资金费率绝对值超过它，四个开仓开关也全关。

而**实际触发**（`CheckSignal`，`SignalGenerator.cpp:179-217`）时成本会精确抵消：

```
mtOL: spreadAskAsk + F_mt < mtOLStartSpread  ⟺  spreadAskAsk < askAskDQ × 0.8
mtOS: spreadBidBid − F_mt > mtOSStartSpread  ⟺  spreadBidBid > bidBidUQ × 0.8
```

即"当前价差走到自己分位数的 0.8 倍之外"就报单。**成本门槛只在开关那里起作用**
（例外是下面那道地板：它夹的是含 F 的 `StartSpread`）。

⚠️ 上面这个化简**只在地板没生效时成立**。地板一夹，`StartSpread` 就不再是 `q × 0.8 + F`，
触发点变成 `−19.05bp`（MT）/ `−25.05bp`（TT），与分位数彻底脱钩 —— 分位数只决定"夹不夹"。

### 开仓要过几道闸门（7 道，全过才报单）

参数经常被误解成"一个参数 = 一个开关"，实际是一条链。按代码顺序：

| # | 闸门 | 位置 | 由谁决定 | 不通过的后果 |
|---|---|---|---|---|
| ⓪ | `spreadSpan < minSpreadSpan` | `RecalcOrderParams` 开头 | 配置 | **直接 return**，4 个开仓开关全关 |
| ① | 分位数 → `StartSpread` | `CalcExpectSpread` | `quantileUp/Dn` + `spreadAdjPct` | 阈值位置不对 |
| ② | 地板夹逼 `∓(minSpreadTarget+5e-6)` | `RecalcOrderParams` 末尾 | `minSpreadTarget > 0` | 阈值太浅，被抬到地板 |
| ③ | `canOpen`（**严格**不等号）+ `closeFlag`/`autoFlag` | `RecalcOrderParams:190-196` | 配置 + 对子状态 | 4 个开关全关 |
| ④ | 流动性 / 保证金状态 > 0 | `:204-207` | 运行期 | 4 个开关全关 |
| ⑤ | `\|资金费率\| > openMaxFundingRate` | `:210-215` | 运行期 + 配置 | 4 个开关全关 |
| ⑥ | 预期往返净利 `≥ minProfitTarget` | `CheckSignalForSatisfy` | 配置 + **实时价差** | 这一 tick 不报单 |
| ⑦ | 只平不开 `m_globalPosExceeded`/`m_closeOnly` | `ApplyNoOpenGate`（**必须最后**） | 运行期/热改 | 4 个开关全关 |

两个容易踩的点：

1. **③ 用的是严格不等号**，所以 ② 的夹逼值必须比门槛再多 `5e-6`。夹到正好 `−minSpreadTarget` 时
   `−x < −x` 为假 ⇒ 4 个开关全关 ⇒ **一单都不报**。这个 `5e-6` 不是"缓冲带"，去掉就废。
2. **⑦ 必须最后压**。①②③④⑤ 每段都在重写这 4 个开关，把全局闸门放在前面会被它们重新打开。

**"闸门全开"不等于"会成交"**：①②③④⑤⑦ 只回答"允许报单"，⑥ 回答"这一笔能不能赚"，
而价差能不能走到那个价位是第三件事。地板把入场钉在 −19.05bp 时，8% 分位可能只到 −12.5bp
（1.52×），结果就是**开关全是 true、日志里却永远没有信号**。`tests/param_calc` 的第 4 节会把
这个倍数打出来（`可达性`）。

**⚠️ 常见误解：不存在"先无条件建算法单、再由执行端判断要不要开"这回事。**
- 算法单**只在当前价差越过阈值的那一 tick** 创建：`ProcessPairSignal:376` 是
  `if (!sig.hasSignal) return;`，而 `hasSignal` 由 `CheckSignalForSatisfy:294-321` 的 8 个判据给出，
  **每一个都含实时价差比较**（`rt.spreadBidAsk + F_tt < op.ttOLStartSpread` 这类）。
- `ttOLSwitch` / `ttOSSwitch` / `mtOLSwitch` / `mtOSSwitch` **不是"一直开着"**，它们是
  `canOpenLong/Short && autoFlag`（`:193-196`），还会被 ④⑤⑦ 压掉。
  **恒为 true 的是平仓开关** `ttCLSwitch/ttCSSwitch/mtCLSwitch/mtCSSwitch`（`:198-200`），
  因为平仓不该被权限位挡（挡它的是 `CanClose`）。
- 建单**之后**才轮到执行端实时判断：`AlgoContext::OnSpread` 的 `openOrderFlag`
  （行情/深度/成交延迟）、`TargetSpreadStop` 的 `mtSpreadFlag`、`mtSlipageFlag`
  决定这一 tick 要不要报子单；`ProcessModify` 每 `modifyTimespanSec`（60s）把最新参数推给在跑的单。
- 这两层是**串联**的，不能拿掉第一层：`satisfyTime` 靠 `HasOpenSignal(sig)` 续命
  （`PairTradingContext.cpp:523`），若建单不判价差，价差回撤后 `satisfyTime` 就停表，
  150s 后被 `CheckAlgoOrderTimeout` 撤掉 —— "无条件建单"必然要求同时改超时语义。

### 开仓阈值的"绝对地板"（`minSpreadTarget`，2026-10-26 起）

分位数只回答"历史上有多少价差"，回答不了"多少价差才够覆盖两边的手续费"。所以
`RecalcOrderParams` 末尾还有一道**夹逼**（祖先 `cc_pricespread_gb_ltp.py:781-782`）：

```
minSpreadTarget > 0 时：
    mtOLStartSpread = min(mtOLStartSpread, −(minSpreadTarget + 5e-6))    # 开多
    mtOSStartSpread = max(mtOSStartSpread, +(minSpreadTarget + 5e-6))    # 开空
    ttOL/ttOS 同构，但地板再深一个 ttAddPercent（TT 两腿都是 taker）
```

四条容易搞错的：

1. **那个 `5e-6` 不是缓冲带，去掉就一单都不报。** `canOpenLong = (mtOLStartSpread < −minSpreadTarget)`
   是**严格小于**；夹到正好 `−minSpreadTarget` 时 `−x < −x` 为假 ⇒ `canOpenLong/Short` 全 false
   ⇒ 4 个开仓开关全关。所以夹逼值必须比门槛再深 5e-6 才活。
2. **它是夹逼，不是开关。** 上面的 `canOpen*` 只把 4 个开仓开关压成 false（"不参与"）——
   分位带宽只有 6bp 时，市场真冲到 20bp 也不会有单；夹逼是"把阈值钉在地板上等着"
   （当前地板 `0.0012` ⇒ 12.05bp）。
   分位数比地板更深时**不动它**（只抬高、不压低）。
3. **量纲是"净额"，但只净了入场那一笔。** 夹的是 `StartSpread`，而它含 F —— 所以这个值
   **已经是扣掉入场成本之后**的数字，不要再自己加一次手续费。（分位数那条线为什么不用管成本：
   见 §3.1.1，`F` 在信号闸门/算法单阶梯/偏离守卫三处都精确抵消了。**地板是唯一抵消不掉的地方**，
   所以"要不要考虑手续费"这个问题只在地板这里成立。）三条恒等式（假设平到 0）：

   ```
   毛价差门槛 = minSpreadTarget + 5e-6 + F
   净利       = minSpreadTarget + 5e-6 − F
   该填的值   = 想净赚的 + F − 5e-6
   ```

   | 想净赚（平到 0） | F = 3bp（有返佣） | F = 8bp（零售） |
   |---|---|---|
   | 10bp | `0.001295` | `0.001795` |
   | 20bp | `0.002295` | **`0.002795`** |
   | 30bp | `0.003295` | `0.003795` |

   对比一下：若配 `0.002` + 零售费率（F_mt = 8bp）⇒ 净利只有 `20.05 − 8 = 12.05bp`；
   现在配的 `0.0012` + 2/5bp（F_mt = 7bp）⇒ `12.05 − 7 = 5.05bp`。
   **改费率就必须重算这个值**，否则门槛会跟着 F 一起漂（F=−2bp 时是 18.05bp，F=+8bp 时是 28.05bp）。

   **为什么是 `+ F` 而不是 `+ 2F`？**（一开一平明明要付两次。）因为地板的 `StartSpread` 里
   **已经含了一个 F**，"毛价差门槛"这个数本身就把开仓那一笔算进去了。摊开看（maker 2bp /
   taker 5bp / 想净赚 5bp ⇒ `F_mt = 7bp`、`minSpreadTarget = 0.0012`）：

   ```
   毛价差门槛 19.05bp = 12 (mst) + 0.05 (5e-6) + 7 (F_mt)   ← 这 7bp 就是开仓成本
   − 开仓 7bp  → 12.05bp
   − 平仓 7bp  →  5.05bp                                    ← 一开一平都扣掉了
   ```

   写成 `minSpreadTarget = 想净赚 + 2F` 会**多要一个 F**（本例多要 7bp，实际净赚变成 12bp）。

   | maker 2bp / taker 5bp，想净赚 5bp | 值 |
   |---|---|
   | `F_mt = activeMaker + passiveTaker` | 7bp |
   | `minSpreadTarget = 5 + 7 − 0.05` | **`0.001195`**（取整 **`0.0012`**） |
   | MT 毛门槛 `= 12 + 0.05 + 7` | **19.05bp** |
   | MT 往返成本 `2 × 7` | 14bp |
   | MT 净利 `= 19.05 − 14` | **5.05bp** |
   | TT 毛门槛 `= 12 + 0.05 + 3(ttAdd) + 10(F_tt)` | 25.05bp |
   | TT 净利 `= 25.05 − 2×10` | **5.05bp** |

   TT 和 MT 净利相同不是巧合：`ttAddPercent` 默认 `0.0003` 正好等于 `taker − maker`（5 − 2bp），
   它同时补掉了 TT 多出来的 3bp 成本和 3bp 门槛。**改费率要同步改 `ttAddPercent`**，否则两条线
   的净利会分叉，差额 = `ttAddPercent − (F_tt − F_mt)`。

   加滑点就并进 F：`F_mt` 按 1bp 滑点算成 8bp ⇒ `minSpreadTarget = 5 + 8 − 0.05 = 0.001295`（取整 `0.0013`）。

   ⚠️ **平仓那一侧不受 `minSpreadTarget` 控制。** 上面的算法是"价差回到 0 就平"的保守情形；
   真实平仓由分位数决定（`mtCLStartSpread = q_up × 0.8 − F_mt + profitPct`，`F` 又抵消一次）
   ⇒ **裸价差回到 `q_up × 0.8 + profitPct` 就平**。完整式：

   ```
   净利 = minSpreadTarget + 5e-6 − F_mt + (q_up × 0.8 + profitPct)
          └──── 平到 0 的净利 ────┘   └─ 平在分位线上多赚的 ─┘
   ```

   以 `0.0012`（`F_mt = 7bp`、`profitPct = 1bp`）为例：

   | `q_up`（0.92 分位） | 平仓裸价差 | 净利 |
   |---|---|---|
   | −2bp | −0.6bp | 4.45bp |
   | 0 | +1.0bp | 6.05bp |
   | +3bp | +3.4bp | 8.45bp |
   | +6bp | +5.8bp | 10.85bp |

   所以 **5bp 是"价差完全回归到 0"的下限**，正常会更多；只有 `q_up × 0.8 + profitPct < 0`
   （上分位为负）时才跌破 5bp。

   两个附注：
   - **开仓和平仓不在同一根轴上**：开仓看 `spreadAskAsk`、平仓看 `spreadBidBid`，两条腿的
     买卖价差会让实际捕获量与上表差一个盘口宽度。
   - 想抬高平仓线，该动的是 `quantileUp` 或 `profitPct`。`profitPct` **不在 `config.json` 里**
     （`PairInfo.h:323` 默认 `0.0001`），但它**可以在运行期按对子改**：发 `PairCmd_MODIFY`、
     `params["profit"] = 值`（`PairInfoManager.cpp:1007`），改完进快照、重启也保留。
     `openProfitPct` 是死参数，调它没用。
4. **`<= 0` 等于关掉这一层**，不是"更松的软门槛"。`-0.001` 只等于"允许在 +10bp 上开多"。

`EndSpread` 跟着 `StartSpread` 一起夹：只夹 Start 会让 `End` 比 `Start` 更浅、阶梯反向
（`AlgoPairOrder` 里 `(End−Start)` 还可能变成 0）。用例见 `tests/market_to_algo` 的 D17。

#### ⚠️ 地板保证的是"**如果成交**"，不保证"**会成交**"

上面所有净利都建立在"价差真的走到地板"这个前提上。走不走得到，**只由分位带宽 `B = q_up − q_dn` 决定**，
跟 `minSpreadTarget` 填多少无关 —— 地板不创造 edge，它只是把"不赚钱的交易"变成"不发生的交易"。

设对称带宽 `q_dn = −B/2`、`q_up = +B/2`、`F_mt = 7bp`、`profitPct = 1bp`、`minSpreadTarget = 0.0012`：

| 带宽 `B` | 8% 分位 `q_dn` | 无地板净利<br>`0.8B − 13` | 地板入场 | 地板净利<br>`0.4B + 6.05` | 地板入场 / 8%分位 |
|---|---|---|---|---|---|
| 10bp | −5.0bp | **−5.0bp** | −19.1bp | 10.1bp | **3.81×**（几乎不可能） |
| 15bp | −7.5bp | −1.0bp | −19.1bp | 12.1bp | 2.54× |
| 20bp | −10.0bp | +3.0bp | −19.1bp | 14.1bp | 1.91× |
| 25bp | −12.5bp | +7.0bp | −19.1bp | 16.0bp | 1.52× |
| 30bp | −15.0bp | +11.0bp | −19.1bp | 18.1bp | 1.27× |
| 40bp | −20.0bp | +19.0bp | −19.1bp | 22.1bp | 0.95×（分位内，能成交） |
| 50bp | −25.0bp | +27.0bp | −20.0bp | 27.0bp | 地板不生效（`B ≥ 47.6bp`） |

三条硬结论：

1. **`B ≥ 16.25bp` 才不亏**（`0.8B + profitPct − 2F ≥ 0`）；**`B ≥ 22.5bp` 才净赚 5bp**。
   这条与地板无关 —— 地板关掉时净利就是 `0.8B − 13`。
2. **`B < 47.6bp` 时地板都生效**，把入场钉死在 −19.05bp。但 `B = 20bp` 时那是 8% 分位的
   **1.91 倍深**，`B = 10bp` 时是 **3.81 倍** —— 表里"地板净利 14.1bp / 10.1bp"是**算得出来、碰不到**。
3. 所以 `minSpreadTarget` 不是自由参数：**它必须与 `B` 匹配**。`B` 只有十几 bp 的对子，
   填 `0.0012` 等于"永不开仓"；想开就得把地板降到分位线附近（甚至 `<= 0`），
   而那时净利只剩 `0.8B − 13`，`B < 16.25bp` 依然是亏的。

> **一句话**：地板回答"如果成交赚多少"，带宽回答"能不能成交"。
> 先量 `B`（`q_up − q_dn`，`docs/tools/dex_probe/` 或 `spread_stats` 快照里有），再决定填不填地板。

#### `minSpreadTarget` 该填多少：可行区间（`tests/param_calc` 第 8 节）

上面说的是"填了会怎样"，这里说"该填多少"。两个约束把它夹住：

- **上限（可达）**：地板把入场钉在 `−(mst+5e-6)`，成交要求这个价位**落在分位之内**
  ⇒ `mst ≤ |入场分位| − 5e-6 − F_mt`（MT）或 `− 5e-6 − ttAdd − F_tt`（TT）
- **下限（净利）**：地板越浅、入场越浅、净利越小 ⇒ 阈值处净利 `CL − OL` 要 `≥ minProfitTarget`

对称带宽（`q_dn = −B/2`）、`F_mt=7bp`、`F_tt=10bp`、`ttAdd=3bp`、门槛 5bp：

| 带宽 `B` | MT 上限 | TT 上限 | MT 有解？ | TT 有解？ |
|---|---|---|---|---|
| 20bp | **+2.95bp** | −3.05bp | 刀刃点（宽度 0，实际不可用） | ✗ |
| 25bp | +5.45bp | −0.55bp | ✓（`mst ≤ 5.45`） | ✗ |
| 30bp | +7.95bp | +1.95bp | ✓ | ✓（`mst ≤ 1.95`） |
| 40bp | +12.95bp | +6.95bp | ✓ | ✓ |
| 50bp | +17.95bp | +11.95bp | ✓ | ✓ |

**TT 的上限永远比 MT 低 6bp** = `ttAddPercent` 3bp + `F_tt − F_mt` 3bp。

> **当前 `minSpreadTarget = 0.0012`（12bp）要落在区间内，MT 需要 `B ≥ 38bp`，TT 需要 `B ≥ 50bp`。**
> 实测 p95 只有 1~11bp（`B ≈ 2~22bp`）⇒ 这个配置在该对子上是"**永不开仓**"，不是"少开仓"。

跑法：

```bash
cd utrade_hft/tests/param_calc
./run.sh axes -0.00125 0.00125 -0.00125 0.00125 -0.00125 0.00125 -0.00125 0.00125   # B=25bp
```

输出会逐方向给 `下限 / 上限 / 当前值判定`；无解时还会给"最接近可行"的点（净利差多少、深度差多少），
方便判断是差一点还是差很多。

**"下限 = 无下限"不代表地板没用**：它只说明关掉地板净利也够，地板此时的作用是把单笔做大、频率压低。

### 开仓的"预期往返净利"门槛（`minProfitTarget`，2026-10-26 起）

地板只回答"入场够不够深"，回答不了"出场线在哪"。出场线由**对向**分位决定：

```
mtCLStartSpread = q_up × 0.8 − F_mt + profitPct   ⇒  裸价差回到 q_up × 0.8 + profitPct 就平
```

`q_up` 很浅（甚至为负）时出场线贴在 0 附近，地板给的那 5bp 就被吃掉。`minProfitTarget`
把两头一起算进开仓判据：

```
净利 = 预期出场裸价差 − 当前入场裸价差 − 2F
     = (平仓阈值 + F) − 当前价差 − 2F
     = 平仓阈值 − 当前价差 − F
```

四个方向逐条（`SignalGenerator::CheckSignalForSatisfy` 里就是这四行）：

| 方向 | 净利式子 | 轴 |
|---|---|---|
| `mtOL` | `mtCLStartSpread − spreadAskAsk − F_mt` | ask-ask |
| `mtOS` | `spreadBidBid − mtCSStartSpread − F_mt` | bid-bid |
| `ttOL` | `ttCLStartSpread − spreadBidAsk − F_tt` | bid-ask |
| `ttOS` | `spreadAskBid − ttCSStartSpread − F_tt` | ask-bid |

`>= minProfitTarget` 才允许开仓。**只在开仓四个方向上生效，平仓不受约束** ——
否则止损/风控平仓会被这道门槛卡死（用例 D19④ 专门钉这一条）。

必须知道的五点：

1. **净额口径，不要再自己加手续费。** 式子里那个 `− F` 已经是往返成本：开仓判据
   `裸价差 + F < start` 与平仓判据 `裸价差 − F > start` 各含一个 F，相减时两个都留下。
   祖先的 `min_profit_target` 是毛口径（`_q_org` 与 `_n_org` 两边 F 抵消），这里**故意改成净口径** ——
   否则 4bp 的毛门槛盖不住十几 bp 的往返费。
2. **分工**：地板管"入场深"，门槛管"入场到出场还剩多少"。两者同时成立时，等价于要求
   `出场线 >= minProfitTarget − minSpreadTarget − 5e-6 + F_mt`。当前配置
   （`0.0005 / 0.0012 / F_mt = 7bp`）算出来是 **−0.05bp**，即 `q_up × 0.8 + 1bp >= −0.05bp`
   ⇒ **`q_up >= −1.3bp` 就放行**。所以它现在是保险，不是刹车。
3. **逐 tick 用实时价差算，不是用阈值算。** 入场价越好（价差越深），净利越大、越容易过门槛；
   上面那个 −0.05bp 是"刚好卡在入场阈值上"的最紧情形。
   ⚠️ 别把它"化简"成 `ttOSStartSpread − ttCSStartSpread`：在触发边界上两者**数值相等**（F 抵消），
   但输入不同 —— 阈值差只含**分位数**（`RecalcOrderParams` 重算，默认 24h 窗口、60s 一次，是慢变量），
   逐 tick 版含**瞬时价差**。相差的正是"这一笔比阈值深多少"。
4. `<= 0` = 关掉这一层（与 `minSpreadTarget` 同一约定）。
5. 改了要重启，不支持热改。

**它解决不了什么**：这里假设出场一定发生在"对向分位线"上。而**那条线本身在漂** ——
`mtCLStartSpread = q_up × 0.8 − F + profitPct`，`q_up` 每 `spreadStatsUpdateIntervalSec`（默认 **60s**）
按 **24h** 窗口重算一次。所以**没有"固定的平仓价差"**：`q_up` 涨 5bp，平仓线就涨 4bp。

价差没回到那条线就被风控强平 / 超时撤单 / 人工平仓，或者实际成交价劣于阈值时，实际净利会低于这个数。
按**实际持仓均价**控制平仓线（祖先的 `close_profit` / `adj_profit`）**没有搬**，那是另一件事 ——
而且它最多只挪 `profitPct`（1bp），只在逼近杠杆上限（90% / 95%）时才生效，不是"按目标盈利平仓"的旋钮。

> **唯一锚定入场价的机制是 `profitSwitch`**（`AlgoPairOrder.cpp:477`）：`tempSpread − lockedSpread ≥ profitPct`，
> 即 `spreadBidBid ≥ lockedSpread + profitPct + F`。但地板强制在 −19bp 附近开仓、分位线在 +5.8bp，
> 所以这条锚定条件（`−19 + 1 + 7 = −11bp`）比阶梯的门槛（`+5.8bp`）**低 16.8bp，从来不 binding**。
> ⇒ 现在真正决定平仓的**只有分位线**。想让"每笔至少赚 X bp"成为硬约束，`X` 必须大于
> 分位线已经给出的净利（p92 = 6bp 时是 **10.85bp**），否则改了也没用。

用例见 `tests/market_to_algo` 的 D19。

## 3. 参数放在哪、怎么改

**参数已经全部配置化**（2026-10-01）。`utrade_hft/etc/config.json` 的 `op` 段下有三份子对象，
覆盖了原来散落在两个头文件里的编译期常量、以及 `BuildAlgoOrderJson` 里那一大段硬编码：

```
op.feeSlippage  ->  m_ptCfg.feeSlippage (pt::FeeSlippageConfig)  13 个字段  执行成本 / 滑点 / 价差阈值
op.risk         ->  m_ptCfg.risk        (pt::RiskConfig)         14 个字段  风控门槛 + 渐进式平仓三档
op.pairTrading  ->  m_ptCfg             (pt::PairTradingConfig)  55 个字段  策略参数(18) + 分位数快照(2) + 算法单参数(35)
                                                                ─────────
                                                                 82 个字段
```

前两个是 `PairTradingConfig` 的成员（`feeSlippage` / `risk`）—— `SignalGenerator` 与
`RiskManager` 是跨组件使用的单例，各自必须持有一份自己的配置副本；放在
`PairTradingConfig` 里是为了让"本次启动实际生效的全部参数"集中在一处，便于日志核对。
`pre_start` 解析完这两段之后会调 `SetConfig` 推给这两个单例。

**算法单参数没有独立结构体**（2026-10-02 去掉了 `pt::AlgoOrderConfig`）：报单类型 /
撤单门槛 / rebalance 这些就是 `PairTradingConfig` 的普通字段，和策略参数一起放在
`op.pairTrading` 段，由 `BuildAlgoOrderJson` 直接读，不用推送。

另有 **7 个 key 也在 `op.pairTrading` 段**（2026-10-26 之前平铺在 `op` 段，现已移入）：
`pairKeys` / `activeAccountId` / `passiveAccountId` / `maxPositionValue` / `maxAmount` /
`targetAmount` / `csvStatePath`。它们和其余策略参数的区别只是**读法带副作用**
（`pairKeys` 边遍历边订阅行情），所以仍然是 `pre_start` 直接读。
搬完之后 `op` 段只剩 base 类自己要读的 `strategyOp` / `timerInterval` / `strategyIds`。

**解析就在 `pre_start` 里，逐字段读，没有中间层**：每个 key 都是

```cpp
if (s.HasMember("activeMakerFeeRate")) c.activeMakerFeeRate = std::stod(s["activeMakerFeeRate"].GetString());
```

数值一律 `Value.GetString()` 再交给 `std::stod` / `std::stoll` / `std::stoi`
（`config.json` 用 `kParseNumbersAsStringsFlag` 解析，数值读出来都是字符串）；
布尔字段没有对应的 std 函数，直接和 `"true"` 比字符串。

改配置**不需要重新编译**。启动时 `pre_start` 会打六行 `配置生效[…]`，
打的是**解析之后**的实际值（不是文件里的原文），可直接核对。

紧接着还有**一行派生值** `配置派生[门槛]`（2026-10-26 起），把配置翻译成"价差实际要走到多少 bp"：

```
配置派生[门槛] 地板=12bp 毛门槛 mt=19.05bp tt=25.05bp | 价差回0净利 mt=5.05bp tt=5.05bp | 门槛=5bp 地板已够
```

它算的是 `毛门槛 = 地板 + 5e-6 + F`、`净利 = 地板 + 5e-6 − F`。
**改费率后先看这一行**：如果 `价差回0净利` 掉到 `门槛` 以下，会变成 `WARN` 并直接告诉你
"入场需比地板再深 X bp，或把 minSpreadTarget 提到 Y" —— 这是唯一能自动发现
"改了费率忘重算地板"的地方（两个原始值本身看起来都没毛病）。

#### 3.1.1 `activeMakerFeeRate` 只影响**地板**和**记账**，不影响分位数那条线（2026-10-03 复查；2026-10-26 加地板后修正结论）

冒烟测试时有人把 `activeMakerFeeRate` 改成 `-0.0002`，想"更容易开仓"。**在 2026-10-26 之前这个想法
完全不成立** —— 那时没有地板，它对开平仓阈值和报单量一点影响都没有。加了 `minSpreadTarget`
之后它**会**影响，但只通过地板那一条路（`毛门槛 = 地板 + F`），分位数那条线仍然完全不受影响。

原因是执行成本 `F` 在**三处相互独立的地方各自精确抵消**，抵消后阈值里根本没有 `F`：

| # | 位置 | 表达式 | 抵消后 |
|---|---|---|---|
| 1 | 信号闸门 `SignalGenerator.cpp:245` | `spreadAskAsk + F_mt < mtOLStartSpread`，而 `mtOLStartSpread = Q_askAskDQ × 0.8 + F_mt` | `spreadAskAsk < Q_askAskDQ × 0.8` |
| 2 | 算法单阶梯 `AlgoPairOrder.cpp:245-253` | `tempSpread = spreadAskAsk + F_mt`，`startSpread = Q × 0.8 + F_mt`，`endSpread = startSpread − 5e-6` | `(tempSpread − startSpread)/(endSpread − startSpread)` 里 `F` 消掉 → **报单量也与 F 无关** |
| 3 | "目标价差偏离过大"守卫 `BaseAlgoOrder.cpp:848` | `pairRealSpread ±= F_mt`，而 `pairTargetSpread = mtOLStartSpread` **也含** `F_mt` | `pairRealSpread − pairTargetSpread` 里 `F` 消掉 |

（`mtCL` / `ttOL` / `ttOS` / `ttCS` 四条同构，结论一样；`takerTakerFs` 同理。）

**`F` 存活的只剩两处：记账 + 地板**（2026-10-26 加了 `minSpreadTarget` 之后，"唯一"不再成立）。

> 上面三条抵消都发生在"`F` 在比较式**两边各出现一次**"的地方。地板是唯一一处 `F` 只在
> **一边**出现的：它夹的是含 `F` 的 `StartSpread`，而夹逼值本身不含 `F` ⇒ 抵消不掉，
> 于是 `毛价差门槛 = 地板 + F`。**这就是"填费率到底有什么用"的答案：只对地板这一层有用。**

第一处是记账 —— `BaseAlgoOrder.cpp:193/199`：

```cpp
activePrice = pairOrder.activeTotalPriceOnOrder * (1 ± activeMakerFeeRate);
```

它被写进 `pairActiveTotalPrice`（持仓的**记账均价**，`:246/259/280/287`），再喂给
`lockedSpread`（`:363`）= `pairPassiveTotalPrice / pairActiveTotalPrice − 1`，再进
`profitSwitch` 的 `profitRate`（`AlgoPairOrder.cpp:358 / 375 / 477 / 493`）：`profitRate < profitPct`
时把目标量拉回 `startVolume`，**报单量为 0（不平）**；否则按阶梯部分平。

> ⚠️ 这里很容易读反，别被"`targetActiveVolume = startVolume`"骗了。对 `CLOSE_LONG`，
> `startVolume = mtCLStartVolume = −maxVolume`（`SignalGenerator.cpp:47`），而 `pairTotalVolume`
> 对多头也是**负**的 —— 两者同号，所以"目标量 = startVolume"= **维持满仓**，不是"全平"。
> 真正平到底的那一端是 `endVolume = 0`。随后 `targetVolume = targetActiveVolume − expectActiveVolume`
> 为 0 或负，被 `targetActiveVolume > expectActiveVolume` 那道守卫拦掉，**一单都不报**。
> 所以 `profitSwitch` 的语义是"**没赚够就不平**"，与祖先 `:857-860` 的 `except_close_flag = False` 一致，
> 不是"加速平仓"。

⚠️ 所以"记账"不是纯展示，有两件事别搞混：

1. **记账口径 ≠ `CalcExecCost` 口径。** 记账按每个子单的真实类型取费率（被动腿是
   `OT_POST_ONLY` 就 `passiveMakerFeeRate`，否则 `passiveTakerFeeRate`），**不含 `basicSlippage`**；
   而 `CalcExecCost` 一律按"被动腿 taker + 滑点"算。同一笔交易的"阈值成本"和"记账成本"
   本来就不是一个数，**别拿一个去校验另一个**。
2. **记账会改变平仓量。** 上面的 `profitRate` 就是拿记账均价算的 ⇒ 费率填错会连带把
   "还没赚够就不平"这道保护调松或调紧。按当前配置（`activeMakerFeeRate = 0.0002`、
   `passiveTakerFeeRate = 0.0005`），记账每边扣 **+7bp**（maker 2 + taker 5），与零售档一致；
   只有被动腿真的用 `OT_POST_ONLY` 时才按 maker 记。**费率填成 0 或返佣值时，`profitRate` 会虚高
   约 9bp，这道保护就是偏松的。**

> 📌 另外，**交易所实际收了多少钱，系统里根本没有**：`lastExecutedTradeFee` 的赋值整段被注释
> （`AlgoContext.cpp:1108-1123`），字段恒 0，也没有任何地方读它、算法单 CSV 也不写这一列
> （`WriteFileContent.h` 的 `ty==3` 表头只有四个**费率**和 `makerTakerFs/takerTakerFs`）。
> 想核对"这一笔实际净赚多少"，只能拿成交价 × 配置费率自己重算 —— 而配置费率一旦不是账户真实
> 档位，重算出来的数也是错的。这是"必须把五个费率填成真实值"的第二个理由（第一个是地板）。

**结论**：`activeMakerFeeRate` 不影响**分位数那条线**（三处抵消），但它**会**通过地板改变
"毛价差要走到多深才报单"（`毛门槛 = minSpreadTarget + F`）。所以在有地板的前提下，把费率填成
返佣值确实会让开仓更容易（毛门槛 23.05bp → 18.05bp）—— **这不是漏洞，是地板的正确语义**：
成本低就该少要求一点。要让冒烟测试更容易触发开仓，该动的是**真正出现在阈值里的量**：`spreadAdjPct`（调小 → 阈值更靠近中位数 → 更容易）、
`minSpreadTarget`、`ttAddPercent`（只影响 TT）。**而且负费率会把成本口径变成"倒贴"，测出来的 PnL 不可信。**

> **那"只成交一笔 → 算法单撤单 → 接着报平仓单"是怎么来的？** 与费率无关。
> 算法单终结只有三条路（`RequestCancelAlgoOrder` 的三个调用点），按可能性排：
>
> | # | 日志关键字 | 含义 |
> |---|---|---|
> | 1 | `CheckAlgoOrderTimeout: ... idleSec:X > 150s -> cancel` | `satisfyTime` 连续 150s 没被刷新。它只在**当下**有开仓/平仓信号时才刷新（`UpdateSatisfyTime`），价差一回到中间就停表 |
> | 2 | `TargetSpreadStop MAKERTAKER ... mtSpreadFlag:true` | "目标价差与实际价差离的太远，暂停交易" → `AlgoContext.cpp:484` 挡住**所有新的 MT 报单**，同时 `CancelOrderOnSpread` 撤掉已有子单 → 单子停摆 → 走第 1 条的超时 |
> | 3 | `mtSlipageFlag`（`BaseAlgoOrder.cpp:784`） | 判据 `mtSlipage > 2 × passiveTakerSlippage + profitPct`。`passiveTakerSlippage = 0`、`profitPct` 默认 0 → **`mtSlipage > 0` 就会触发**，同样在 `:484` 挡住新单 |
> | 4 | `CheckExposureAbnormal ... -> errorFlag + cancel` / `ProcessRisk RequestCancelAlgoOrder` | 敞口异常 / 风控强平 |
> | 5 | `swch is false!` | 开关被 `RecalcOrderParams` 关掉（`spreadSpan < minSpreadSpan`、资金费率过大、流动性/保证金状态） |
>
> 之后的平仓单**本身是合法的**：对子释放后 `mtCLSignal` 的判据是
> `spreadBidBid > Q_bidBidUQ × 0.8 + profitPct` —— 它用的是 **bid-bid 轴**，与开仓用的
> **ask-ask 轴**不是同一个，所以"刚开就平"在盘口抖动时完全可能发生。
> 要定位走了哪条，就搜上面 5 个关键字。
> ⚠️ 曾经在 `CheckSignalForSatisfy` 里有 8 行 `std::cout` 逐 tick 打 `F_tt/F_mt` 和 8 个条件，
> **2026-10 已全部删除**（`grep -c "std::cout" quant_library/signal/SignalGenerator.cpp` = 0）。
> 现在要看逐 tick 条件，用 `tests/param_calc`（离线复算）或临时加一行日志，别再按老文档去找那些输出。

#### 3.2.1 `spreadStatsStatePath` / `spreadStatsMaxStaleSec` —— 重启免预热

**问题**：`SpreadStatsBuilder` 要先在内存里攒够 `spreadStatsMinSamples` 个样本、
算出价差上下分位数，`SignalGenerator::RecalcOrderParams` 才有东西可算 ——
在那之前它直接 `return`，`orderParams` 全是默认值，**一单都发不出去**。
生产参数下这段"哑火期"是分钟级，每次重启都要重付一遍。

**做法**：把算好的分位数单独落一份盘（`data/spread_stats.csv`，12 列），
重启时够新就直接顶上，不必再等预热。

```
                        ┌── 每个 spreadStatsUpdateIntervalSec（60s）──┐
OnTimer ─► Prune(24h) ─► Build(qUp,qDn,minSamples) ─► UpdateLargeStats ─► RecalcOrderParams
                                                                              │
                                                        SaveSpreadStats ◄─────┘  顺手落盘
Init ─► LoadSnapshot ─► LoadSpreadStats ─► 对每个对子 RecalcOrderParams
         （账本）         （分位数）        ← 必须重算，否则阈值仍是默认值
```

几个要点：

- **新鲜度按样本时间算**（`calcTs`，取自 dbp 的 `generateTs`，不是墙钟）。
  停牌 / 断档时它不前进，所以一条判据同时挡住"进程停了很久"和"行情本身就停了很久"。
  超过 `spreadStatsMaxStaleSec` 就**不恢复**、回退到正常预热，日志打
  `统计已过期 …s > …s -> 不恢复，正常预热`。
- **一个有效统计都没有时不写盘**（预热期每轮都会走到这里，无脑 truncate 会把
  上一份好值刷成空表头，"重启顶上"就永远生效不了）。
- **单独一个文件，不动 `pair_info.csv` 的 33 列格式**：分位数是派生字段，
  两个文件的恢复语义不同（这本账丢了只是回到旧行为；`pair_info.csv` 丢了是丢账）。
- 路径留空、或 `spreadStatsMaxStaleSec <= 0`、或列数不兼容 → 都等于关掉这个功能，
  回到改动前的行为（重新攒样本）。**最坏情况就是多预热一次**，没有正确性风险。

#### 3.2.2 为什么不直接存 `orderParams`

开平仓判据（`SignalGenerator::CheckSignalForSatisfy`）读的确实是 `pi.orderParams`，
所以"把 `orderParams` 存下来、重启直接灌回去"看起来更直接。但它比存分位数差，原因有三条：

**① `orderParams` 不是一个输入，是一个"用当前配置算出来的结果"。**
存结果 = 存一份**用旧配置算出来的缓存**。重启后配置一变，这份缓存就和现场不一致，
而且是**静默**不一致 —— 没有任何东西会发现它错了。

`RecalcOrderParams` 用的是 `startSpread = Q × spreadAdjPct − dir × (execCost − buffer)`，
而 `CheckSignalForSatisfy` 判的是 `spread + execCost < startSpread` ——
两者**同源**，`execCost` 精确抵消，最终入口条件就是 `spread < Q × spreadAdjPct − buffer`，
**与费率无关**（这是刻意的设计）。一旦 `orderParams` 被跨配置恢复，这个抵消就断了：

| | 存的时候费率 | 恢复后费率 | 实际入口 |
|---|---|---|---|
| 设计意图 | 任意 | 任意 | `spread < Q×0.8 − buffer` |
| 存 `orderParams` | `0`（冒烟值） | `0.0013`（生产值） | `spread < Q×0.8 − buffer − 0.0013` → **紧了 13 bp** |
| 存 `largeStats` | — | — | `spread < Q×0.8 − buffer` ✓ |

⚠️ 这不是假想：**仓库现在五个费率全是 `0`，实盘前必须填回真值**（见 §9）。
按"存 `orderParams`"的做法，那次改动会在**重启之后被悄悄吃掉**。

**② 一半的 `orderParams` 根本不是分位数的函数。**

| 字段 | 真正的来源 | 重启时 |
|---|---|---|
| 16 个 `*StartSpread` / `*EndSpread` | `largeStats` 的分位数 + 配置 | 分位数可恢复 |
| 16 个 `*StartVolume` / `*EndVolume` | `pi.maxVolume`（由腿价算出） | **要等第一条行情**，恢复不了 |
| 8 个 `*Switch` | `autoFlag` / `closeFlag` / 资金费率 / 流动性 / 保证金状态 | 部分是实时状态，**不该恢复** |
| 4 个 `*CL` / `*CS` 的 Start | 还叠了 `profitSwitch` / `profitPct` | 运维意图，另有快照管 |

存 `orderParams` 就得连"当时的腿价、当时的资金费率、当时的流动性状态"一起存，
重启后把这些**过期的现场**灌回去 —— 那是把一个缓存当成了事实。

**③ 没有新鲜度锚点。** 分位数有 `calcTs`（行情时间），可以判"这份统计还作不作数"。
`orderParams` 只有墙钟可锚，而墙钟判不出"行情本身停了"。

**结论**：存**输入**（分位数），重启时用**当前配置**重算一遍。多一次函数调用，换来自洽。

#### 3.2.3 一个被这个功能暴露出来的耦合 bug

`RecalcOrderParams` 原来把"分位数"和"`maxVolume`"两个**互相独立**的输入
耦合在同一个 `if (!ls.IsValid()) return;` 后面，于是：

```
重启恢复分位数 → Init 里算一次 orderParams，但那一刻腿价还没有 → maxVolume = 0
              → ttOLEndVolume = 0 → 开仓判据 `vol > ttOLEndVolume + 1e-9` 退化成 `0 > 1e-9`
              → 一单都开不出去
下一轮统计刷新 → 窗口刚重启、样本不够 → largeStats 被刷成无效 → 早退一挡
              → 量字段永远停在 0，直到窗口重新预热完 ≈ 29 min → **等于一天没省**
```

修法是把量字段移到早退**之前**（它们本来就只依赖 `maxVolume`），
并在 `OnTimer` 的量重算之后补一次 `RecalcOrderParams`：

```cpp
// SignalGenerator::RecalcOrderParams —— 量字段与分位数解耦
{ const double mv = pi.maxVolume;
  op.ttOLStartVolume = 0.0;   op.ttOLEndVolume = -mv;   ... }
if (!ls.IsValid()) { return; }        // 只有"价差类"字段才需要分位数
```

```cpp
// PairTradingContext::OnTimer —— 量一变就重算（orderParams 的量字段取自 maxVolume）
pim.RecalcVolumeParams(...);
for (PairInfo* pi : pim.GetAllPairInfos()) { sg.RecalcOrderParams(*pi); }
```

这个耦合在加恢复功能之前**一直存在**，只是被"冷启动本来就要等 29 min"掩盖了：
冷启动时 `largeStats` 无效，早退挡着，谁也看不出量字段没跟上。

回归用例 **G20** 钉住这件事 —— 它断言的是"单真的报出去了"（`fx.N() > 0`），
不是"某个字段有值"。只断言 `ttOLStartSpread` 的话，上面那个 bug 照样全绿。

### 3.5 语义约定（改配置前先看这段）

解析就是 `pre_start` 里的 `if (s.HasMember("x")) 字段 = std::stod(s["x"].GetString());`，所以：

| 约定 | 说明 |
|---|---|
| **只覆盖、不清零** | 配置里**少写一个 key** 等价于"保持代码里的默认值"，不会变成 0 —— 因为赋值只在 `HasMember` 成立时发生。所以可以只写想调的那几个 |
| **值写错 → 启动直接失败** | 数值字段走 `std::stod` / `std::stoll` / `std::stoi`，解析不出来会抛 `std::invalid_argument` / `std::out_of_range`，`pre_start` 不接 —— 配置写错就该在启动时炸，别带着一个"看起来对"的值跑起来。这也和原有那 7 个平铺 key 的行为一致 |
| **布尔必须写带引号的 `"true"` / `"false"`** | 取值是 `s["x"].GetString() == "true"`。**写成裸 `true` 会挂进程**：`kParseNumbersAsStringsFlag` 不影响布尔，裸 `true` 是原生 bool，对它调 `GetString()` 触发 `RAPIDJSON_ASSERT(IsString())` —— 断言失败不是异常。除 `"true"` 之外的一切（含 `"1"` / `"yes"`）都当 false |
| **枚举必须显式拒绝哨兵** | `OrderType` 用 `OrderTypeStr2EnumMap.find()`（**不能用 `operator[]`** —— key 不存在时它会插入 `OT_MIN`），并且显式拒掉 `OT_MIN`；`targetSpreadType` / `activeVolumeCalcualteType` 用 if/else 只认真值。哨兵配上去会被当成合法值用下去 |
| **单位** | 时间字段带单位后缀：`*Sec`（风控）与 `*Ms`（算法单撤单）写秒 / 毫秒，结构体内部仍是微秒。风控的 `*Sec` 在 `pre_start` 里 ×1000000；算法单的 `*Ms` 在 `BuildAlgoOrderJson` 里 ×1000（**只在这一处**换算） |
| **数值字符串与原生数字都认** | `config.json` 用 `kParseNumbersAsStringsFlag` 解析，所以 `"1000"` 与 `1000` 读出来都是字符串。现有文件统一用字符串，照着写即可 |

### 3.8 哪些参数可以**热改**（不用重启）

目前只有**两个**，都在 `op.pairTrading` 下：

```json
"closeOnly":   false,     // 只平不开（运维急停）
"stopAllAlgo": false      // 停掉所有算法单（更狠的一档，人工接管）
```

⚠️ **必须写裸 `true` / `false`，不能加引号。** 加了引号时 `GetBool()` 作用在字符串上：
Debug 是 `RAPIDJSON_ASSERT` 直接 abort，Release 下**静默读成 `false`** —— 也就是"你写了 true，
系统认为你没写"。这一点和 `etc/config.json` 里其他布尔字段完全一样，没有额外兜底。

两个开关的区别：

| | `closeOnly` | `stopAllAlgo` |
|---|---|---|
| 新开仓 | 不发 | 不发 |
| 策略平仓 | **照常发** | 不发 |
| 风控强平 | 照常发 | **不发** |
| 在跑的算法单 | **不撤**：推一条 MODIFY 把 4 个开仓开关压掉。空仓且无在途子单 ⇒ 执行侧下一轮自己终结成 `FILLED`；已部分成交 ⇒ **退化成只能平仓的单**（等平仓价差条件到了才平，不立刻平） | **撤掉**，每 tick 请求一次直到终结 |
| 谁收尾 | 策略自己 | **人**（已有持仓要自己处理） |

`closeOnly` 对**正在跑的开仓单**到底做什么（2026-10-26 复核，逐层）：

1. `closeOnly` **从不调用** `RequestCancelAlgoOrder` —— 它是关闸门，不是拉手刹。
2. `OnTimer` 第 0.6 步把 `algoModifyTime` 归零 ⇒ 同一轮 `ProcessModify` 推一条 `MODIFY`，
   把 4 个开仓开关（`ttOL/ttOS/mtOL/mtOS`）压成 `false`，4 个平仓开关不动。
   - 开关是**显式逐个字段覆盖**到在跑对象上的：`BuildNormalModify` 把 `pi.orderParams` 的
     8 个开关全抄进消息（`PairTradingContext.cpp:637-644`），`AlgoContext` 的 MODIFY 分支再逐个
     赋给 `pAlgoOrder`（`AlgoContext.cpp:195-202`）。所以 `pAlgoOrder->ttOLSwitch` 真的变成 false，
     之后 `GetTargetPairOrder`（`AlgoPairOrder.cpp:132/144/150`）读的就是这个成员。
   - **生效时点不是"等一秒"**：`heavy_work` 一个循环里先 `FetchLast → on_dbpdata → OnSpread`
     （读开关、报单的地方），再按 `timerInterval` 跑 `on_timer`（MODIFY 在这里）——
     见 `base_strategy.h:132-142`。所以本次 tick 的 `OnSpread` 用的还是旧开关，
     **下一次行情到达**才用新的（亚毫秒到几十毫秒）。全部在 `heavy_work` 一条线程上，没有跨线程竞争。
3. 执行侧**下一个 tick** 按 `expectVolume = GetExpectActiveVolume()`（当前已成交的主动腿量）分三种走：
   - **还没成交**（`|expectVolume| < minVolume`）⇒ 走 `AlgoPairOrder.cpp:677-686` 的 else 分支，
     而那里只判 `ttOSSwitch` / `ttOLSwitch`，两个都是 false ⇒ **不报单**；
     再下一轮命中"结束订单检查"（`AlgoContext.cpp:1388`：4 个开仓开关全 false +
     `|pairTotalVolume| < minSize` + `allPairOrders` 空）⇒ 自己终结成 `ALGO_OS_FILLED`，对子释放。
     **没有撤单动作。**
   - **已部分成交** ⇒ 走 `AlgoPairOrder.cpp:665-676`：`ttOLSwitch` 为 false、`ttCLSwitch` 为 true
     ⇒ 落到 `GetTargetPairOrder(CLOSE_LONG)` 分支。也就是说这张单**退化成一张"只平不开"的单**：
     它不会接着把开仓量补完，而是**等平仓价差条件成立时**把已有那部分平掉（`GetTargetPairOrder`
     里还要过 `ttCLStartSpread` 的价差判断，所以不是立刻平）。
   - **有在途 pairOrder** ⇒ 先等它走完（被动腿成交），再按上面两条之一处理。
4. 兜底：开仓开关压掉后 `CheckSignalForSatisfy` 不再产出开仓信号 ⇒ 无持仓时 `satisfyTime`
   停止刷新 ⇒ `algoOrderTimeoutMs`（默认 **150s**）后 `CheckAlgoOrderTimeout` 发 CANCEL。
   ⚠️ 这条对**手动对子**（`autoFlag == false`）不生效，它会一直跑到自己成交完。

> ⚠️ **开关有两套（`tt*` / `mt*`），执行侧读哪一套由 `BaseAlgoOrder::tradingTypeOrder` 决定**，
> 不是由 `algoMode` 字符串决定：建单时按 `isTT ? TAKER_TAKER : MAKER_TAKER` 写进这个字段
> （`PairTradingContext.cpp:892`），`AlgoContext::OnSpread` 再用它选分支
> （`AlgoContext.cpp:484` 要 `MAKER_TAKER`、`:572` 要 `TAKER_TAKER`）。
> **2026-10-26 之前这一行被写死成 `MAKER_TAKER`** ⇒ 所有 `algoMode == "TT"` 的算法单实际跑的是
> MT 分支：读 `mt*` 开关、用 `spreadAskAsk / spreadBidBid` 与 `makerTakerFs` 定价，只有子单类型
> 和报单量来自 TT。`closeOnly` 两套开关都压，所以上面那条链路不受影响；但"报出去的单按哪套价差挂"
> 完全取决于这一行。`tests/algo_exec` 的 D8 现在会验执行侧 4 个开关真的被写成 false。
>
> 改完这一行后，TT 单才真正走 TT 分支，于是这两处跟着变了：① 并发闸门用 `maxTTOrderSize`
> 而不是 `maxMTOrderSize`（`etc/config.json` 里两个都是 `1.0`，默认也是 1.0，不会因此一单不报）；
> ② "结束订单检查"（`AlgoContext.cpp:1388`）同时看 `tt*` 和 `mt*` 四开关，不受影响。
>
> 顺带记一处**钓鱼单分支**里的参数错配（`AlgoType_FishingOrder`，配对交易不走这条路）：
> `AlgoContext.cpp:858` 拿 `GetSizeByOrderTypeAndActiveDirection(MAKER_TAKER, DT_LONG)` 去比
> `maxMTOrderSize`，但紧跟着创建的是 `CreatePairOrder(TAKER_TAKER, DT_LONG)`；`:885` 的
> `TAKER_TAKER` 计数比的却是 `maxMTOrderSize`。两处都该是 `TAKER_TAKER` + `maxTTOrderSize`。
> 现在配置里两个值都是 1.0，所以没有可观测差异。

所以"现在正在开仓，改成只平不开"的实际效果是：**不再报新开仓子单；未成交的单下一轮自己终结，
已部分成交的退化成只能平仓的单**，最差 150 秒后按超时撤掉（手动对子除外）。
想立刻撤，用 `stopAllAlgo`。

`stopAllAlgo` 是给"人工接管"用的：打开后系统不再动任何单。**它不会帮你平仓，也不会
保留任何自动收尾能力** —— 场上已有的持仓、以及撤单过程中被动腿可能的成交，都得自己处理。

⚠️ **"打开 `stopAllAlgo`" ≠ "场上立刻干净"。** 撤单是异步两段式的：`CANCELLING` 只撤**主动腿**，
被动腿留着等成交（挂着的被动腿说明主动腿已成交、场上存在单边敞口），对子要等
`allPairOrders` 清空才释放。而**这个等待没有上界** —— 被动腿长期不成交（流动性没了、价格跑掉）
时，算法单会一直停在 CANCELLING，对子也一直被它占着。系统没有"撤单超时升级"，所以打开开关后
**必须自己去交易所确认是不是真的没单了**。这是既有的已知残余风险（`PairTradingContext.cpp`
里 `ProcessRisk` 的注释记着），不是这个开关引入的。

改完保存文件，**约 1 秒**生效，不用重启：

| 步骤 | 谁做 | 频率 / 代价 |
|---|---|---|
| `stat()` 配置文件，比对 inode + mtime(纳秒) + size | `T_signal` | 1 次/秒（没变就只有这一条 syscall） |
| 指纹变了才读文件 + 用 rapidjson 解析 | `T_signal` | 只在变化时（几十 KB 的 JSON，一次几 ms） |
| 解析成功就 `push` 进 `m_cfgQ`（SPSC，容量 16）；失败直接跳过 | `T_signal` | 一次 push |
| 抽干队列、搬进 `SignalGenerator` / `m_cfg` + 重算 `orderParams` + 把 `algoModifyTime` 归零 | 交易线程 `OnTimer` 第 0.6 步 | 1 秒内 |
| `stopAllAlgo` 为 true：对每个 `hasActiveAlgoOrder` 的对子发 CANCEL | 交易线程 `OnTimer` 第 0.7 步 | 每 tick |
| 把新开关推给**正在跑**的算法单 | `ProcessModify`（上一步归零了它的计时） | 同一轮 |

`stopAllAlgo` 落在**三个**位置，各管一件事，缺一个都漏：

| 位置 | 作用 | 为什么在这儿 |
|---|---|---|
| `ProcessPairSignal` 开头（启动闸门之后） | 不创建任何新算法单 | 与启动闸门同一个语义"这个对子本轮什么都不做"。代价是 `satisfyTime` 不再刷新 ⇒ `CheckAlgoOrderTimeout` 会把在跑的单按超时撤掉；方向一致，不用额外处理 |
| `ProcessRisk` 里 `CheckRisk` 之后 | 连风控强平也不发 | 强平单也是算法单。**`CheckRisk` 必须照常调**：它内部在无持仓时要把几个计时起点归零，跳过它等于把陈旧时间戳带进恢复之后（一恢复就按旧档位强平） |
| `OnTimer` 第 0.7 步 | 撤掉在跑的单 | 撤单是异步两段式的（`CANCELLING` 要等被动腿成交才终结），每 tick 请求一次才能维持"一直在撤"；对已在撤单流程里的单重复发 CANCEL 是安全的（`CheckAlgoOrderTimeout` 到点后也这样）。**它保证的是"持续请求"，不是"一定终结"** |

另外 `ProcessModify` 在 `stopAllAlgo` 时直接返回：不给正在被撤的单推参数。推过去要么被执行端
跳过（算法单已在撤单流程里），要么在撤单延迟期间把刚压掉的开仓开关又推回去。

**排查"为什么不报单"先 grep 这一行**：`启动即处于急停状态: closeOnly=... stopAllAlgo=...`
（`Init` 里打的，任一开关为 true 就有一条）。因为上面三处闸门都是**静默 `return`**，
而第 0.6 步那行 `运行时配置: ...` 只在"配置发生变化"时打 —— 不补这一行的话，
"配置写着 true 然后重启"在日志里是完全看不出来的，最容易被误判成"策略没信号"。

`closeOnly` 生效后的表现：

- 4 个**开仓**开关（`ttOL/ttOS/mtOL/mtOS`）压成 `false`，4 个平仓开关一个不动；
- `CanOpen` 返回 false，理由写 `closeOnly = true (配置)` —— 日志里能看出是人关的，
  而不是"没信号"；
- **已有持仓照常平**，它**不会**主动平掉任何东西，只挡新开仓。

### 为什么是"一条队列"而不是"每个参数一个 `std::atomic<bool>`"

参数会越加越多，所以这里是一条 SPSC 队列，元素是**整份 `RuntimeConfig`**：

- 加参数不用动队列（不是"某参数的消息"，是整份配置）；
- `atomic` 只有"值"没有"事件"，消费端不知道"刚变的是哪个"，就没法只对变了的那个做
  附加动作（`closeOnly` 要 `RecalcOrderParams` + `algoModifyTime=0`，别的大多数参数不需要）；
- 队列天然有序：改两次就是两条，后一条覆盖前一条（`OnTimer` 抽干时只留最后一条）。

代价是 push 失败（满）就丢一次。16 条排不上要"文件被改 16 次而交易线程一个 tick 都没跑"，
那种情况下也没在交易，所以不做补偿。

三条刻意设计：

1. **删掉 key 等于 `false`，不是"保持当前值"。** `ReadRuntimeConfigFile` 每次都从默认值
   （全 `false`）开始填，文件里没有这个字段就保持默认。这与"和其他解析配置保持一样的方式"
   一致，但要注意：**想长期只平不开，就把它写在文件里**，别指望"注释掉就维持上次状态"。
2. **解析失败不更新指纹**，所以下一轮会重试。编辑器保存是"截断 + 写入"，
   中间那一瞬间读到半截是常态；如果失败也记成"已处理"，配置写坏了就永远不会被重试。
   同理，`HasParseError()` 和"根不是对象"都当失败返回 —— 否则 `v["op"]` 作用在非对象上，
   Release 是 UB、Debug 直接 assert，而这条代码跑在 `T_signal` 上（**那条线程没有 try/catch**，
   一崩就是整个进程）。
3. **解析用 rapidjson**，写法与 `src/strategy/PairTradingStrategy.cpp` 读配置那几段一致
   （`HasMember` + 一行取值）。本机没装 rapidjson，测试用 `tests/third_party/rapidjson`
   （1.1.0 原版头文件，未改一行）；`run.sh` 会先探测系统包，有就用系统的。
4. **不在交易线程读文件。** `OnTimer` 是执行线程，上面一条 IO 都不能有
   （见 `docs/执行线程耗时操作清单与方案.md`）。

加下一个字段的门槛：**改了立刻生效、且不需要重建对子**。
对子清单 / 账户 / 快照路径这些改了必须重启（要以另一套状态重来），不要往这里塞。
步骤（3 处）：`basic/RuntimeConfig.h` 加字段 → `ReadRuntimeConfigFile` 加一行解析
（照抄 `closeOnly` 那行）→ 落地点（`OnTimer` 第 0.6 步负责搬进 `m_cfg`，需要拦截的地方
再加闸门）→ `tests/market_to_algo` 的 K 组加用例。队列不用动。

### 4.4 `tb/etc/trade_config.json` —— 只有 BINANCE，而且指向 demo

这一处比前三处更硬：`TB.tb_accounts` 里**只有 `test1` 一个账户**，
`exchId = BINANCE` / `accountId = 10000`，而且 `accounts[0].restUrl` 是

```

```

也就是说：

| 缺什么 | 后果 |
|---|---|

## 5. 目标开仓量怎么设

`config.json` 的 `op.pairTrading` 段里三个量（单位都是 **USDT 名义价值**，不是币数）：

```json
"pairTrading": {
    "maxPositionValue": "500000",   // 全局持仓闸门（跨所有对子求和），<=0 关闭
    "maxAmount": "1000",            // 单对子最大持仓金额 -> pi.maxVolume
    "targetAmount": "1000"          // 单对子目标报单金额 -> pi.ttTargetVolume / mtTargetVolume
}
```

这三个**不是一个层级**，别混（2026-10-26 实测口径，与祖先一致）：

| 字段 | 作用域 | 换算成 | 超了会怎样 |
|---|---|---|---|
| `maxAmount` | 单个对子 | `pi.maxVolume`（开仓阶梯的上界） | 该对子不再加仓 |
| `targetAmount` | 单个对子 | `pi.ttTargetVolume` / `mtTargetVolume`（目标量） | — |
| `maxPositionValue` | **所有对子之和** | 不换算，直接比 | **只平不开**：全部对子禁止新开仓 |

`maxPositionValue` 就是祖先 `cc_pricespread_gb_ltp.py:825/832` 的 `just_close_flag`：
`position_value_all = pair_info['positionValue'].abs().sum()`。
落点是 `PairTradingContext::OnTimer` 第 0.5 步（算全局和）+ `SignalGenerator::RecalcOrderParams`
末尾（把 4 个**开仓**开关压成 false，4 个平仓开关一个都不动）。
它只管"要不要开新仓"，**不会主动平掉超出的部分** —— 减仓仍然靠平仓信号/运维命令。
`<= 0` = 关闭（**默认就是 0**，即没配就不改变行为）。
⚠️ 全局市值是**现算**的（`PairInfoManager::TotalPositionValue`），不用缓存的 `pi.positionValue` ——
后者只在 `UpdateOnAlgoOrder` 里刷，两次成交之间的价格变动不会更新，拿它当风控输入会滞后。

⚠️ **生效延迟（已知限制，刻意与祖先一致）**：闸门置位后 `pi.orderParams` 的开仓开关当轮就是 `false`
（下一条新单直接不开），但**已经在跑的算法单**要等到下一次 `ProcessModify` 才收到这个 `false` ——
`modifyTimespanSec` 默认 **60s**（`etc/config.json:48`），所以最坏 60s 内它还可能按旧开关继续开。
这段敞口的上界是"单个对子的 `maxAmount`"（算法单阶梯到 `maxVolume` 就停），不是无界的。
祖先 `cc_pricespread_gb_ltp.py` 结构相同（`just_close_flag` 也只经 modify 推送生效），故保持一致。
要缩短这个窗口，在闸门翻转时把 `pi.algoModifyTime` 归零即可（让下一个 tick 就推）——**未实施**，
因为那会偏离祖先行为，属于独立决定。

`PairInfoManager::RecalcVolumeParams`（`PairInfoManager.cpp:572+`）把后两个换算成**币数**：

```
a_target = ceil2min(targetAmount / activePrice / multiple, minVolume)
pi.ttTargetVolume = max(a_target, p_target)
pi.maxVolume      = min(a_max, p_max)          // a_max 来自 maxAmount
```

DOGE ≈ 0.0937 时，`targetAmount = 1000` → `1000 / 0.0937 ≈ 10672 DOGE ≈ 1000 USDT`。

**首轮联调强烈建议先调小**，否则第一笔就是 1000 USDT 的名义敞口：

```json
"maxAmount": "20",
"targetAmount": "20"
```

跑通全流程后再放回去。

> 注意 `RecalcVolumeParams` 需要腿价 > 0。K 线统计没接入
> （`UpdateKlineStats` 全仓库无调用者），所以走的是 `rtSpread.activePriceTema` 兜底 ——
> 这个值来自 dbp 推送。**行情没到之前，`maxVolume` 恒为 0，算法单建不出来。**

## 6. 分阶段跑通全流程

### 阶段 0：预热（约 30 分钟，必须等 —— **但只在冷启动等一次**）

`spreadStatsMinSamples = 8640`，`spreadSampleIntervalMs = 200`
→ 攒够样本至少要 `8640 × 0.2s = 1728s ≈ 29 分钟`。
在此之前 `largeStats.IsValid() == false`，`RecalcOrderParams` **直接 return**，
`maxVolume` 也是 0 —— **什么都不会发生，这是正常的，不要以为坏了。**

观察点：`PairInfoManager::UpdateLargeStats` 之后 `largeStats.valid == true`。

> **重启不用再等**：这一轮算出来的分位数会落到 `data/spread_stats.csv`，
> 重启时够新（默认 1h 内）就直接顶上，日志打
> `重启免预热: pairKey:… 已恢复价差统计（样本数:… 统计时刻:…）-> 无需等待预热即可报单`。
> 只有首次启动、快照过期、或列数不兼容时才走完整预热。见 §3.2.1。
> 想强制走一次完整预热来验证：把 `spreadStatsMaxStaleSec` 设成 `0` 再启动。

### 阶段 1：开仓

前置：行情新鲜（`generateTs` 在 30s 内）、`spreadEffective = true`、
两腿账户都有余额（`FundVerify` 通过）、`|fundingRate| ≤ 0.002`。

触发：`spreadAskAsk < askAskDQ × 0.8`（开多）或 `spreadBidBid > bidBidUQ × 0.8`（开空）。

观察点：
- 日志出现 `SubmitAlgoOrder` / `报单:` 行；
- `AlgoContext allAlgoOrders size` 从 0 变 1；
- **主动腿先报出去**（BINANCE），成交后**立刻补报被动腿**（GATEIO）。

### 阶段 2：超时撤单（两层，别混淆）

| 层 | 判据 | 默认值 | 代码 |
|---|---|---|---|
| **子单级** | 主动腿 Taker 挂太久 / Maker 价格偏离 | `activeTakerCancelOrderTime = activeMakerCancelOrderTime = 5e6 µs = 5s`；`*CancelOrderPct = 0.001` | `BuildAlgoOrderJson` 固定参数块 → `BaseAlgoOrder::CancelOrderOnSpread` |
| **算法单级** | **机会连续不成立**的时长（不是订单年龄！） | `algoOrderTimeoutMs = 150000` = 150s | `PairTradingContext::CheckAlgoOrderTimeout` |

算法单级的语义容易看错：`UpdateSatisfyTime` 每 tick 刷新 `satisfyTime`，
只有**连续 150 秒**机会条件都不成立才撤。所以要主动验证这一条，
得让价差**持续回到中性**（比如手动把两腿报价拉平 / 断开一腿行情）。

观察点：算法单 → `ALGO_OS_CANCELLING` → 主动腿被撤 → 子单清零 → `ALGO_OS_CANCELED`。

#### 为什么"设了 150s，实际十几分钟才撤"

不是计时器坏了，是**计时器的输入被信号续命**。链路：

1. 算法单占着对子时 `ProcessPairSignal` 在 `hasActiveAlgoOrder` 处早退，**不会报新单**；
   但 `UpdateSatisfyTime` 在那句早退**之前**（`PairTradingContext.cpp:364` vs `:366`），每个行情 tick 都跑。
2. 它的判据是 `canOpen && 有开仓信号` 或 `canClose && 有平仓信号`，而
   `HasOpenSignal` / `HasCloseSignal` 是**对子级**的 —— 4 个开仓方向里任一成立就算"开仓机会成立"，
   4 个平仓方向同理（`||`，与在跑的是哪个方向无关）。
3. "价差还在阈值外"既是算法单被创建的原因，也是它一直不成交的原因
   ⇒ **信号成立 ⇒ satisfyTime 刷新 ⇒ idle 永远 < 150s ⇒ 永不超时**。
4. 要等价差回到阈值内、信号消失，`satisfyTime` 才停表，再跑满 150s 才撤。

**所以实际撤单时刻 ≈ 价差回到阈值内的时间 + 150s**，与"这单活了多久"无关。

最容易踩的组合是"报不出子单 + 信号仍成立"：

| 报不出子单的原因 | 日志关键字 | 会不会让信号消失 |
|---|---|---|
| 行情 / 深度 / 成交延迟 | `OnSpread depth delay >` / `OnSpread depth tradesdelay` | **不会**（`openOrderFlag=false` 只挡报单，`AlgoContext.cpp:438/466`） |
| 目标价差偏离 | `TargetSpreadStop MAKERTAKER ... mtSpreadFlag:true` | 不会 |
| MT 滑点 | `mtSlipageFlag` | 不会 |

这三条都在**执行端**，策略层的 `satisfyTime` 看不到它们 ⇒ 一个不干活的算法单能把对子占住
十几分钟到几小时。而 `BaseAlgoOrder::insertTime` 虽然存在，**全仓库没有消费者**
（只有 `PairTradingContext.cpp:859` / `AlgoContext.cpp:247` 两处赋值）⇒ 连"订单年龄"兜底也没有。

**这是设计意图，不是缺陷（2026-10 已确认，不要再提修改）**：算法单的生命周期由
"开平仓条件是否成立"决定，不由"这单活了多久"决定。条件成立就一直报，执行端因为延时 /
滑点没成交就继续报，**不该撤**；只有条件不成立（价差回到阈值内）才停表、再满 150s 撤。
理由：撤掉重报在条件仍然成立时只会把排队位置和 maker 收益丢掉，并且多打一次撤单/报单。

代码里本来就写着这层意思 —— `PairTradingContext.cpp:354-361` 的注释：这里**必须**用
`CheckSignalForSatisfy`（不看 `hasActiveAlgoOrder` 的那版）且**不能**早退，否则
"`satisfyTime` 永远刷不到 ⇒ 每一个算法单都在 150s 后被撤掉（包括刚发出去的风控强平单）"。
也就是说"在有单在跑时仍然刷新 `satisfyTime`"是**刻意**的，不是漏判。

因此下面这些"修复"已被否决：

| 曾被提的方案 | 为什么不要 |
|---|---|
| 加算法单年龄兜底（读 `insertTime`，超时即撤） | 与上面语义冲突：会撤掉一个机会仍在、只是暂时报不出的单 |
| `satisfyTime` 改成"本 tick 真的报出子单/有成交才刷新" | 把执行端延迟错误地升格为策略层判据；行情抖动会误撤 |
| 执行端延迟时主动让策略层感知并撤单 | 需要新通道/新状态，成本远大于收益 |

要接受的残留风险只有一条：**若某个对子的条件长期成立、而执行端长期报不出子单
（`TargetSpreadStop` / `mtSlipageFlag` / 深度延迟持续），该对子会被一直占住**，
`ProcessPairSignal` 在 `hasActiveAlgoOrder` 处早退，不会再报新单。这是有意的取舍
（占住的是同一个已经想做的机会），排查时按下面的关键字定位，不要去动超时逻辑。

**现场怎么判**：

- 搜 `CheckAlgoOrderTimeout` —— 有这行才是正常超时撤单，`idleSec` 直接给出当时 idle 多大；
- 搜 `SubmitAlgoOrder(MODIFY)` —— 每 `modifyTimespanSec`（默认 60s）一条。它**只**刷新
  `algoModifyTime`（`ProcessModify:757`）并覆盖算法单参数（`AlgoContext.cpp:168-233`），
  **不碰 `satisfyTime`** —— 不是它把计时重置了，它只是"这单还活着"的证据；
- 搜 `OnSpread depth delay` / `TargetSpreadStop` / `mtSlipageFlag` —— 报不出子单的真实原因。

结论：**不需要改代码**。看到十几分钟才撤，先按上面三条关键字确认是"信号仍在续命"
（正常）还是"信号已消失但没撤"（那才是 bug，查 `CheckAlgoOrderTimeout` 有没有打日志）。

### 阶段 3：风控平仓

`RiskManager::CheckRisk` 的顺序是 `CheckTinyClose` → `CheckADLRisk` →
`CheckSpreadNoRegression` → `CheckFundingAbnormal`，命中后走**渐进式让利平仓**三档：

| 档 | 让利（绝对价差） | 等待 |
|---|---|---|
| t1 | `tier1ForgoProfit = 2e-5` | `tier1WaitUs = 30min` |
| t2 | `tier2ForgoProfit = 5e-5` | `tier1WaitUs + tier2WaitUs`（+60min） |
| t3 | `tier3ForgoProfit = 1e-4` | 之后持续以 t3 重试 |

各条风控的触发条件：

| 风控 | 条件 | 默认门槛 |
|---|---|---|
| 碎单 `CheckTinyClose` | 有持仓且 `\|pairTotalVolume × 腿价 × multiple\|` | `< 25 USDT` |
| ADL | 持仓超阈值且 ADL 分位高，持续 | `> 2000 USDT` + rank `> 0.8` + 持续 4 天 |
| 价差不回归 | 持满最短持有期后连续未回归 | 持有 `> 1h` 且未回归 `> 24h` |
| 资金费率异常 | 下一结算期资金费亏损 | `> 30 USDT` |

> **最容易复现的是碎单**：把 `targetAmount` 设成很小（例如 5 USDT），
> 建仓后市值就 < 25 USDT → 立刻命中碎单风控 → 走撤单/强平流程。
> 这是联调风控链路最快的路径。
>
> ⚠️ `fundingAbnormalUsdt = 30` 是按祖先 `max_amount = 30000` 标定的，
> 本工程 `maxAmount = 1000` 时，要亏到 30 USDT 需要两腿费率差约 3%（很极端），
> 所以这条实际上**很难触发**。

### 阶段 4：正常平仓

`ttCLSwitch` / `ttCSSwitch` / `mtCLSwitch` / `mtCSSwitch` **恒为 true**
（`RecalcOrderParams:129-130`），不需要开关。触发条件是价差**回归**：

```
多头：spreadAskBid − F_tt > ttCLStartSpread   或  spreadBidBid − F_mt > mtCLStartSpread
空头：spreadBidAsk + F_tt < ttCSStartSpread   或  spreadAskAsk + F_mt < mtCSStartSpread
```

其中 `ttCLStartSpread = askBidUQ × 0.8 + F_tt + profitPct`（`profitPct = 0.0001`）。
也就是说：**开仓点比 0.8 倍分位数更极端，平仓点比 0.8 倍分位数略保守一点，
两者之差就是 `profitPct` 这点利润。**

验证方法：开仓后把价差拉回中性并穿过阈值，观察算法单以 `ALGO_OS_FILLED` 终结。

### 路线 C：只为"把流程跑通"的冒烟测试

|---|---|---|---|

| `maxAmount` / `targetAmount` | `config.json` | `20` | **必须调小**，冒烟不承担真实敞口 |

计算器里可以直接看到每个值的效果：

```bash

```

> ⚠️ 冒烟参数会让每轮往返净亏约 7–9 bp。**验证完必须改回来**，
> 且不要用这套参数跑真实资金。

### 有算法单、但一直没有子单（报单）

这是最常见的"看起来卡住了"。建单（策略层）和报子单（执行层）用的是**两套有效性判据**：

| 层 | 判据 | 代码 | 宽松程度 |
|---|---|---|---|
| 策略层建单 | `rtSpread.valid` | `PairInfoManager.cpp:677` **无条件置 true**，只要收到过一条价差就永远有效 | 极宽 |
| 执行层报单 | `pdata->spreadEffective` | `dbsnap.h:288-300`：两腿深度时间戳差 ≤ `activeCheckspan`（默认 500ms）**且**最新腿在 checkspan 内 | 严 |

⇒ 行情稍微不同步（薄对子、某家所深度推送慢），策略照样建单，执行端一律不报，
**而且那行 `if` 没有 else，日志里一个字都没有**。这就是 `docs/盈利能力优化建议.md:97`
说的"虚假候选"，也是 `docs/modification_plan.md` Step 5 留的口子（`rt.valid` 还没接 `spreadEffective`）。

从"算法单已存在"到"子单发出去"，一共 10 道闸门，**其中 6 道完全静默**：

| # | 闸门 | 位置 | 失败时能看到什么 |
|---|---|---|---|
| 1 | 状态必须是 `NEW`/`PARTFILLED` | `AlgoContext.cpp:462` | 无 |
| 2 | `openOrderFlag` = 行情延迟 && 深度延迟 && 成交延迟 | `:438` | ✅ `OnSpread delay >` / `depth delay >` / `depth tradesdelay`（每 tick 刷） |
| 3 | `pdata->spreadEffective` | `:470` | **无** ← 头号嫌疑 |
| 4 | `systemDelayFlag` / `exchangeDelayFlag`（粘性，5 分钟重置） | `:470`、置位在 `:1123/:1136` | 只在置位那一下发 Lark |
| 5 | `mtSlipageFlag` / `mtSpreadFlag`（粘性） | `:472` | 新单不可能有（只在 pairOrder 有被动成交后才置位） |
| 6 | `tradingTypeOrder` 必须正好是 `MAKER_TAKER` 或 `TAKER_TAKER` | `:472` / `:560` | 无（两个分支都不进 = 永不报单） |
| 7 | `LimitManager::PassLimit`（每秒单数限流） | `:478` | 无 |
| 8 | `CreatePairOrder` 要求 `\|expectVolume\| >= minVolume` | `AlgoPairOrder.cpp:645-720` | ✅ `tradingType:… expectVolume:… minVolume:…`（`:649`，每次尝试都打） |
| 9 | `CreateActiveOrder` 返回 `strategyOrderId > 0` | `AlgoContext.cpp:486` | 无 |
| 10 | `AccountManager::FundVerify` | `:489` | 只有 Lark `FundVerify failed`，**没有 LOG** |

**排查顺序**（3 分钟）：

1. 日志搜 `OnSpread depth delay` / `tradesdelay` —— 刷屏 ⇒ 闸门 2。
2. 日志搜 `expectVolume:` —— 有这行说明前面 7 道全过了，看 `expectVolume` 是不是小于 `minVolume`（报单量太小，闸门 8）。
3. 以上都没有 ⇒ 卡在闸门 3：直接看 dbp 快照 JSON 的 `spef` 字段
   （`dbpsnapshot.cpp:99` 把 `spreadEffective` 写成 `spef`），一直是 0 就是它。
4. Lark 里翻 `FundVerify failed` ⇒ 闸门 10（保证金 / 单笔名义额不够）。

**要么调 `activeCheckspan`，要么按 Step 5 把 `rt.valid` 接上 `spreadEffective`**
（后者会让策略层**少建单**，正好消掉"有单不报"的虚假候选）。
最小止血：给 `AlgoContext.cpp:470` 那个 `if` 加一个节流日志，否则这条链永远是黑的。
| 13 | 分位数已经算出来了，开仓却还是不发单 | `orderParams` 的 16 个 `*StartVolume/*EndVolume` 取自 `pi.maxVolume`，与分位数是**两个独立输入**。`maxVolume` 要等腿价（第一条行情）才有效；没跟上就是 `ttOLEndVolume = 0`，开仓判据 `vol > ttOLEndVolume + 1e-9` 退化成 `0 > 1e-9`，**恒不成立**。修法见 §3.2.3；回归用例 `market_to_algo` **G20** |
