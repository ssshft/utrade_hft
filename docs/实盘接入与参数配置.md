# 实盘接入与参数配置（DOGE-USDT 配对）

> 目标：把 `BINANCE.USDT_SWAP.DOGE-USDT|GATEIO.USDT_SWAP.DOGE-USDT` 接到真实行情 + 真实交易上跑通
> **开仓 → 超时撤单 → 风控平仓 → 正常平仓** 整条链。
>
> 配套工具：`tests/param_calc/`（链接**真实的** `SignalGenerator.cpp` 算阈值，不要靠手推）。

---

## 0. 结论速览（先看这段）

**「价差 0.0002」这个数必须先确认口径，两种理解的结论完全相反：**

| 你看的是 | 换算成策略用的相对价差 | 能不能开仓（默认参数） |
|---|---|---|
| dbp 里的 `spreadAskAsk` 字段本身 = 0.0002 | **2.0 bp** | **❌ 开不了**。需要 ±11.25 bp |
| 两腿价格之差 = 0.0002 USDT（DOGE≈0.0937） | **21.3 bp** | **✅ 能开**，默认参数就够 |

原因是**执行成本比价差还大**：

```
F_mt（主动腿挂单 + 被动腿吃单 + 滑点）= 0.0002 + 0.0006 + 0.0001 = 0.0009 = 9.0 bp
F_tt（两腿都吃单 + 滑点）              = 0.0006 + 0.0006 + 0.0001 = 0.0013 = 13.0 bp
```

开仓开关的判据是 `StartSpread = 分位数 × 0.8 − direction × F`，而开关要求 `StartSpread` 穿过 0，
所以**分位数必须达到 F/0.8**：

```
开多(MT) 需要 askAskDQ < −11.25 bp
开空(MT) 需要 bidBidUQ > +11.25 bp
开多(TT) 需要 bidAskDQ < −12.50 bp
开空(TT) 需要 askBidUQ > +12.50 bp
```

DOGE ≈ 0.0937 时，**11.25 bp ≈ 0.000105 USDT**。所以：
- 绝对价差 0.0002 USDT → 21.3 bp → **是门槛的 1.9 倍，能开**；
- 相对价差 0.0002（= 2 bp）→ **只有门槛的 18%，开不了**。

**怎么确认**：`PairTradingStrategy::on_dbpdata`（`PairTradingStrategy.cpp:126`）会把
**四条价格**打到 stdout（`activeAsk activeBid passiveAsk passiveBid`），不是价差。
如果你是从这行输出里自己减出来的，那就是绝对价差 → **21.3 bp，能开**。
如果你是从 `dbp` 共享内存 / 别处的 `spreadAskAsk` 字段读的，那就是相对价差 → 2 bp。

用计算器立刻验证：

```bash
cd utrade_hft/tests/param_calc
./run.sh band 0 0.00213     # 相对 ±21.3bp -> 四个开仓开关全开
./run.sh band 0.0002 0.0002 # 相对 0.0002 上下 -> 四个开仓开关全关
```

## 1. 价差口径（一切数字的前提）

### 1.1 四个轴的定义

价差**不是本工程算的**，是 `dbp` 进程算好写进共享内存的。公式在
`dbp/dbprocess/dbsnap.h:303-306`：

```cpp
spreadBidAsk = calcspread(activeBidPrice[0], passiveAskPrice[0]);
spreadBidBid = calcspread(activeBidPrice[0], passiveBidPrice[0]);
spreadAskBid = calcspread(activeAskPrice[0], passiveBidPrice[0]);
spreadAskAsk = calcspread(activeAskPrice[0], passiveAskPrice[0]);
```

而 `calcspread`（`dbsnap.h:230-238`）按 `spreadCalcType` 分支：

```cpp
SPCT_PRICEDIV1 = 0  ->  (d1 - d2) / d1
SPCT_PRICEDIV2 = 1  ->  (d2 - d1) / d1
SPCT_PRICESUB1 = 2  ->  d1 - d2
SPCT_PRICESUB2 = 3  ->  d2 - d1
```

**`dbp/etc/dbprocess.xml` 里 `spreadcalctype = 1`** → `SPCT_PRICEDIV2` → `(d2 − d1)/d1`。
（注意 `dbp/etc/dbprocess.json` 写的是 0，但**代码读的是 `dbprocess.xml`** ——
`dbpinitialer.cpp:28` 硬编码 `auto filename = "dbprocess.xml"`。两份配置不一致，以 xml 为准。）

`active` / `passive` 来自 `pairlist.xml` 里 `<name>` 按 `|` 切分的左右两半
（`dbpserver.cpp:306-307`：`result[0]` → active，`result[1]` → passive）。
`utrade_hft/etc/config.json` 的 `pairKeys` 是 `BINANCE...|GATEIO...`，所以：

```
active  = BINANCE.USDT_SWAP.DOGE-USDT
passive = GATEIO.USDT_SWAP.DOGE-USDT

spreadBidAsk = (GATEIO_ask − BINANCE_bid) / BINANCE_bid
spreadBidBid = (GATEIO_bid − BINANCE_bid) / BINANCE_bid
spreadAskBid = (GATEIO_bid − BINANCE_ask) / BINANCE_ask
spreadAskAsk = (GATEIO_ask − BINANCE_ask) / BINANCE_ask
```

**四个都是无量纲的相对价差，正 = GATEIO 比 BINANCE 贵。**

### 1.2 方向怎么读

`OPEN_LONG` 的腿约定是**主动腿卖、被动腿买**（`AlgoPairOrder.cpp:408-430`：
`tradingTypeOffset == OPEN_LONG` 分支里 `activeDirection = DT_SHORT; passiveDirection = DT_LONG;`），
也就是"卖 BINANCE + 买 GATEIO"。
要赚钱就得 **GATEIO 便宜**，即 `spread` 为**负**。

这和开关判据一致：`canOpenLong = mtOLStartSpread < 0`，而
`mtOLStartSpread = askAskDQ × 0.8 + F_mt`，只有 `askAskDQ` 足够负才成立。

所以：
- `spread` 很负 → 开多（卖 BINANCE / 买 GATEIO）
- `spread` 很正 → 开空（买 BINANCE / 卖 GATEIO）

## 2. 参数是怎么算出来的

`SignalGenerator::RecalcOrderParams`（`SignalGenerator.cpp:24-146`）在每个统计刷新周期
（默认 60s）跑一次，从**分位数**推导全部阈值：

```
CalcExpectSpread(qb, isTT, direction):
    execCost = CalcExecCost(isTT)
    buffer   = isTT ? ttAddPercent : 0
    startSpread = qb × spreadAdjPct − direction × (execCost − buffer)
    endSpread   = startSpread + direction × 5e-6
```

代入四个开仓方向（`direction`：开多 = −1，开空 = +1）：

| 方向 | 分位数来源 | StartSpread | 开关判据 |
|---|---|---|---|
| `ttOL` 开多 | `bidAskDQ` | `bidAskDQ × 0.8 + 0.0010` | `< −minSpreadTarget` |
| `mtOL` 开多 | `askAskDQ` | `askAskDQ × 0.8 + 0.0009` | `< −minSpreadTarget` |
| `ttOS` 开空 | `askBidUQ` | `askBidUQ × 0.8 − 0.0010` | `> +minSpreadTarget` |
| `mtOS` 开空 | `bidBidUQ` | `bidBidUQ × 0.8 − 0.0009` | `> +minSpreadTarget` |

（TT 的 0.0010 = `F_tt − ttAddPercent` = 0.0013 − 0.0003；MT 无缓冲 = `F_mt`。）

另外两个前置门槛：

- **`minSpreadSpan = 0.0002`**：`spreadSpan = bidBidUQ − askAskDQ` 低于它，
  `RecalcOrderParams` **直接关掉全部四个开仓开关并 return**（`SignalGenerator.cpp:32-37`）。
- **`openMaxFundingRate = 0.002`**：任一腿资金费率绝对值超过它，四个开仓开关也全关。

而**实际触发**（`CheckSignal`，`SignalGenerator.cpp:179-217`）时成本会精确抵消：

```
mtOL: spreadAskAsk + F_mt < mtOLStartSpread  ⟺  spreadAskAsk < askAskDQ × 0.8
mtOS: spreadBidBid − F_mt > mtOSStartSpread  ⟺  spreadBidBid > bidBidUQ × 0.8
```

即"当前价差走到自己分位数的 0.8 倍之外"就报单。**成本门槛只在开关那里起作用。**

## 3. 参数放在哪、怎么改

**参数已经全部配置化**（2026-10-01）。`utrade_hft/etc/config.json` 的 `op` 段下有三份子对象，
覆盖了原来散落在两个头文件里的编译期常量、以及 `BuildAlgoOrderJson` 里那一大段硬编码：

```
op.feeSlippage  ->  m_ptCfg.feeSlippage (pt::FeeSlippageConfig)  12 个字段  执行成本 / 滑点 / 价差阈值
op.risk         ->  m_ptCfg.risk        (pt::RiskConfig)         14 个字段  风控门槛 + 渐进式平仓三档
op.pairTrading  ->  m_ptCfg             (pt::PairTradingConfig)  55 个字段  策略参数(18) + 分位数快照(2) + 算法单参数(35)
                                                                ─────────
                                                                 81 个字段
```

前两个是 `PairTradingConfig` 的成员（`feeSlippage` / `risk`）—— `SignalGenerator` 与
`RiskManager` 是跨组件使用的单例，各自必须持有一份自己的配置副本；放在
`PairTradingConfig` 里是为了让"本次启动实际生效的全部参数"集中在一处，便于日志核对。
`pre_start` 解析完这两段之后会调 `SetConfig` 推给这两个单例。

**算法单参数没有独立结构体**（2026-10-02 去掉了 `pt::AlgoOrderConfig`）：报单类型 /
撤单门槛 / rebalance 这些就是 `PairTradingConfig` 的普通字段，和策略参数一起放在
`op.pairTrading` 段，由 `BuildAlgoOrderJson` 直接读，不用推送。

另有 **7 个 key 平铺**在 `op` 段（不在子对象里，因为读法带副作用，由 `pre_start` 直接读）：
`pairKeys` / `activeAccountId` / `passiveAccountId` / `maxPositionValue` / `maxAmount` /
`targetAmount` / `csvStatePath`。

**解析就在 `pre_start` 里，逐字段读，没有中间层**：每个 key 都是

```cpp
if (s.HasMember("activeMakerFeeRate")) c.activeMakerFeeRate = std::stod(s["activeMakerFeeRate"].GetString());
```

数值一律 `Value.GetString()` 再交给 `std::stod` / `std::stoll` / `std::stoi`
（`config.json` 用 `kParseNumbersAsStringsFlag` 解析，数值读出来都是字符串）；
布尔字段没有对应的 std 函数，直接和 `"true"` 比字符串。

改配置**不需要重新编译**。启动时 `pre_start` 会打六行 `配置生效[…]`，
打的是**解析之后**的实际值（不是文件里的原文），可直接核对。

#### 3.2.1 `spreadStatsStatePath` / `spreadStatsMaxStaleSec` —— 重启免预热

**问题**：`SpreadStatsBuilder` 要先在内存里攒够 `spreadStatsMinSamples` 个样本、
算出价差上下分位数，`SignalGenerator::RecalcOrderParams` 才有东西可算 ——
在那之前它直接 `return`，`orderParams` 全是默认值，**一单都发不出去**。
生产参数下这段"哑火期"是分钟级，每次重启都要重付一遍。

**做法**：把算好的分位数单独落一份盘（`data/spread_stats.csv`，12 列），
重启时够新就直接顶上，不必再等预热。

```
                        ┌── 每个 spreadStatsUpdateIntervalSec（60s）──┐
OnTimer ─► Prune(24h) ─► Build(qUp,qDn,minSamples) ─► UpdateLargeStats ─► RecalcOrderParams
                                                                              │
                                                        SaveSpreadStats ◄─────┘  顺手落盘
Init ─► LoadSnapshot ─► LoadSpreadStats ─► 对每个对子 RecalcOrderParams
         （账本）         （分位数）        ← 必须重算，否则阈值仍是默认值
```

几个要点：

- **新鲜度按样本时间算**（`calcTs`，取自 dbp 的 `generateTs`，不是墙钟）。
  停牌 / 断档时它不前进，所以一条判据同时挡住"进程停了很久"和"行情本身就停了很久"。
  超过 `spreadStatsMaxStaleSec` 就**不恢复**、回退到正常预热，日志打
  `统计已过期 …s > …s -> 不恢复，正常预热`。
- **一个有效统计都没有时不写盘**（预热期每轮都会走到这里，无脑 truncate 会把
  上一份好值刷成空表头，"重启顶上"就永远生效不了）。
- **单独一个文件，不动 `pair_info.csv` 的 33 列格式**：分位数是派生字段，
  两个文件的恢复语义不同（这本账丢了只是回到旧行为；`pair_info.csv` 丢了是丢账）。
- 路径留空、或 `spreadStatsMaxStaleSec <= 0`、或列数不兼容 → 都等于关掉这个功能，
  回到改动前的行为（重新攒样本）。**最坏情况就是多预热一次**，没有正确性风险。

#### 3.2.2 为什么不直接存 `orderParams`

开平仓判据（`SignalGenerator::CheckSignalForSatisfy`）读的确实是 `pi.orderParams`，
所以"把 `orderParams` 存下来、重启直接灌回去"看起来更直接。但它比存分位数差，原因有三条：

**① `orderParams` 不是一个输入，是一个"用当前配置算出来的结果"。**
存结果 = 存一份**用旧配置算出来的缓存**。重启后配置一变，这份缓存就和现场不一致，
而且是**静默**不一致 —— 没有任何东西会发现它错了。

`RecalcOrderParams` 用的是 `startSpread = Q × spreadAdjPct − dir × (execCost − buffer)`，
而 `CheckSignalForSatisfy` 判的是 `spread + execCost < startSpread` ——
两者**同源**，`execCost` 精确抵消，最终入口条件就是 `spread < Q × spreadAdjPct − buffer`，
**与费率无关**（这是刻意的设计）。一旦 `orderParams` 被跨配置恢复，这个抵消就断了：

| | 存的时候费率 | 恢复后费率 | 实际入口 |
|---|---|---|---|
| 设计意图 | 任意 | 任意 | `spread < Q×0.8 − buffer` |
| 存 `orderParams` | `0`（冒烟值） | `0.0013`（生产值） | `spread < Q×0.8 − buffer − 0.0013` → **紧了 13 bp** |
| 存 `largeStats` | — | — | `spread < Q×0.8 − buffer` ✓ |

⚠️ 这不是假想：**仓库现在五个费率全是 `0`，实盘前必须填回真值**（见 §9）。
按"存 `orderParams`"的做法，那次改动会在**重启之后被悄悄吃掉**。

**② 一半的 `orderParams` 根本不是分位数的函数。**

| 字段 | 真正的来源 | 重启时 |
|---|---|---|
| 16 个 `*StartSpread` / `*EndSpread` | `largeStats` 的分位数 + 配置 | 分位数可恢复 |
| 16 个 `*StartVolume` / `*EndVolume` | `pi.maxVolume`（由腿价算出） | **要等第一条行情**，恢复不了 |
| 8 个 `*Switch` | `autoFlag` / `closeFlag` / 资金费率 / 流动性 / 保证金状态 | 部分是实时状态，**不该恢复** |
| 4 个 `*CL` / `*CS` 的 Start | 还叠了 `profitSwitch` / `profitPct` | 运维意图，另有快照管 |

存 `orderParams` 就得连"当时的腿价、当时的资金费率、当时的流动性状态"一起存，
重启后把这些**过期的现场**灌回去 —— 那是把一个缓存当成了事实。

**③ 没有新鲜度锚点。** 分位数有 `calcTs`（行情时间），可以判"这份统计还作不作数"。
`orderParams` 只有墙钟可锚，而墙钟判不出"行情本身停了"。

**结论**：存**输入**（分位数），重启时用**当前配置**重算一遍。多一次函数调用，换来自洽。

#### 3.2.3 一个被这个功能暴露出来的耦合 bug

`RecalcOrderParams` 原来把"分位数"和"`maxVolume`"两个**互相独立**的输入
耦合在同一个 `if (!ls.IsValid()) return;` 后面，于是：

```
重启恢复分位数 → Init 里算一次 orderParams，但那一刻腿价还没有 → maxVolume = 0
              → ttOLEndVolume = 0 → 开仓判据 `vol > ttOLEndVolume + 1e-9` 退化成 `0 > 1e-9`
              → 一单都开不出去
下一轮统计刷新 → 窗口刚重启、样本不够 → largeStats 被刷成无效 → 早退一挡
              → 量字段永远停在 0，直到窗口重新预热完 ≈ 29 min → **等于一天没省**
```

修法是把量字段移到早退**之前**（它们本来就只依赖 `maxVolume`），
并在 `OnTimer` 的量重算之后补一次 `RecalcOrderParams`：

```cpp
// SignalGenerator::RecalcOrderParams —— 量字段与分位数解耦
{ const double mv = pi.maxVolume;
  op.ttOLStartVolume = 0.0;   op.ttOLEndVolume = -mv;   ... }
if (!ls.IsValid()) { return; }        // 只有"价差类"字段才需要分位数
```

```cpp
// PairTradingContext::OnTimer —— 量一变就重算（orderParams 的量字段取自 maxVolume）
pim.RecalcVolumeParams(...);
for (PairInfo* pi : pim.GetAllPairInfos()) { sg.RecalcOrderParams(*pi); }
```

这个耦合在加恢复功能之前**一直存在**，只是被"冷启动本来就要等 29 min"掩盖了：
冷启动时 `largeStats` 无效，早退挡着，谁也看不出量字段没跟上。

回归用例 **G20** 钉住这件事 —— 它断言的是"单真的报出去了"（`fx.N() > 0`），
不是"某个字段有值"。只断言 `ttOLStartSpread` 的话，上面那个 bug 照样全绿。

### 3.5 语义约定（改配置前先看这段）

解析就是 `pre_start` 里的 `if (s.HasMember("x")) 字段 = std::stod(s["x"].GetString());`，所以：

| 约定 | 说明 |
|---|---|
| **只覆盖、不清零** | 配置里**少写一个 key** 等价于"保持代码里的默认值"，不会变成 0 —— 因为赋值只在 `HasMember` 成立时发生。所以可以只写想调的那几个 |
| **值写错 → 启动直接失败** | 数值字段走 `std::stod` / `std::stoll` / `std::stoi`，解析不出来会抛 `std::invalid_argument` / `std::out_of_range`，`pre_start` 不接 —— 配置写错就该在启动时炸，别带着一个"看起来对"的值跑起来。这也和原有那 7 个平铺 key 的行为一致 |
| **布尔必须写带引号的 `"true"` / `"false"`** | 取值是 `s["x"].GetString() == "true"`。**写成裸 `true` 会挂进程**：`kParseNumbersAsStringsFlag` 不影响布尔，裸 `true` 是原生 bool，对它调 `GetString()` 触发 `RAPIDJSON_ASSERT(IsString())` —— 断言失败不是异常。除 `"true"` 之外的一切（含 `"1"` / `"yes"`）都当 false |
| **枚举必须显式拒绝哨兵** | `OrderType` 用 `OrderTypeStr2EnumMap.find()`（**不能用 `operator[]`** —— key 不存在时它会插入 `OT_MIN`），并且显式拒掉 `OT_MIN`；`targetSpreadType` / `activeVolumeCalcualteType` 用 if/else 只认真值。哨兵配上去会被当成合法值用下去 |
| **单位** | 时间字段带单位后缀：`*Sec`（风控）与 `*Ms`（算法单撤单）写秒 / 毫秒，结构体内部仍是微秒。风控的 `*Sec` 在 `pre_start` 里 ×1000000；算法单的 `*Ms` 在 `BuildAlgoOrderJson` 里 ×1000（**只在这一处**换算） |
| **数值字符串与原生数字都认** | `config.json` 用 `kParseNumbersAsStringsFlag` 解析，所以 `"1000"` 与 `1000` 读出来都是字符串。现有文件统一用字符串，照着写即可 |

### 4.4 `tb/etc/trade_config.json` —— 只有 BINANCE，而且指向 demo

```
https://demo-api.binance.com        ← Binance 的 demo/testnet，不是主网
wss://demo-stream.binance.com/ws
```

也就是说：

| 缺什么 | 后果 |
|---|---|
| 没有 GATEIO 账户（10001） | **被动腿根本报不出去**。`tb/include/Gateio/GateioTradeClient.h` 的代码在，但配置里没有它的 `apiKey`/`secretKey`，`mTradeClient` 找不到 `GATEIO.{strategyId}` 这条路由 |

## 5. 目标开仓量怎么设

`config.json` 里三个量（单位都是 **USDT 名义价值**，不是币数）：

```json
"maxPositionValue": "500000",   // 总持仓上限
"maxAmount": "1000",            // 单对子最大报单额
"targetAmount": "1000"          // 单对子目标报单额
```

`PairInfoManager::RecalcVolumeParams`（`PairInfoManager.cpp:572+`）把它们换算成**币数**：

```
a_target = ceil2min(targetAmount / activePrice / multiple, minVolume)
pi.ttTargetVolume = max(a_target, p_target)
pi.maxVolume      = min(a_max, p_max)          // a_max 来自 maxAmount
```

DOGE ≈ 0.0937 时，`targetAmount = 1000` → `1000 / 0.0937 ≈ 10672 DOGE ≈ 1000 USDT`。

**首轮联调强烈建议先调小**，否则第一笔就是 1000 USDT 的名义敞口：

```json
"maxAmount": "20",
"targetAmount": "20"
```

跑通全流程后再放回去。

> 注意 `RecalcVolumeParams` 需要腿价 > 0。K 线统计没接入
> （`UpdateKlineStats` 全仓库无调用者），所以走的是 `rtSpread.activePriceTema` 兜底 ——
> 这个值来自 dbp 推送。**行情没到之前，`maxVolume` 恒为 0，算法单建不出来。**

## 6. 分阶段跑通全流程

### 阶段 0：预热（约 30 分钟，必须等 —— **但只在冷启动等一次**）

`spreadStatsMinSamples = 8640`，`spreadSampleIntervalMs = 200`
→ 攒够样本至少要 `8640 × 0.2s = 1728s ≈ 29 分钟`。
在此之前 `largeStats.IsValid() == false`，`RecalcOrderParams` **直接 return**，
`maxVolume` 也是 0 —— **什么都不会发生，这是正常的，不要以为坏了。**

观察点：`PairInfoManager::UpdateLargeStats` 之后 `largeStats.valid == true`。

> **重启不用再等**：这一轮算出来的分位数会落到 `data/spread_stats.csv`，
> 重启时够新（默认 1h 内）就直接顶上，日志打
> `重启免预热: pairKey:… 已恢复价差统计（样本数:… 统计时刻:…）-> 无需等待预热即可报单`。
> 只有首次启动、快照过期、或列数不兼容时才走完整预热。见 §3.2.1。
> 想强制走一次完整预热来验证：把 `spreadStatsMaxStaleSec` 设成 `0` 再启动。

### 阶段 1：开仓

前置：行情新鲜（`generateTs` 在 30s 内）、`spreadEffective = true`、
两腿账户都有余额（`FundVerify` 通过）、`|fundingRate| ≤ 0.002`。

触发：`spreadAskAsk < askAskDQ × 0.8`（开多）或 `spreadBidBid > bidBidUQ × 0.8`（开空）。

观察点：
- 日志出现 `SubmitAlgoOrder` / `报单:` 行；
- `AlgoContext allAlgoOrders size` 从 0 变 1；
- **主动腿先报出去**（BINANCE），成交后**立刻补报被动腿**（GATEIO）。

### 阶段 2：超时撤单（两层，别混淆）

| 层 | 判据 | 默认值 | 代码 |
|---|---|---|---|
| **子单级** | 主动腿 Taker 挂太久 / Maker 价格偏离 | `activeTakerCancelOrderTime = activeMakerCancelOrderTime = 5e6 µs = 5s`；`*CancelOrderPct = 0.001` | `BuildAlgoOrderJson` 固定参数块 → `BaseAlgoOrder::CancelOrderOnSpread` |
| **算法单级** | **机会连续不成立**的时长（不是订单年龄！） | `algoOrderTimeoutMs = 150000` = 150s | `PairTradingContext::CheckAlgoOrderTimeout` |

算法单级的语义容易看错：`UpdateSatisfyTime` 每 tick 刷新 `satisfyTime`，
只有**连续 150 秒**机会条件都不成立才撤。所以要主动验证这一条，
得让价差**持续回到中性**（比如手动把两腿报价拉平 / 断开一腿行情）。

观察点：算法单 → `ALGO_OS_CANCELLING` → 主动腿被撤 → 子单清零 → `ALGO_OS_CANCELED`。

### 阶段 3：风控平仓

`RiskManager::CheckRisk` 的顺序是 `CheckTinyClose` → `CheckADLRisk` →
`CheckSpreadNoRegression` → `CheckFundingAbnormal`，命中后走**渐进式让利平仓**三档：

| 档 | 让利（绝对价差） | 等待 |
|---|---|---|
| t1 | `tier1ForgoProfit = 2e-5` | `tier1WaitUs = 30min` |
| t2 | `tier2ForgoProfit = 5e-5` | `tier1WaitUs + tier2WaitUs`（+60min） |
| t3 | `tier3ForgoProfit = 1e-4` | 之后持续以 t3 重试 |

各条风控的触发条件：

| 风控 | 条件 | 默认门槛 |
|---|---|---|
| 碎单 `CheckTinyClose` | 有持仓且 `\|pairTotalVolume × 腿价 × multiple\|` | `< 25 USDT` |
| ADL | 持仓超阈值且 ADL 分位高，持续 | `> 2000 USDT` + rank `> 0.8` + 持续 4 天 |
| 价差不回归 | 持满最短持有期后连续未回归 | 持有 `> 1h` 且未回归 `> 24h` |
| 资金费率异常 | 下一结算期资金费亏损 | `> 30 USDT` |

> **最容易复现的是碎单**：把 `targetAmount` 设成很小（例如 5 USDT），
> 建仓后市值就 < 25 USDT → 立刻命中碎单风控 → 走撤单/强平流程。
> 这是联调风控链路最快的路径。
>
> ⚠️ `fundingAbnormalUsdt = 30` 是按祖先 `max_amount = 30000` 标定的，
> 本工程 `maxAmount = 1000` 时，要亏到 30 USDT 需要两腿费率差约 3%（很极端），
> 所以这条实际上**很难触发**。

### 阶段 4：正常平仓

`ttCLSwitch` / `ttCSSwitch` / `mtCLSwitch` / `mtCSSwitch` **恒为 true**
（`RecalcOrderParams:129-130`），不需要开关。触发条件是价差**回归**：

```
多头：spreadAskBid − F_tt > ttCLStartSpread   或  spreadBidBid − F_mt > mtCLStartSpread
空头：spreadBidAsk + F_tt < ttCSStartSpread   或  spreadAskAsk + F_mt < mtCSStartSpread
```

其中 `ttCLStartSpread = askBidUQ × 0.8 + F_tt + profitPct`（`profitPct = 0.0001`）。
也就是说：**开仓点比 0.8 倍分位数更极端，平仓点比 0.8 倍分位数略保守一点，
两者之差就是 `profitPct` 这点利润。**

验证方法：开仓后把价差拉回中性并穿过阈值，观察算法单以 `ALGO_OS_FILLED` 终结。

## 7. 参数怎么定：三种路线

### 路线 A（推荐）：确认口径后按默认参数跑

如果 0.0002 是**绝对价差** → 21.3 bp > 11.25 bp 门槛 → **默认参数就能开**，什么都不用改，
只改 §4 的配置清单 + §5 把 `targetAmount` 调小。

```bash
cd utrade_hft/tests/param_calc && ./run.sh band 0 0.00213   # 验证：四个开关全开
```

### 路线 B：价差真的只有 2 bp —— 别做这个对子

2 bp 相对价差**无法覆盖 9 bp 的往返成本**，任何"让它能开仓"的参数改动都是让它亏钱。
计算器会直接把缺口算给你看：

```bash
./run.sh band 0.0002 0.0002
#   askAskDQ 实际 +0.000 bp  需要 -11.250 bp  缺口 -11.250 bp
```

要么换一个价差带宽 > 9 bp（MT）/ 13 bp（TT）的对子，要么先把成本真正降下来
（VIP 费率 / maker 返佣 / 调小 `basicSlippage`）。

### 路线 C：只为"把流程跑通"的冒烟测试

如果目的只是验证**链路通不通**（不是验证盈利），可以临时把门槛放松到能让它开仓，
**配合极小的 `targetAmount`（如 20 USDT）**：

| 旋钮 | 位置 | 冒烟值 | 说明 |
|---|---|---|---|
| `minSpreadTarget` | `SignalGenerator.h:37` | `-0.0010` | 判据是 `startSpread < −minSpreadTarget`，设成负数直接放松。±2bp 带宽下两边都能开 |
| `spreadAdjPct` | `SignalGenerator.h:32` | `3.0`（备选） | 放大分位数边界；等价于"愿意在更小的价差上开仓" |
| `maxAmount` / `targetAmount` | `config.json` | `20` | **必须调小**，冒烟不承担真实敞口 |

计算器里可以直接看到每个值的效果：

```bash
./run.sh sweep 0.0002 0.0002
```

> ⚠️ 冒烟参数会让每轮往返净亏约 7–9 bp。**验证完必须改回来**，
> 且不要用这套参数跑真实资金。
