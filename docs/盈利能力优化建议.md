# utrade_hft 跨所同币对价差：算法单创建与执行的增益方案

> 基于当前工作树的静态代码审阅；只修改本分析文档，不改交易源代码、不改配置、不下单。以下是研究与实施建议，**不是已验证的盈利结论**。所有收益、阈值及模型能力都须经真实成交记录和样本外检验。

## 一、先说结论：先排通路，再谈钓鱼与预测

本策略最有价值的增益路径不是先训练复杂模型，而是：**确认交易模式真按信号执行 → 用可成交的双腿净收益决定建单 → 控制第一腿成交后的对冲尾部风险 → 再用短周期预测过滤坏的 maker 成交**。尤其有四处现状会扭曲任何模型评估：

| 优先级 | 核实结果（代码锚点） | 影响及建议 |
|---|---|---|
| P0 | `PairTradingContext.cpp:312-350` 同方向优先 TT 后 MT；但 `BuildAlgoOrderJson():797` 把 `tradingTypeOrder` **固定为 `MAKER_TAKER`**，`802` 仅按 `isTT` 改主动子单类型。`AlgoContext.cpp:484,606` 执行侧又依据该字段分流 MT/TT。 | 选中 TT 信号不等于实际跑 TT 逻辑；可能转入 MT 分支，并搭配 TT 的主动单类型。先用已存在的订单/成交事件按“预期模式→算法类型→子单类型→实际成交”逐一核对，再研究收益。此处是代码可见的不一致，具体影响需以回放证实。 |
| P0 | 自动建单始终 `new AlgoPairOrder()`（`PairTradingContext.cpp:768-769`）。`AlgoFishingOrder` 有实现、执行侧有分支（`AlgoContext.cpp:659`），但未找到自动策略实例化它的入口。 | **钓鱼单并未被当前自动创建链路使用**，不能只调 `fishingSlippagePct` 就当上线了。钓鱼应有独立触发、参数、生命周期与风控；先保持 shadow 模式。 |
| P0 | `AlgoFishingOrder.cpp:9` 默认 `fishingSlippagePct=0`，`:212/253/295/337` 除以该值；当前自动链路未走到此类。 | 这是**未来启用时的潜在数值风险**，不是“线上正在算无穷大”。必须在建单及每次重新报价前校验系数为有限、正值，报价为有限、正值且可按 tick/价格带落地；无效时拒绝钓鱼单，不要静默切成另一类交易。 |
| P0 | `SignalGenerator.cpp:68-70` 统计无效时直接 `return`，没有清除旧 `op.*Switch`/阈值；`PairTradingContext.cpp:1152-1154` 会覆盖旧统计再调用重算。 | 失效窗口可能保留**旧的开仓开关**；设计上应明确“统计过期/不足样本时 fail-closed，已有平仓和风险对冲仍可运行”。测试统计由有效→无效、断流、重启和快照过期四种情况。 |

### 不要把这些参数读错

- `spreadSampleIntervalMs=5000` 只给统计窗口**抽样**；`PairTradingStrategy.cpp:552-554` 对每条 `dbp` 价差更新依次调用执行侧、策略侧的 `OnSpread`，`PairTradingContext.cpp:219-234` 每次尝试信号。**不能说策略每 5 秒才看到一个行情。**统计分位数约每 60 秒刷新（`PairTradingContext.cpp:173-185`）。
- `maxMTOrderSize=maxTTOrderSize=1.0` 是**在途配对单数量上限**（`AlgoContext.cpp:521/606`），不是“每单 1 个 DOGE”；单笔目标量是 `pi.mtTargetVolume/ttTargetVolume`（`PairInfoManager.cpp:807-840` 从 `targetAmount=10` 与合约单位换算），另受盘口、最小下单量和仓位限制。不能靠把并发上限调大来“放大单笔仓位”。
- 配置里 `activeMakerFeeRate=-0.0002` 是**策略假设的主动腿 maker 返佣 2 bp**，其他费率和基础滑点为 0（`etc/config.json:110-122`）。这不是实际成交费率证明，更不能推断“只有 MT 有正期望”；返佣、实际对冲成本及真实费档必须从账单核验。`minSpreadTarget=-0.001` 与 `minSpreadSpan=0` 也只是当前门槛，非盈利证明。
- `spreadStatsMinSamples=5` 是样本下限，并非“运行 25 秒即完成首次分位数计算”：首次构建约在 60 秒刷新时触发；5 个有效样本对 8%/92% 分位不稳，但不应未经回测直接改 720。`SpreadStatsBuilder.cpp:36-46` 用**线性插值**，不是直接取两个极值。
- `smallStats` 虽然在 `PairInfo.h:205` 存在，但当前计算线程只写 `largeStats`（`PairTradingContext.cpp:175-184,1152`）；`RiskManager.cpp:152-154` 也指出 `smallStats` 无生产者。故“现成的 1h/24h 状态比较”**尚不能直接用**，需要另建小窗口生产者。
- 四个 `*Depth*Check` 字段被配置和拷贝（`PairTradingContext.cpp:805-808`），但在当前 `quant_library` 的报单/决策源码内未找到其读取判断；**仅把配置从 false 改 true 不能证明深度闸门会生效**。盘口量对单笔数量的约束是另一套逻辑（`AlgoPairOrder.cpp:238-257`）。

## 二、盈利指标：以“双腿能否兑现”为目标，不以可见价差为目标

在每次候选机会时，对方向 `d`、执行模式 `m`、数量 `q` 估计：

```text
可兑现净边际（bp，按实际名义折算） =
    预测的双腿可成交价差收益（入/平仓两阶段，采用正确 bid/ask 与深度）
  + 预期的实际 maker 返佣 / 资金费现金流
  - 实际 taker 费与主动/被动腿冲击成本
  - 第一腿成交到对冲完成之间的跳价损失
  - 持仓不回归、断流、拒单、对冲失败的尾部风险预算
```

区分**候选、报单、第一腿成交、第二腿对冲完成、最终平仓**五种分母：只看已配对盈利样本会漏掉未成交机会、单腿卡住和强平损失。开多对应主动腿卖/被动腿买（`AlgoFishingOrder.cpp:289-315`）；开空对应主动腿买/被动腿卖（`:203-232`）。净资金费要带方向、分别按每个场所的实际结算事件计算，不能简单把两腿费率差当常数收益。

**最低限度的观测（先离线关联既有下单/回报/盘口记录；缺字段再设计轻量采集）：**

1. 每个候选记录 `pair,方向,决策时刻,两腿盘口/时间戳,统计阈值及有效性,模式,预期净收益,拒绝原因`；每个 `algoId/pairId/orderId` 关联决策、交易所受理、撤改单、成交和对冲完成。不要在逐 tick 热路径同步写盘。
2. 记**成交条件 markout**：以 maker 实际成交时刻与价格为锚，在 +100ms/+1s/+5s/+30s 的*可交易对冲价格*估计双腿净值变化；同时统计第一腿单边暴露持续时间 P50/P95/P99、对冲最终成本与失败率。非成交候选用相同决策时点的反事实报价单独比较，**不能**直接把“未成交单的 markout”当成交样本。
3. 按模式/方向/深度/价差分位/波动率/结算邻近度分桶：候选数→建单率→maker 成交率→成功对冲率→净 bp/每候选→净 bp/每单位风险；再对账实际手续费、资金费、资金占用、强制平仓。

## 三、钓鱼单：等待“短时冲击并回补”，而不是无条件报得更远

### 3.1 建议的建单判据

仅当**方向一致的价差异常**出现，且属于更可能回补的流动性冲击：① 两腿行情都新鲜，② 偏离近端基准/波动单位足够大，③ 领先场所尚未确认同向重定价，④ 被动腿能在限定滑点内对冲，⑤ 实际预期净收益足以覆盖无成交机会成本和单腿风险，才允许挂 fishing。相反，持续单向成交、盘口同时撤量、基差慢速漂移、结算/维护/限流附近，更像信息冲击——不钓或显著缩量。`spread*TEMA` 已通过 `PairInfoManager.cpp:578-584` 进入状态，可先用“价差偏离 TEMA + TEMA 斜率”做**待验证的状态特征**，不是保证回归的标签。

候选报价应离散为 `挂当前最佳价 / 挂离一档 / 不挂而等待 / 立即双腿吃单 / 不交易`；用交易所最小价位、post-only、盘口可见量、预估排队和订单存活时间定价。仅有 BBO 时**无法精确推断自己的真实队列位置**，需要成交/撤单事件与更细盘口或用保守上界。评估式：

```text
EV(挂价,k,T) = P(在T内成交 | 决策态,k)
               × E[全程净PnL | 成交,决策态,k]
               - P(未成交) × 机会占用成本
               - 单腿暴露尾部预算
```

对比 `EV(当前 MT)`、`EV(立即 TT)` 和 `0（不交易）`；同一个“立即吃单”必须重算两腿**实际可用深度**。只在当前已经出现可兑现净价差且立即行动的价值大于等待成本时考虑 maker→taker；**不能**仅因为挂了 T 秒、价差仍极端就无条件追单。

### 3.2 生命周期不可省略

`Candidate → PendingPostOnly → PartialFill/HedgePending → Hedged/Exit → Cancel/Error`：候选未成交要有过期/撤单策略；主动腿每笔部分成交立即按**真实已成交数量**启动被动腿对冲，留好撮合、最小合约数、滑点预算和最坏价格。`AlgoContext.cpp:1171-1197` 已存在回报触发对冲；新策略需要沿用其状态语义。`BaseAlgoOrder.cpp:403-443` 的 CANCELLING 刻意只撤主动腿、保留被动腿等待对冲；现有注释也承认被动腿久不成交可能无上界。上线 fishing 前，先设计**有上限的单腿暴露时间、最大追价和失败时人工/风控处理**，不能用“所有腿一律撤掉”制造裸仓。

**渐进实施**：先记录候选与模拟报价但不报单；再小名义、限定时段 A/B，与现有 MT 比较；只有当每候选净收益扣除风险成本在样本外更优，且单腿敞口指标不过界，才扩大。

## 四、除钓鱼单外的增益方向（按优先度）

| 方向 | 如何接到当前架构 | 何时有用 / 主要陷阱 |
|---|---|---|
| **模式选择器（优先）** | 在 `ProcessPairSignal` 的固定 TT→MT 顺序（`PairTradingContext.cpp:312-350`）前，对当前可执行 MT、TT、fishing 按相同数量、净 bp、成交/对冲概率和风险预算排序；平仓/强平优先保留安全性。 | 如果返佣价值被逆向选择吞没，应 TT 或不交易；不能凭费率静态定赢家。先修/核实 `tradingTypeOrder` 分流不一致。 |
| **对冲腿动态流动性预算** | 用被动腿可见深度、盘口倾斜和价格随数量的冲击，决定主动腿下单量；部分成交按余额/合约乘数配平。 | 比纯提高报单数量更能降低单腿尾部风险。当前被动腿量上限基于 BBO × `passiveVolumePct=0.5`，不足以覆盖多档冲击与最小报单量。 |
| **队列/逆向选择过滤** | 已有两腿 BBO 与 `dbp` 盘口时间戳，可维护短窗口的顶档量变化、mid、spread*TEMA 斜率；按成交后 markout 标定过滤。 | 盘口量变化同时包含撤单、挂单与成交，**不能直接称为 OFI 或净主动成交量**；撤单仍要留足对冲余量。 |
| **资金费事件过滤/持仓调度** | `PairInfoManager.cpp:589-593` 已接两腿费率和 funding 时间字段，`RiskManager.cpp:238-263` 仅做预测亏损超阈值；补实际结算时间/费率事件的校验后，对跨结算仓位按方向计入未来现金流。 | **不是免费且确定赚钱**：当前费率可能改变，两所结算时点与周期不同；不能仅凭 `PairInfo.h:82-83` 的默认 interval=8（未见行情写回）推导真实周期，也不能断言 `fundingTime` 是已结算还是下次结算。先核对行情字段单位与交易所账单。 |
| **预热/阈值稳健性** | 对统计样本量、连续覆盖、最近样本时效设置显式闸门；对 `minSpreadSpan`、`spreadAdjPct`、`minSpreadTarget` 做候选级别的离线扫描。 | 当前 `spreadStatsMinSamples=5`、60s 刷新与 24h 窗口混用，可能导致启动后的分位数波动；过高门槛又会错过机会。`bidBidUQ - askAskDQ` 是**不同价差序列**，不可武断断言永远非负/闸门永远不触发。 |
| **动态仓位与退出** | 对已证实的正边际按可用深度、预估对冲滑点、剩余风险预算限量；在达到利润、资金费变化和回归假设失效时重新评估退出。 | `maxMTOrderSize` 限并发，不管单笔量。现有 `targetAmount=10` 决定基础目标量，先核对合约乘数、最小量、单笔成本与真实成交深度；禁止直接按可见极端价差放大仓位或套 Kelly 公式。 |

### 关于“增加预测能力”：建议预测**成交后的对冲质量**，而不是币价涨跌

1. **第一阶段，非 ML、逐 tick 特征**：两个场所的 BBO 变化顺序、盘口不平衡、价差偏离与短期漂移、价格/盘口时间戳滞后、波动率。分别对 `E[对冲腿未来100ms/1s可成交价]`、`P[maker填单]` 和 `E[填单后markout]` 建很小的分桶/线性模型，先用于“拒绝坏候选/改变挂单距离”，不要直接承担裸方向仓位。逐 tick 价差已到进程，**5 秒抽样限制的是历史统计窗口，不是这个在线特征的更新频率**；高频预测仍受实际链路延迟、跨所时间戳质量制约。
2. **第二阶段，逐笔主动成交失衡**：`dbp` 接收 TRADES（`dbp/dbprocess/dbsnap.h:193-215`），但 `utrade_hft` 的 `AlgoContext::OnMarketTrade()` 目前为空（`AlgoContext.cpp:411-413`），未确认策略进程有独立逐笔成交事件。要做 trade-OFI，先核实交易方向语义、推送频率、时钟、是否真正转发逐笔；若仅有 BBO，则只能做“盘口失衡/报价更新”代理，不要把二者混称。
3. **第三阶段，跨所 lead-lag**：用相同币对两所 mid/可执行价的时序，先测在当前完整链路延迟后仍存的条件可兑现价差，以及是否只是延迟造成的**陈旧报价假信号**。时间对齐以各所事件时钟 + 本地接收时钟双记；禁止用未来的同步快照泄漏标签。只有多日、多状态样本外净收益为正才考虑更复杂模型。

## 五、离线验证与上线闸门

- **回放必须按事件时间**：既存行情 / 订单回报对齐；延迟、post-only 拒单、部分成交、改单丢排队、两所最小量/手续费、断流都进入模拟。L1 盘口不足以精确回放队列时，用保守填单上界/下界；乐观全额成交只能做不可交易对照。
- **统一三种基线**：当前策略真实成交、同候选的可执行 TT、同候选的 MT/fishing shadow；以“每候选预期净收益 + 实际每笔归因 + 单腿尾部风险”三层比较，不用只看胜率或回测总收益。唯一当前配置对子是 DOGE 的 Binance/Gate 合约（`etc/config.json:22`），先做跨时间状态 walk-forward，跨币对可做稳健性校验但新增对子前须单独验证合约、费档、流动性及账户风控。
- **防过拟合**：同一冲击的连续 tick 不算独立样本；按日期/事件块划分训练/验证/测试，净边际报告置信区间、费用敏感性与最坏分位，对阈值做小范围稳定性检验。统计显著但净收益不足以覆盖尾部对冲损失时拒绝上线。
- **顺序**：① 审计 TT/MT 实际派发和真实成本，修好防失效闸门的设计；② 建候选—成交—对冲—平仓账本；③ A/B 模式选择与数量预算；④ shadow fishing；⑤ 盘口预测过滤；⑥ 数据链可用后再做成交流/lead-lag。每一步都应小名义、限额、可即时回退；平仓/强平不应被盈利预测模型延误。

## 六、最先需要回答的问题

1. 真实生产费档、返佣入账、两所最小名义与最近一个月的净 PnL / 单腿超时是多少？目前只有配置假设，没有证据证明哪一项贡献最大。
2. TT 信号创建后的实际 `algoMode`、`tradingTypeOrder`、`CreatePairOrder` 参数、主动子单 `orderType` 是否一致？建议用测试回放四方向及开平仓验证，优先于调参。
3. 当前 `dbp` 盘口更新时间/成交时间与策略本地接收时间的分布怎样？`spreadEffective` 在信号建单时是否同步阻断？若只在执行侧挡住，会产生“建了算法单但无法执行”的虚假候选。
4. 结算时间戳的**单位与语义**及两所真实账单能否对上？何时需要被动腿降级为更强制的对冲方式？

**建议取舍**：优先做“实际模式核对 + 双腿净收益计量 + 对冲尾部约束”，再做 fishing 的冲击回补模型；预测只作为**成交质量/执行选择器**，不要在未经验证时改变为单边价格预测交易。任何模型都不能保证提高盈利。
