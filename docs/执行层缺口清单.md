## 1. P0 —— 会让实盘真出事

### 1.1 重启后场上的孤儿单永远不撤，而且系统不知道它们存在

| 证据 | 位置 |
|---|---|
| `OrderManager::Recovery()` 整段被注释 | `OrderManager.h:18`、`OrderManager.cpp:15-33` |
| 全仓**没有**"查询交易所活动单"的接口 | 搜 `openOrders` / `QueryOpenOrder` → 0 结果 |
| 启动对账只比**持仓**，不比**在途单** | `PairTradingContext.cpp:1205-1251`（`ReconcilePair` 只碰 `pairTotalVolume`） |

**后果**：进程崩溃/重启那一刻挂在交易所的单，重启后变成无人认领的孤儿单。
它们随时可能成交，而本地账本、`errorFlag`、风控档位全都不知道。
更糟的是**运行期没有第二次对账**（见 1.2），所以这个洞不会被自动发现。

**要补的**：启动时先查一次交易所活动单 → 全部撤掉 → 再放行交易。
这需要一个 `QueryOpenOrders(accountId)` 的出向接口，目前 `tb` 只有按 `strategyOrderId` 查单。

### 1.2 运行期没有周期对账

`TryReconcile` 只在 `!IsTradingReady()` 时被调用（`PairTradingContext.cpp:1121-1126`）。
一旦进入 `StartupPhase::Trading`，**再也不会对账**。

⇒ 1.1 的孤儿单成交后，敞口漂移没人发现；任何"本地账本与交易所不一致"的事故，
都要等到下一次重启才暴露。

**要补的**：交易期内每 N 分钟一次轻对账（只比量，不一致就告警 + 冻结该对子，不自动改账）。

### 1.3 CANCELLING 下被动腿没有上界

`BaseAlgoOrder.cpp:414-427` 刻意不撤被动腿（注释写明"等成交把敞口平掉"），这是对的。
但**没有任何兜底**：被动腿如果挂在市场再也不回去的价位，这个对子会无限期停在
`ALGO_OS_CANCELLING`，单边裸腿一直存在。

`AlgoType_Rebalance` 能平，但只由**人工命令**触发（`AlgoContext.cpp:367-370`），
不是超时自动升级。

**要补的**：被动腿在 CANCELLING 下等超过 X 秒 → 自动转成"吃单平掉"（IOC/FOK），
并把这次升级计入告警。

### 1.4 没有"全平 / 一键停"

全仓搜 `closeAll` / `flattenAll` / `panicClose` → **0 结果**。
出事时只能人工逐单敲。配合 1.1（孤儿单）和 1.3（裸腿），这是最要命的组合：
**你既不知道场上有多少单，也没有一个按钮能全部收掉。**

**要补的**：一个"停止 + 撤全部 + 平全部"的命令，允许在 `errorFlag` 状态下执行。

## 2. P1 —— 会让账/价算错

### 2.1 被动腿 taker 做空时滑点符号反了（已修）

`BaseAlgoOrder.cpp:218` 原为：

```cpp
passivePrice = passiveTargetPrice * (1 + passiveTakerSlippage) * (1 - passiveTakerFeeRate);
```

做多分支是 `(1 + slip)`（付更多，保守，对），做空分支也是 `(1 + slip)`（收更多，**错**）。
同函数的 post-only 做空分支写的是 `(1 - makerSlip)`（`BaseAlgoOrder.cpp:216`），两者自相矛盾。
净 PnL 会系统性偏乐观 `2 × passiveTakerSlippage`。

已改为 `(1 - passiveTakerSlippage)`。改完 `tests/algo_exec` 结果不变（35/7，无回归）。

### 2.2 `CalculateTotalPriceVolume` 的合约信息查询被注释掉

`OrderManager.cpp:107-108`：

```cpp
md::InstrumentInfo info;
//smc->get_instrument_info(order.exchangeType, order.instType, order.instrument, info);
```

`info` 是默认构造，`calcType` 恒为默认值 ⇒ `calcType == 1`（反合约）那条分支永远进不去，
反合约的加权均价会算错。

**先确认还有没有调用点**：没有就是死代码，删掉比修好更干净。

### 2.3 `clientOrderId` 用的是 `rdtscp()`

`Utility.h:67-68`：`GenerateStrategyOrderId() { return crypto::rdtscp(); }`

问题不在"会不会重复"，在**可运维性**：
- 从 ID 看不出策略 / 对子 / 时间 ⇒ 对账、排障只能靠翻日志
- 跨重启的唯一性依赖"TSC 单调"这个隐含假设
- 交易所侧如果按 clientOrderId 去重，重启后语义不清晰

**要补的**：`<strategyTag><yyMMddHHmmss><seq>` 这种可读 ID，`rdtscp` 只做进程内去重。

## 3. 建议动手顺序

| 顺序 | 做什么 | 为什么排这里 |
|---|---|---|
| 1 | 把 `tradingTypeOrder` 分流修对，让 `algo_exec` 回到 140/0 | 没有绿的回归网，后面每一条都不敢改 |
| 2 | 1.4 全平/一键停 | 唯一一个"出事时救命"的东西，且不依赖新接口 |
| 3 | 1.1 + 1.2 孤儿单 + 周期对账 | 需要 `QueryOpenOrders` 接口，工作量最大，但这是 1.3 的前提 |
| 4 | 1.3 被动腿超时升级为吃单 | 依赖 1.2 的对账结果判断"是否真的裸腿" |
| 5 | 2.2 / 2.3 | 算价与可运维性，不救命但会持续放血 |

⚠️ 第 1 条是硬前置：**套件红的，等于没有回归网**，先修它再动别的。
