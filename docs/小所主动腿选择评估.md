# 小所「主动腿」选择评估（对手方 = Binance 被动腿）

> 命题：把**小所**放在**主动腿**（先成交腿 / 挂单腿），**Binance** 放在**被动腿**（对冲吃单腿），该选哪家小所。
>
> 本文只做选型评估与复测设计，**未修改任何源码或配置**。

**三条要点：**

1. **费率不是选所依据。** 18 家候选里 **13 家的 `F_mt` 恰好都是 9.0 bp**，最好（7.0）与最差（11.0）只差 4 bp。

2. **费率最优的那家实测最差。** MEXC 的 `F_mt` 最低（7.0 bp）、K 线上 89 个标的里 54 个有尾部，

**所以答案是：**
- 要**实测最强**：**Bitget**（其次 HTX），但要为它写一整套适配。

## 2. 主动腿的成本语义（从代码反推）

`quant_library/signal/SignalGenerator.h:85-86` 与 `algo/AlgoContext.cpp:378-379`：

```
makerTakerFs = activeMakerFeeRate + passiveTakerFeeRate + activeMakerSlippage + passiveTakerSlippage
takerTakerFs = activeTakerFeeRate + passiveTakerFeeRate + activeTakerSlippage + passiveTakerSlippage
```

- **MT 模式**：主动腿挂 `OT_POST_ONLY`（`config.json:67`），被动腿吃单 ⇒ 主动腿 **maker 费率**是主成本。
- **TT 模式**：主动腿穿价限价（`ttActiveOrderType=OT_LIMIT`，等效吃单）⇒ 主动腿 **taker 费率**是主成本。
- **被动腿恒为吃单腿**（`tests/algo_exec/suite.cpp:39`）。

对调后的执行成本：

| 模式 | 主动腿（小所） | 被动腿（Binance） | 费率合计 |
|---|---|---|---|
| MT | 小所 maker | Binance taker 0.05% | 小所 maker + **5.0 bp** |
| TT | 小所 taker | Binance taker 0.05% | 小所 taker + **5.0 bp** |

**注意被动腿那 5.0 bp 是常数**——这就是为什么选小所**不能靠比费率**，只能靠比「这家小所的机会能不能越过这条线」。

## 4. 上一轮同步实测结论（**这是选所的真正依据**）

你此前做过一轮 18 家候选的筛选，方法在 `cross-venue-spread-validation` 里：
先用 1 分钟 K 线粗筛，再用**同步采样**（同一窗口内并发抓各家最优买卖价）复核，
因为 1 分钟 K 线上「价差大」有一半是**交易所自己的时钟误差**：

```
survive_ratio = sync_p90 / kline_p90        # 实测中位数 0.49 —— 一半的尾部是假的
exec_basis    = max(bidA - askB, bidB - askA)   # 已经扣掉两边的点差
reach%        = exec_basis 超过该所 F_mt 的样本占比
```

**47 个 (venue, symbol) 组合的结果：**

| venue | survive | K 线 verdict | 同步 verdict |
|---|---|---|---|
| Bybit | 0.80 | TAIL EXISTS | usable，2/5 标的 |
| **Bitget** | **0.77** | TAIL EXISTS | **strong —— 3/5 标的越过费率** |
| **Gate.io** | 0.77 | TAIL EXISTS | 1/7 标的 |
| **HTX** | **0.73** | （曾被代理指标误判为"陈旧漂移"） | **exec +29.68 bp，reach 100% —— 全组最佳** |
| KuCoin | 0.41 | TAIL EXISTS | 2/7 标的 |
| **MEXC** | **0.18** | TAIL EXISTS | **never clears fees** |
| Bitunix | **0.16** | TAIL EXISTS | **never clears fees** |

**四条必须带上的解读：**

1. **K 线排序与同步排序不一致。** MEXC 在 K 线上有 54/89 个标的的尾部，同步采样下 0/7 越过费率线。
   **只看 K 线选所会选错。**
2. **HTX 被代理指标冤枉过。** 早期用一个「中位数漂移」代理把 HTX 写成"陈旧漂移"，但直接在 HTX 自己的宽价差标的上同步测量：
   survive 0.73、exec +29.68 bp、reach 100%。**代理与直接测量冲突时，直接测量赢。**
3. **大市值标的不能用来选所。** 每家都有 BTC/ETH 且都是最深盘口，其 basis（IQR ~0.5-1 bp）**低于每家的费率线**。
   BTC 扫描无法区分任何交易所。**尾部标的数量才是判据。**
4. **"大容量 + 大价差"多半是持续溢价，不是可套利的机会。** 用 `|mean edge| / sd(edge)` 判：
   持续溢价得分 **4~26**，真错价得分 **~1**。实测中**所有大容量的对子都是持续溢价**，
   而唯一真正的错价容量只有 **$0~$2,616**——**收敛性与容量是负相关的**。
   （典型例子：BNB 对 Binance 在六家交易所、30/30 次观测全为负，因为 BNB 是 Binance 自家代币，结构性溢价。）

> ⚠️ **原始脚本与产物已不在本机**（`/tmp` 与本仓库都没有），本节的数字来自 `cross-venue-spread-validation` 的结论记录。
> 决策前应当用新鲜数据重跑一遍（§8），但**排序不太可能翻转**，因为它是结构性的。

## 5. 分层推荐

### 第一层：实测首选 —— **Bitget**（其次 HTX）

- **Bitget**：同步实测 survive 0.77、3/5 标的越过费率线，是全组除 HTX 外唯一"strong"的。
  永续成交量第一梯队，且有大量**跟单/散户 taker 流**——这类流量对挂单腿结构性友好
  （成交来自非信息性冲击，而不是被职业做市商挑单）。
  账户体系（UTA 统一账户，支持逐仓/全仓/多资产保证金）比较完整。
- **HTX**：同步实测全组最佳（survive 0.73、exec +29.68 bp、reach 100%），
  但要注意它符号覆盖与主流差异大，且对手方风险评价一般。

**代价**：两家都不在现有四家里，要新写行情 + 交易 + 合约信息 + 资金/仓位/回报四块适配。

### 第二层：零工程验证路径 —— **Gate.io 主动 / Binance 被动**

理由不是 Gate 最优（实测只有 1/7 标的可用），而是**它是唯一能把"小所主动腿"这件事本身先验证掉的路径**：

- 行情端、交易端、合约信息全都有；`AlgoPairOrder` / `AlgoFishingOrder` / `BaseAlgoOrder` 的双腿逻辑已跑通。
- 只需对调 `pairKeys` 与 `activeAccountId`/`passiveAccountId`，并复核四个价差轴符号与阈值方向。
- 先用真实成交把「候选机会 → 主动腿成交 → 被动腿对冲 → 平仓」的**净收益账本**跑出来。
  **没有这张账本，换哪家小所都是盲选。**

## 7. 换所之前必须先定下来的三个数

不做完这三件事，换所是在调一个**没有标定过的公式**。

### 7.1 `feeSlippage` 块现在是未标定的

`config.json:110-123` 当前是：

```
activeMakerFeeRate  = -0.0002   ← 负数 = 假设主动腿拿 2bp 返佣
activeTakerFeeRate  =  0
passiveMakerFeeRate =  0
passiveTakerFeeRate =  0
basicSlippage       =  0
```

代入 §2 的公式：

```
F_mt = -0.0002 + 0 + 0 + 0 = -2.0 bp   （模型认为执行成本是"负的"）
F_tt =  0      + 0 + 0 + 0 =  0.0 bp   （模型认为执行成本为零）
```

而 `utrade_hft/docs/实盘接入与参数配置.md` 里推的是 `F_mt = 9.0 bp`、`F_tt = 13.0 bp`。**两者不一致，且配置里那份明显偏低。**

这直接关系到选所：**选哪家小所，决定的就是这几个数**。

- 若主动腿 = Binance 零售（maker **+2 bp**），`activeMakerFeeRate` 应为 `+0.0002` 而非 `-0.0002`。
- `passiveTakerFeeRate` 现在写 0，但被动腿（Binance）吃单实际是 **5 bp**。

**动作**：先用两所账户费率页 / fee rate 端点取真实 maker/taker，把四个数填准，再重算
`StartSpread = 分位数 × spreadAdjPct − direction × F` 的门槛。
否则换所争来的 2~3 bp，会被一个错 10 bp 的基线完全淹没。

### 7.2 对调两腿会翻转价差符号

见 §1 的警告。四个轴全部变号，阈值方向要整条复核。

### 7.3 小所的 tick / 最小名义价值 / 合约乘数

必须在 `contractinfo` 里确认目标币对在小所上的：tick size、最小下单量、最小名义价值、合约乘数、杠杆上限、逐仓/全仓。
**DOGE ≈ 0.0937 时，tick `0.00001` = 1.07 bp，tick `0.0001` = 10.7 bp**——tick 粗一档，很多机会在下单前就被量化掉。

## 8. 复测清单（用新鲜数据重跑，因为原始产物已不在本机）

在真正改配置前，做**纯采集、不下单**：

1. **同步采样**：对 `Binance + 每个候选小所` 的同一批**尾部标的**（不要用 BTC/ETH），
   在同一窗口内并发抓最优买卖价，算 `survive_ratio`、`exec_basis`、`reach%`。
   并发数要够（实测 54 请求 / 24 worker 时窗口跨 4.06 s、0/70 轮合格；64 worker 时跨 0.02 s、60/60 合格）。
2. **持久性检验**：对同一对子隔几秒采 ~20 次，算 `|mean edge| / sd(edge)`。
   远大于 1 = 持续溢价（不可交易）；≈1 = 真错价。
3. **容量**：必须做**逐档 book-walk**，不要用"距中间价 N bp 内的量"——
   宽点差的所（如 HTX OP 点差 31.3 bp）在 5 bp 带内恒为 0，会误读成"没有流动性"。
4. **双腿净收益账本**：按「候选机会 → 主动腿成交 → 被动腿对冲 → 平仓」逐笔记录实际费率、
   对冲滑点、单腿暴露时长、以及**未成交机会的机会成本**。
5. **先影子验证**（只记录模拟决策、不下单），再用**最小资金**实盘验证。

| 排名 | 交易所 | 24h 自报成交量 | 市场数 | 问题 |
|---|---|---|---|---|
| 5 | Bitget | $9.52B | 757 | 参照 |
| 11 | XT.COM | $10.59B | 721 | |
| 17 | CoinW | $19.30B | 330 | 成交量 > Bitget，市场数不到一半 |
| 18 | Pionex | $21.19B | 499 | 同上 |
| 19 | Toobit | $15.48B | 715 | |
| 20 | Echobit | $26.18B | **122** | 122 个市场做出 $26B |
| 21 | BTCC | $22.16B | **87** | 87 个市场做出 $22B |

**读法**：排名 20 以后，「第 27 名」不等于「第 27 名的流动性」。这些数字里混着刷量，
**不能用榜单排名做流动性代理**——必须用 §9.3 的直接测量。

另一个相对可靠的信号是**市场数**：20 名以后普遍只有 **87~184 个市场**，
而 1~11 名是 **622~846 个**。市场少 = 你要的币对可能根本没有，且自然流量更少。

### 9.2 这个队列里已经测过的两家都失败了，而且失败原因不同

| 交易所 | CMC 排名 | 实测结论 |
|---|---|---|
| **Bitunix** | 28 | **survive 0.16 —— never clears fees** |
| **Toobit** | 19 | 与 **XT.COM（第 11 名）是同一个数据源**：50.6% 收盘价完全相同、收益相关性 0.9909；且对 BTC 有 **+4.87 bp 稳定偏移**（IQR 仅 1.00 bp）= 钉住价格 |

**2/2 失败，且失败模式不同**（一个是「价差不成立」，一个是「根本不是独立行情」）。
这正是问题所在：**越往尾部走，失败原因是异质的**，不存在一个统一参数能调好。

### 9.3 尾部专有的失效模式（1~11 名基本不会遇到）

| 失效模式 | 具体表现 | 怎么查 |
|---|---|---|
| **盘口是死的/聚合的** | 点差 < 1 tick。实测 XT.COM 与 Toobit 对 BTC 的点差是 **0.001 bp**，而 tick 是 0.0082 bp ⇒ 只有 **0.14 tick** | **[A]** 点差必须 ≥ 1 tick；tick 取「相邻档位价差」的**众数** |
| **价格被钉住** | 不是围绕 0 震荡，而是**稳定单边偏移**。实测 XT.COM +4.87 bp、Toobit +4.88 bp，1000 分钟内 IQR 只有 1.00 bp | **[B]** 看**带符号**中位数，不是绝对值中位数 |
| **两家所其实是同一个源** | 完全相同的收盘价占比极高 + 收益相关性接近 1 | **[D]** 统计「收盘价完全相等」的比例并算收益相关性 |
| **交易所时钟误差被当成价差** | K 线上的 p90 价差有一半是假的（实测 survive 中位数 0.49） | **同步采样**：同一窗口并发抓各家最优买卖价 |
| **合约乘数 / 符号撞车** | 产生 1,000~14,000 bp 的「价差」。实测 OKX QNT 中位数 14,025 bp、Gate ONE 1,707 bp、Bitunix PUMP 2,883 bp | 中位数 \|basis\| 超过 ~100 bp 的符号直接丢弃 |
| **对手方** | 无牌照、披露少、提币暂停史、保险基金不透明 | 只能靠尽调，没有量化替代 |

### 9.4 经济上不会变好 —— 这才是关键

**「更小的所 = 更宽的价差 = 更多 alpha」是错的**，而且是可测量的错：

```
spearman(无条件 |basis|, 衰减%)  =  -0.927      ← 近乎完美单调
宽价差的所（无条件 ≥ 18bp）：平均衰减  -77.5%    ← 价差在扩大，不是收敛
窄价差的所（无条件 < 18bp）：平均衰减  +91.7%    ← 才收敛
```

**价差看起来宽的那些所，恰恰是价差不收敛的那些所。**「更宽更好」是反的。

叠加两条容量事实：实测每个机会的容量中位数只有 **$18~$3,215**；
而「大价差 + 大容量」的对子几乎全是**持续溢价**（`|mean|/sd` 4~26），
唯一真正的错价容量只有 **$0~$2,616** —— **收敛性与容量负相关**。越往尾部走，容量只会更小。

### 9.5 如果还要试，把它当成「筛选练习」而不是「接入项目」

成本很低，一个下午能筛掉一大批。顺序：

1. **[A]–[D] 四项静态检查**（点差 ≥ 1 tick / 带符号偏移 / 触档深度 / 完全相等收盘价占比）。
   这一步就能把「死盘口、钉住价、同源行情」全部筛掉——而这三类占了尾部的多数。
2. **同步 survive 测试**，且必须**逐所用它自己的宽价差流动标的**，不能用全局固定清单
   （此前用同一份 7 个标的的清单，导致 HTX 一个标的都没被测到，而 HTX 最后是全组最佳）。
3. **持久性检验** `|mean edge| / sd(edge)`：远大于 1 = 持续溢价，不是机会。
4. **逐档 book-walk 容量**，不要用「距中间价 N bp 内的量」（宽点差的所恒为 0，会误读成没有流动性）。

**只有在第 1~4 步都通过之后，才值得考虑写适配。** 而目前通过这四步的，仍然只有 Bitget / HTX 这一档。

## 10. 验证阶段的最短路径：只做 `contractinfo` + `db`（不做 `tb`）

**这个判断是对的**：`tb` 只管下单与回报，行情验证完全不经过它。
`db/src/main.cpp:63-65` 只起 `DbOperation`；`db/src/operation/DbOperation.cpp:35-59`
按配置里的 exchId 块**逐个 new Market** —— 所以**一个进程可以同时挂多个交易所**。

### 10.1 但 `contractinfo` 是硬前置，省不掉

| 位置 | 事实 |
|---|---|
| `db/src/base/BaseMarket.cpp:168` | `BaseMarket` **构造函数里直接调** `generateUnitInfo()` |

**所以顺序必须是：先跑 `contractinfo` 把合约信息写进 shm，再起 `db`。**


**关键：把 Binance 和候选所放进同一个进程、同一份配置。**

这样两条腿**共用同一个本地时钟**，时间戳可比 ——
**分成两个进程录会引入无法量化的时钟偏斜**，而那正是这次实验最怕的东西。

### 10.4 还缺一块：`db` 是写共享内存的，不落盘

`BaseUnit` 把数据发到 `Depth1Spmc` 等 SPMC 队列（`db/src/base/BaseMarket.cpp:51-75`），由 `dbp` 消费算价差。
**但验证需要的是原始逐笔 L1 + 时间戳，不是 `dbp` 的四轴价差**（`dbp` 的价差还依赖 `pairlist.xml` 的顺序约定，见 §1）。
所以要补一个小消费者把队列落成 CSV/Parquet。模板：`db/tools/db_shm_latency.cpp`、`db/tools/db_shm_perf.cpp`。

### 10.5 录什么，才能让这次实验真的能下结论

| 字段 | 为什么必须有 |
|---|---|
| **交易所时间戳**（报文里的） | 没有它就只能测「我的收包时刻」，**测不出交易所自身的陈旧度**——而陈旧度是最大的假信号来源（实测 K 线 p90 有一半是假的） |
| **本地收包时刻**（ns） | 把「交易所慢」和「我慢」分开 |
| best bid/ask 价格 + 量 | L1 基本盘 |
| 前 5 档（建议） | 后面算容量要用 |
| 序号（若该所提供） | 检测丢包 |

**两家必须用同一种流（都 L1），同一台机器、同一条网络路径。**

### 10.6 算这六个量

1. **点差**（相对 mid）的分位数，两家分别算
2. **前 N 档深度**（美元）
3. **带符号**中位数偏移 + 点差/tick 比 ⇒ 判死盘口与钉住价
4. **`survive_ratio`**：分钟级 p90 vs 同步 p90（有完整流就能重建同步切片）
5. **`exec_basis = max(bidA − askB, bidB − askA)`** 与 **`reach%`**（越过 `F_mt` 的占比）
6. **持久性** `|mean edge| / sd(edge)`

**判据**：只有 `survive_ratio` 高、`reach%` 显著大于 0、且持久性 ≈1（不是持续溢价）时，才进入下一阶段。

### 10.7 两条路的取舍（诚实版）

| | 独立录制脚本（不接入） | `contractinfo` + `db`（你的方案） |
|---|---|---|
| 工作量 | ~1 天 | ~1~2 周（两家） |
| 能否回答「是否可以」 | **能，完全能** | 能 |
| 数据是否代表生产链路 | 否（自有代码，延迟与生产不同） | **是**（走的就是将来要用的管线） |
| 是否改动生产代码 | 不 | 新增模块（都是增量，不动现有逻辑） |
| 后续是否复用 | 不能 | **能** —— trading 侧只需再加 `tb` |

**所以：只要 go/no-go 就独立脚本更快；本来就要接入，你的方案顺路把管线建好了，而且录到的延迟是生产可比的。**
这正是你这个判断的价值。

### 10.8 录制时长

**≥ 14 天**，且必须覆盖：一个完整周末、至少一次资金费结算密集时段、至少一段高波动。
**不要把一段平静的行情当成压力测试** —— 真正的风险是交易所停摆/插针/提币暂停，平静月份里不会出现。
