## 1. 被测对象与调用链

```

  ├── SubmitAlgoOrder(BaseAlgoOrder*)         ★ A 组
  │     ├── alogOrderManager.SubmitAlgoOrder  入册（★ 所有权转移）
  │     ├── SpreadManager::AddSpreadPara      建价差槽位
  │     └── dbp::DbpReader::Subscribe         订阅价差
  │
  ├── OnSpread(topic, pdata)                  ★ B / E 组
  │     ├── openOrderFlag = curDelay && curDepthDelay && curTradeDelay   三道延迟闸门
  │     ├── CancelOrderOnSpread(pdata)        ★ 撤单（E 组）
  │     │     ├── CANCELLING 分支：只撤主动腿，10ms 门槛
  │     │     └── else 分支：时间撤单 / 被动腿价格偏离 / 主动腿价格偏离
  │     └── PairOrder 报单（按 tt/mt × OL/OS 四个 switch）
  │           └── AlgoPairOrder::GetTargetPairOrder    算目标价/量
  │                 └── PairOrder::CreateActiveOrder   orderStatus = OS_PEND
  │                       └── QuantTrade::CreateOrder  ──► om::TradeClient（★ 出向边界）
  │
  ├── OnOrder(orderResponse)                  ★ C 组
  │     ├── 解析 strategyRef "algoPairId_pairId"
  │     ├── orderMgr.UpdateOrderOnOrder
  │     ├── UpdateAlgoPairOrderByQuantOrder   同步量/价到 pairOrder
  │     ├── 终态(FILLED/REJECTED/CANCELED) ──► UpdateAlgoPairOrderByDeleteQuantOrder
  │     │                                       （★ 子单从 orderMgr 删除）
  │     └── PairOrderTrade(pairOrder)         补报被动腿 / 收口
  │
  ├── OnTimer(eventTime)                      ★ D 组
  │     ├── 卡单检查（PEND/CANCELLING > 5s → QueryOrder；queryCount > 5 → ERRORCANCELED）
  │     ├── 结束订单检查（四个 switch 全关 && |pairTotalVolume| < minSize → ALGO_OS_FILLED）
  │     └── allPairOrders == 0 && CANCELLING → ALGO_OS_CANCELED
  │
  └── OnBalance(balance)                      资金（SeedFunds 走这条真实入口）

PairTradingContext                            ← 策略侧（G / H 两条链的起点）
  ├── OnSpread ──► UpdateRtSpread + ProcessPairSignal
  ├── ProcessPairSignal ──► SubmitAlgoOrder ──► AlgoCommandCallback ──► AlgoContext::SubmitAlgoOrder
  ├── ProcessRisk ──► RiskManager::CheckRisk ──► AlgoOrderModifyCallback ──► AlgoContext::SubmitAlgoOrder(id, CANCEL, …)
  └── OnAlgoOrderUpdate（执行侧同线程直接回调）
        ├── 非终态：只同步量/价
        └── 终态：OnAlgoFinished + RecalcOrderParams + ClearActiveAlgoOrder
```

**串起两边的那根线**（`Boot()` 里装的回调）：

```cpp
fx.ptCtx.SetAlgoCommandCallback([&fx](BaseAlgoOrder* o) {
    fx.created.push_back(o);
    fx.algoCtx.SubmitAlgoOrder(o);          // ★ 策略层建的单，立刻注册进执行层
});
fx.ptCtx.SetAlgoOrderModifyCallback([&fx](int64_t id, stra::CommandType c, const stra::AlgoOrderModify* m) {
    fx.modifyCalls.emplace_back(id, c);
    fx.algoCtx.SubmitAlgoOrder(id, c, m);   // ★ 策略层要撤的单，立刻传给执行层
});
```

**两个关键不变量**（很多用例围着它们转）：

1. **子单报出去时是 `OS_PEND`，不是 `OS_NEW`。** `CancelOrderOnSpread` 只处理
   `OS_NEW || OS_PARTFILLED || OS_FILLED` —— 任何撤单用例都必须先喂一条交易所确认回报
   把子单推到 `OS_NEW`，否则撤单路径进不去（表现为"撤单条数 = 0"）。
2. **终态子单会被从 `orderMgr` 删掉，不是留在里面变 `OS_FILLED`。**
   成交量要去 `pairOrder.activeTotalVolumeOnOrder` 上看。

### A. 注册（4 用例 / 12 断言）

被测函数：`AlgoContext::SubmitAlgoOrder(BaseAlgoOrder*)`

| ID | 用例 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| A1 | 首次注册 | 策略层已建单 | `SubmitAlgoOrder(o)` | ① 拿到 `algoOrderId > 0`；② `AlgoOrderManager::SeletAlgoOrderByAlgoOrderId(id) == o`（**同一个对象指针**，不是拷贝）；③ `algoOrderStatus = ALGO_OS_NEW`；④ `commandType = CommandType_TRADING`；⑤ `algoType = AlgoType_PairTrading`；⑥ `dbpReader.subscribed` 里出现该价差 key；⑦ `SpreadManager::GetSpread(key) != nullptr`（槽位已建） |
| A2 | 重复注册同一价差 | 已注册过一次 | 再注册一张同 key 的单 | 订阅数**不增加**（`Subscribe` 内部有去重）；但新单**仍然入册**（`AlgoOrder(999) == o2`） |
| A3 | 空指针 | — | `SubmitAlgoOrder(nullptr)` | 不崩、不报错 |
| A4 | 改一个不存在的 id | 有一张在册单 | `SubmitAlgoOrder(99999, CANCEL, nullptr)` | 在册单不受影响（`updateTime` 不变、状态不变） |

> **所有权**：`SubmitAlgoOrder` 一旦被调用，算法单的**所有权就转移给了 `AlgoContext`** ——
> `alogOrderManager` 是 `AlgoContext` 的**成员**（不是指针），其析构函数会 `delete` 掉
> 每一个注册过的指针（`AlgoOrderManager.cpp:9-17`）。夹具里的 `created` 只是"策略层报出了哪些单"
> 的观察日志，**绝不能**再 `delete` 一遍（会 double free，进程直接 abort）。

### B. 拆单报单（5 用例 / 29 断言）

被测函数：`AlgoContext::OnSpread` → `BaseAlgoOrder` 的配对报单分支 → `AlgoPairOrder::GetTargetPairOrder`
→ `PairOrder::CreateActiveOrder` → `QuantTrade::CreateOrder`

| ID | 用例 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| **B1** | **TT/OL 主动腿整份字段** | 有一张 `ttOLSwitch` 的算法单 | `OnSpread(有效行情)` | 出向**恰好 1 条**报单，且字段逐一核对（见下表） |
| B2 | `spreadEffective = false` | 同上 | `OnSpread(pdata.spreadEffective = false)` | 不报单；**也不产生 pairOrder** |
| B3 | 行情延迟 | 同上 | `pdata.generateTs = now - 1s`（> `curspreaddelay = 50ms`） | 不报单（`curDelay` 闸门挡住） |
| B4 | 在途 pairOrder 去重 | `rebalance` 模式下 | 连喂两帧有效行情 | 第一帧报 1 条；第二帧**不重复报**（`GetSizeByOrderType(TAKER_TAKER) != 0`）；`pairOrder` 仍只有 1 张 |
| B5 | 价差 key 不匹配 | 同上 | `OnSpread(topic = 别的 key)` | 不报单（`strcmp(pairInstrumentKey, topic->__name)` 不命中） |

**B1 逐字段断言**：

| 层面 | 断言 |
|---|---|
| 子单 | 已登记进 `orderMgr`；`isActiveOrder = true`；`orderStatus = OS_PEND`；`volume = 1.0`（受 `min(targetVolume, ttTargetVolume)` 约束） |
| 配对单 | 已登记进 `pairOrderMgr`；`tradingTypeOrder = TAKER_TAKER`；`tradingTypeOffset = OPEN_LONG`；`activeDirection = DT_SHORT`；`passiveDirection = DT_LONG`；`algoPairId == algoOrderId` |
| 出向指令 | `exchangeTypeEnum = BINANCE`（主动腿）；`instId = DOGE-USDT`；`offsetFlag = OF_OPEN`；`direction = DT_SHORT`；`orderType = OT_MARKET`（TT 主动腿吃单）；`volume = 1.0`；`clientOrderId == 子单 strategyOrderId`；`strategyId = "test1"`；`strategyRef == "algoOrderId_pairId"` |

> **`OPEN_LONG` 的腿约定**：主动腿（BINANCE）是 `DT_SHORT`，被动腿（GATEIO）是 `DT_LONG`。
> 也就是说"开多"在主动腿上是先卖出 —— 这是配对交易的腿方向约定，不是笔误。
>
> **`strategyRef` 格式**：`QuantTrade::CreateOrder` 里 `sprintf(ref, "%ld_%ld", algoPairId, pairId)`。
> `AlgoContext::OnOrder` 解析出 `v[0]` 当 `algoId`（拿去 `AlgoOrderManager` 查）、`v[1]` 当 `pairId`。
> `PairOrder.algoPairId` 在 `AlgoPairOrder.cpp:573` 里是从 `unsignedAlgoOrderId` 赋的，
> 所以**两者当前恰好相等** —— 但这是巧合，用例里一律用 `MakeRef(o, pairId)` 生成，不手写。

### D. 撤单（7 用例 / 21 断言）

被测函数：`AlgoContext::SubmitAlgoOrder(id, CommandType_CANCEL, …)` → `BaseAlgoOrder::CancelOrderOnSpread`
→ `QuantTrade::CancelOrder` → `OnTimer` 收尾

| ID | 用例 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| D1 | CANCEL 请求 | 在册、状态 `NEW` | `SubmitAlgoOrder(id, CANCEL, nullptr)` | `algoOrderStatus = ALGO_OS_CANCELLING`；`commandType = CommandType_UCANCELLING`；`cancelOrderTime > 0` |
| D2 | 重复 CANCEL 幂等 | 已在 `CANCELLING` | 再发一次 | 状态不变、`cancelOrderTime` **不刷新** |
| D3 | CANCELLING 下撤在途主动腿 | 主动腿已报出 **且已确认到 `OS_NEW`** | `OnSpread(spreadEffective = false)` | 出向**恰好 1 条撤单**；`clientOrderId` 就是那条子单；发给主动腿交易所（BINANCE）；**不再报新单** |
| D4 | 撤单回报 → 收尾 | 接 D3 | `OnOrder(OS_CANCELED)` → `OnTimer` | 子单清零 → `pairOrder` 被删除；此时仍停在 `CANCELLING`（要等 `OnTimer`）；`OnTimer` 后 `algoOrderStatus = ALGO_OS_CANCELED`、`commandType = CommandType_CANCELED` |
| D5 | 已终结的单拒绝 CANCEL | 已 `CANCELED` | 再发 CANCEL | 被拒；`updateTime` 不动 |
| D6 | MODIFY 快照 | 在册、`NEW` | `SubmitAlgoOrder(id, MODIFY, m)` | `profitSwitch` / `profitPct` 被覆盖；`ttOS` 参数被覆盖；**状态不变**（仍是 `NEW`） |
| D7 | CANCELLING 期间拒绝 MODIFY | 已在 `CANCELLING` | `SubmitAlgoOrder(id, MODIFY, m)` | 被拒（`profitPct` 未被改成 0.0042）—— 避免"撤单"和"改参"两套流程互相覆盖 |

> **D3 的前置是关键**：子单刚 `CreateActiveOrder` 出来时是 `OS_PEND`，
> 而 `CancelOrderOnSpread` 的 else 分支第 448 行先卡 `orderStatus ∈ {OS_NEW, OS_PARTFILLED, OS_FILLED}`。
> 不先喂一条 `OS_NEW` 确认回报，撤单条数就是 0。

### E. 超时撤单（3 用例 / 10 断言）

被测函数：`AlgoContext::OnSpread` → `BaseAlgoOrder::CancelOrderOnSpread` 的 else 分支

`CancelOrderOnSpread` 的 else 分支有三条撤单规则，本组覆盖其中两条：

| ID | 规则 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| E1 | **主动腿 Taker 时间撤单**（`BaseAlgoOrder.cpp:464`） | 主动腿是 `OT_MARKET`；已确认 `OS_NEW`；`activeTakerCancelOrderTime = 5s` | `AgeChildOrders(o, 6s)` 把子单 `updateTime` 拨老 6 秒，再 `OnSpread` | 出向**恰好 1 条撤单** |
| E2 | 未超时不撤 | 同上但子单是刚报的 | `OnSpread` | 撤单条数 = 0 |
| E3 | **主动腿 Maker 价格偏离撤单**（`BaseAlgoOrder.cpp:505-514`） | MT 单（`pi.autoFlag = false`）→ 主动腿子单 `orderType = OT_POST_ONLY`；已确认 `OS_NEW` | 把 `activeAskPrice[0]` 压低 5%（`DT_SHORT` 方向；`DT_LONG` 则抬高 `activeBidPrice[0]`），`activeMakerCancelOrderPct = 0.001` | 出向 ≥ 1 条撤单 |

> **E3 为什么必须是 MT 单**：`OT_POST_ONLY` 的判定落在**子单**的 `orderType` 上
> （`CancelOrderOnSpread` 读的是 `orderMgr` 里的 `QuantOrder`），而 `OT_POST_ONLY`
> 只有 `MAKER_TAKER` 配对单才会产生（`GetTargetPairOrder` 里 `acOrderType = OT_POST_ONLY`）。
> TT 单的主动腿恒为 `OT_MARKET`，永远走不到这条 Maker 分支。
>
> **E3 为什么不需要 `AgeChildOrders`**：这条"主动腿价格变化撤单"**没有时间门槛**
> （对比第 464 行那条"时间撤单"，它有 `activeMakerCancelOrderTime`）。

### F. 风控平仓（3 用例 / 13 断言）

被测函数：`PairTradingContext::ProcessRisk` → `RiskManager::CheckRisk` → `RequestCancelAlgoOrder`
→ `AlgoOrderModifyCallback` → `AlgoContext::SubmitAlgoOrder(id, CANCEL, …)`

| ID | 用例 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| F1 | 对子被算法单占着 → 只请求撤单 | 对子已挂上算法单；碎单风控命中 | `ProcessRisk(pi)` | 发出**恰好 1 次**变更回调；回调的 `id` 就是在册算法单；`cmd = CommandType_CANCEL`；执行侧收到 → `ALGO_OS_CANCELLING`；**不另报强平单** |
| F2 | 强平单在途 → 早退 | `pi.riskCloseOrderInFlight = true` | `ProcessRisk(pi)` | 早退，**不再发撤单**；算法单状态未被改动 |
| F3 | 风控撤单走完整条链 | 主动腿已报出并确认 | `ProcessRisk` → `OnSpread` → `OnOrder(OS_CANCELED)` → `OnTimer` | `CANCELLING` → 撤掉在途主动腿 → `ALGO_OS_CANCELED` |

> `CheckRisk` 的第一条是 `CheckTinyClose`（碎单）：
>
> ```
> |pairTotalVolume| > 1e-9                              有持仓
> CalcPositionValue() = |pairTotalVolume * 腿价 * multiple| < 25 USDT
> ```
>
> 夹具的 `ArmTinyCloseRisk(pi)` 就是构造这个条件（`pairTotalVolume = 0.01`、腿价 100、
> `multiple = 1` → 市值 1 USDT < 25）。这是一条**真实存在**的风控分支，
> 不是为了测试新造的开关。

### G. 全链路一：成交闭环（6 用例 / 16 断言）

**一条链跑完"行情 → 建单 → 拆单 → 成交 → 补被动腿 → 收口"。**

| 步 | 事件 | 断言 |
|---|---|---|
| G1 | `ptCtx.OnSpread(策略行情)` + `ProcessPairSignal(pi)` | 策略层报出**恰好 1 张**算法单；已在执行侧入册；`ALGO_OS_NEW`；`pi.hasActiveAlgoOrder = true` |
| G2 | `algoCtx.OnSpread(执行行情)` | 拆出并报出**主动腿子单**（出向 1 条） |
| G2b | `OnOrder(OS_NEW)`（交易所确认） | 主动腿仍在子单簿 |
| G3 | `OnOrder(OS_FILLED, 1.0)`（主动腿成交） | 补报被动腿（出向 2 条）；主动腿**终态后从子单簿出清**；子单簿里只剩新报的被动腿；`pairOrder` 仍在（未收口）；`pairOrder.activeTotalVolumeOnOrder = 1.0` |
| G4 | `OnOrder(OS_NEW)` + `OnOrder(OS_FILLED, 1.0)`（被动腿确认并成交） | 子单簿**清零**；`pairOrder` **收口并从 `pairOrderMgr` 删除**；收口后不再报新单 |
| G5 | （同线程回调） | 策略侧收到执行侧回传 → 对子**拿到持仓**（`pi.HasPosition()`）；算法单**未终结** → 对子**仍被占着** |

> **G5 为什么"对子仍被占着"**：`PairTradingContext::OnAlgoOrderUpdate` 分两档
> （`PairTradingContext.cpp:1011-1029`）：
>
> - **非终态** → 只同步量/价，**不释放对子、不做结算**；
> - **终态** → `OnAlgoFinished` + `RecalcOrderParams` + `ClearActiveAlgoOrder`。
>
> 两腿成交、`pairOrder` 收口之后算法单状态**仍是 `ALGO_OS_NEW`** ——
> 四个 switch 还开着，这是个持续策略，会继续等下一次开仓机会。
> 所以"回传生效"成立、而"对子被释放"**不**成立。

### H. 全链路二：撤单闭环（6 用例 / 15 断言）

**一条链跑完"行情 → 建单 → 拆单 → 风控命中 → 撤单 → 撤在途腿 → 终结"。**

与 F 组的区别：F 是"风控这一环"的**单元**测试，H 是把风控当成链路里的**一环**跑通整条。

| 步 | 事件 | 断言 |
|---|---|---|
| H1 | 行情 + 信号 | 算法单已建 |
| H2 | `algoCtx.OnSpread` + `OnOrder(OS_NEW)` | 报出主动腿子单；确认后在途（可撤） |
| H3 | `ArmTinyCloseRisk(pi)` + `ProcessRisk(pi)` | 前置：对子已被算法单占住、`currentAlgoOrderId == algoOrderId`；风控命中 → 策略层发出**恰好 1 次**变更回调；撤的就是这张算法单；`cmd = CANCEL`；执行侧收到 → `ALGO_OS_CANCELLING` |
| H4 | `AgeChildOrders(o, 20ms)` + `OnSpread(spreadEffective = false)` | 出向 ≥ 1 条撤单；撤的**正是那条主动腿子单** |
| H5 | `OnOrder(OS_CANCELED)` | 子单簿清零；`pairOrder` 收口删除 |
| H6 | `OnTimer(now)` | `algoOrderStatus = ALGO_OS_CANCELED`，全链路走完；终结后在宽限期内仍能查到（留给策略层读状态） |

> **H4 为什么必须 `AgeChildOrders`**：`CancelOrderOnSpread` 的 `CANCELLING` 分支
> （`BaseAlgoOrder.cpp:407-444`）比 else 分支更保守 —— 它只撤主动腿，
> 且要求 `nowTime - order.updateTime > 1000*10`（10ms）。
> 子单是刚报出来的，必须先把 `updateTime` 拨老才跨得过这道门槛。
> `AgeChildOrders` 直接改 `updateTime`，比 `sleep` 稳（不受 CI 负载影响，也不拖慢用例）。
>
> **H4 为什么只撤主动腿**：撤单时两条腿的处置是**刻意不对称**的
> （`BaseAlgoOrder.cpp:416-422` 有注释「2026-09-23 已确认，勿"顺手修"」）：
> 主动腿有在途单 → 说明还没成交、场上没有敞口 → 直接撤掉；
> 被动腿有在途单 → 说明主动腿已经成交了、**存在单边敞口** → 必须先等被动腿成交把敞口平掉。

## 6. 桩保真度（写桩时踩过的坑）

桩可以少实现，但**不能改变语义**。本套件踩到的前三条都是"静默假阴性"——
测试红了但原因不在被测逻辑上：

| # | 桩 / 夹具的错 | 症状 | 真值 |
|---|---|---|---|
| 1 | `stubs/basic/StrategyConfig.h` 让 `GetTradesThreshold()` 返回 `0` | `tradesDelayThreshold = 0 * 1000 = 0`，`0 < 0` 恒假 → `curTradeDelay` 永远 `false` → **一条子单都报不出来** | 真实 `StrategyConfig.cpp:36` 是 `itemMd.get<int>("tradesshold", 1)`；键名拼写是 **`tradesshold`**，且 `etc/strategy.ini` 的 `[MD]` 段里**没有**这个键 → 走默认值 **1**。桩必须返回 `1` |
| 2 | 夹具给两腿盘口填了**一样**的量（都 `10000`） | MT 单一条子单都报不出来（TT 单正常） | `GetTargetPairOrder` 的 MAKER_TAKER 分支有守卫（`AlgoPairOrder.cpp:93-114`）：`if (activeAskAmount1 >= passiveAskAmount1) return pairOrder;` → 返回空单。被动腿量必须**大于**主动腿（夹具用 `30000`） |
| 3 | 夹具给策略层喂的行情把 `spreadAskAsk` 也填成 `-1.0` | G 的"信号成立"建不出算法单（`created = 0`） | `SignalGenerator::CanOpen` 有 sanity（`SignalGenerator.cpp:266-270`）：`if (!isnan(s) && abs(s) > 0.1) → "spreadAskAsk abnormal > 10%" → 拒绝开仓`。而 `PairTradingContext::OnSpread` 会用 `pdata` **覆盖** `pi.rtSpread`。所以夹具分了两个构造器：`FreshData()`（执行侧，四个口径都给 `-1.0`）与 `FreshStrategyData()`（策略层，`spreadBidAsk = -1.0` 让 ttOL 触发，其余三个给 `-0.001`） |

> **共同教训**：桩返回一个"看起来无所谓"的默认值，会把被测逻辑悄悄关掉。
> 写桩时要回去读真实实现的默认值，而不是随手填 `0`。

另外两条是**夹具对生产语义的想当然**（不是桩的错，但同样表现为假阴性）：

| # | 想当然 | 症状 | 真值 |
|---|---|---|---|
| 4 | 主动腿成交后应该以 `OS_FILLED` 留在 `orderMgr` 里 | C1 / G3 断言失败（`kids = 1` 但 `active = 0`） | 终态子单被 `UpdateAlgoPairOrderByDeleteQuantOrder` → `orderMgr.DeleteOrderByOrder` **删掉**（`BaseAlgoOrder.cpp:160-172`）。成交量要看 `pairOrder.activeTotalVolumeOnOrder` |
| 5 | 子单报出去就能撤 | E1 / E3 / H4 撤单条数为 0 | `CreateActiveOrder` 给的是 `OS_PEND`，而 `CancelOrderOnSpread` 只撤 `OS_NEW / OS_PARTFILLED / OS_FILLED`。必须先喂一条交易所确认回报 |

## 7. 怎么跑

```bash
cd tests/algo_exec
./run.sh              # 编译并运行
./run.sh -v           # 额外打开 -Wall -Wextra（suite.cpp 自身零 warning）
CXX=g++-13 ./run.sh   # 指定编译器
```

编译器自动挑选（`$CXX` → `/usr/bin/g++` → `/usr/bin/c++` → `/usr/bin/clang++` → PATH），
挑到后打印并校验可执行。目标环境是 Ubuntu 服务器；**macOS 上 `/usr/bin/g++` 是 clang++ 的软链**，
所以这个顺序两边都安全。

期望输出结尾：

```
PASS: 140   FAIL: 0
ALL PASS
```

> **本机（macOS）无法验证 libstdc++ 那条构建路径** —— 这台机器上没有真的 GNU g++，
> `/usr/bin/g++` 其实是 clang。所以 `#define private public` 之前那份 std 头清单是否足够，
> 要在 Ubuntu 服务器上跑一次 `./run.sh` 才算确认。
